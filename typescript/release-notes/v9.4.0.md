## Highlights

- **wow-bi records only what it cannot observe.** BI layout 8 replaces the ownership registry table with a durable inventory on the deployment anchor: every store and queue the deployment created. A recorded store or queue that disappears makes `DEPLOY` refuse and ask for `RESET`, instead of quietly creating an empty table ([BI deployment and recovery](https://wow.ahoo.me/guide/bi-operations#ownership-and-the-anchor)).
- **`DEPLOY` renders only changes.** One reconciler decides each object's action. An idempotent `DEPLOY` is two `CREATE DATABASE IF NOT EXISTS` statements plus the anchor, and it no longer drops and recreates verified Kafka consumers, which could lose messages with Keeper offset storage (#4028, #4034).
- **`BiScriptService`** runs prepare → inspect → render on a bounded scheduler, so callers other than the Starter's route (a CLI, a batch job) need no orchestration of their own ([BI](https://wow.ahoo.me/guide/bi#structured-result-api)).

> [!IMPORTANT]
> **Every existing BI deployment is rebuilt once.** After upgrading, run one confirmed `RESET` with 9.4.0, then one `DEPLOY`, then drop the old registry table by hand ([upgrade steps](https://wow.ahoo.me/guide/bi-operations#upgrade)). Outside `wow-bi` nothing changes: the API, REST behaviour, configuration, storage and wire formats are those of 9.3.0, and 9.3.x and 9.4.0 nodes can run side by side ([migration guide](https://wow.ahoo.me/guide/migration#upgrading-from-9-3-to-9-4-0)).

## Breaking

**Policy.** 9.4.0 breaks only `wow-bi`, the ClickHouse BI sync-script generator. The maintainer decided (2026-10-09) that `wow-bi` carries no compatibility burden: no migration code, no deprecation cycle, no compatibility shims. Its ClickHouse layout is the single explicit exception to the v9 frozen-storage boundary. Every other v9 REST, storage and wire surface is unchanged.

### TypeScript

No API changes. `@ahoo-wang/wow-view-engine` picks up a `lucide-react` bump (#4038).

### Kotlin / JVM

#### `wow-bi`

- **`BiScriptService` owns the pipeline; the observed model is internal** (#4035). New: `BiScriptService(inspector).generate(options, operation) { namedAggregates }`, a `Mono<BiScriptResult>` that prepares, inspects and renders on a bounded scheduler and reports a saturated scheduler as `BiDeploymentInspectionException.Unavailable`. Now `internal`: `ObservedBiDeployment`, `ObservedBiObject`, `BiObjectMetadata`, `BiObjectMetadataCodec`, `BiDeploymentDescriptor`, `BiConsumerIdentity`, `BiObjectKey`, `BiObjectKind` and `BiDeploymentPhase`. `BiDeploymentInspection.Available` stays a public type, but its constructor and `deployment` are no longer public, so only this module can create one. Removed: `BiScriptGenerator.generate(namedAggregates, operation, inspection)`. **Affects:** code that calls `wow-bi` directly, and custom `BiDeploymentInspector`s that built an `Available` themselves. **Migrate:** call `BiScriptService`, or `generator.generate(generator.prepare(namedAggregates), operation, inspection)`; a custom inspector can wrap `ClickHouseBiDeploymentInspector` or `NoOpBiDeploymentInspector` (to add metrics, for example) but cannot fabricate an observation. `api/wow-bi.api` shrinks from 437 to 292 lines; the Starter's API is unchanged.

### Server behaviour

#### BI storage layout 8: the anchor's durable inventory replaces the ownership registry (#4031)

Up to 9.3, each BI deployment kept an ownership registry table, `__wow_bi_registry_<deploymentId>` in the consumer database, beside the ownership comments on every object. From 9.4.0, the facts that cannot be observed in the catalog (the phase, the configuration and topology fingerprints, the consumer identity, and the inventory of every store and queue the deployment created) live in the comment of the `__wow_bi_deployment` anchor, which every script writes last. Ownership stays in each object's `wow-bi:` comment. 9.4.0 rejects a deployment of an older layout, and 9.3 and earlier reject layout 8. **Affects:** every existing BI deployment.

**Before upgrading:** confirm that Kafka retention covers the history to replay, and back up the ClickHouse scope. Then, with 9.4.0: one confirmed `RESET` (it recognizes the old objects' ownership, drops them, and rebuilds the scope with layout 8), one `DEPLOY` (it records the queues), and finally drop the unused registry by hand. On a cluster, keep `ON CLUSTER` and `SYNC`:

```sql
DROP TABLE IF EXISTS `<consumerDatabase>`.`__wow_bi_registry_<deploymentId>` [ON CLUSTER '<cluster>'] SYNC;
```

`<deploymentId>` is the `deploymentId` field in the `wow-bi:` comment of any BI object, for example `SELECT comment FROM system.tables WHERE name = '__wow_bi_deployment'`. Rolling back to 9.3 means restoring the ClickHouse backup taken before the `RESET`.

**Mixed 9.3/9.4.0 cluster:** BI scripts are generated on request, not by the running nodes, so the application nodes themselves run side by side. Generate BI scripts only from 9.4.0 once the deployment is rebuilt: a 9.3 node refuses a layout 8 deployment, and a 9.4.0 node refuses `DEPLOY` on a layout 7 one until it is reset.

#### `DEPLOY` renders only changes (#4034)

`BiReconciler` compares the desired layout with the observed catalog once and gives each object one action: create a missing object, keep a store or queue that exists, keep a consumer whose whole ingress chain is verified, keep a view whose definition is verified, and replace anything else. Before, every `DEPLOY` recreated all computed objects. An idempotent `DEPLOY` is now two `CREATE DATABASE IF NOT EXISTS` statements plus the anchor, where 9.3 recreated every computed object and rewrote the registry; view drift replaces only the drifted view; consumer drift pauses and recreates only that stream's consumer chain. **Affects:** operators who review or diff BI scripts, and tooling that expects every object in every script. **Before upgrading:** nothing beyond the `RESET` above. **Mixed cluster:** not applicable (see above).

## Behaviour changes

- **`DEPLOY` refuses when a recorded store or queue is missing** (#4031). Losing a store loses history, and losing a Keeper-mode queue loses offsets, so instead of creating an empty table `DEPLOY` answers `400` ("lost recorded durable objects …; RESET is required") and names the objects. **Act:** back up, then run a confirmed `RESET`. A desired store or queue that was never recorded (a first creation, or a rerun after an interruption) is still created.
- **A store whose aggregate left is kept and stays recorded** (#4031). `DEPLOY` still never drops a store; the store of a removed aggregate remains in the anchor's inventory, so its later loss is also detected.
- **`RESET` records the stores only** (#4031). Its anchor is written before Kafka ingress; the following `DEPLOY`, which the runbook already requires, records the queues.

## Fixes

- **A no-op `DEPLOY` no longer drops verified Kafka consumers** (#4028). Every `DEPLOY` dropped and recreated the consumer materialized views on retained queues. With `kafkaOffsetStorage = KEEPER` (ClickHouse `StorageKafka2`), a drop that landed between a poll cycle's view check and its pipeline build left that cycle with no views: it committed the offsets of what it read and wrote nothing, so those messages were lost. The behaviour dates from 8.10.0; with `BROKER` (the default) the window is microseconds wide. Now verified chains stay attached. **Residual:** a `DEPLOY` that repairs consumer drift still recreates that stream's chain; with `KEEPER`, stop the producers or let the topic drain before it, or use `RESET` ([operations](https://wow.ahoo.me/guide/bi-operations#operation-decision)).
- **A `DEPLOY` right after `RESET` on a cluster no longer fails with `REPLICA_ALREADY_EXISTS`** (#4030). `RESET` dropped the replicated registry without `SYNC`, so the Atomic database deferred the drop (480 s by default) and the next `DEPLOY` collided with it. Affects 9.3.0 cluster deployments; layout 8 has no registry.
- **The 9.4.0 pre-release review fixes:** a `DEPLOY` after an interrupted `RESET` answers `400` ("retry RESET with the same configuration") instead of `502`; and configured values that contain a single quote (topic prefix, Kafka bootstrap servers, Keeper path prefix, cluster name) pass catalog validation, where before every `DEPLOY` with such a value failed with `502`.
