## Highlights

- **A command kernel compiled once per aggregate, and atomic.** Each aggregate type is compiled at startup into a model with stateless invokers, so a command no longer rebuilds its function resolver, accessors and sourcing table (13–16 % less allocation per command, 40 % less to recover a 10-event aggregate, #3951). Decide, apply and append are one unit: a command whose sourcing function throws, or whose append fails, stores and publishes nothing and leaves no half-applied instance behind; `@OnError` sees the committed state ([pipeline](https://wow.ahoo.me/guide/command/internals/pipeline#decide-apply-then-append)).
- **One command pipeline, one extension point.** The command filter chain is replaced by a fixed pipeline and `CommandInstrumentation`; the gateway is an admission facade (validate → request-ID check → wait registration); the processing node checks the request ID before the handler runs; a retried saga create no longer creates a second aggregate when the target uses a time-based CosId or Snowflake generator ([migration](https://wow.ahoo.me/guide/migration#command-filters-replaced-by-a-fixed-pipeline)).
- **One transport SPI.** Kafka, Redis Streams and an in-memory broker are `Transport`s under one generic `TransportMessageBus`, with one receive failure policy (Redis now retries a failed receive like Kafka instead of stopping the runtime) and a `FailureRecorder` that the compensation module implements. Local-first sends complete on local hand-off and send the distributed copy asynchronously, in order per aggregate (`sendAndWait(SENT)` through local-first: +224 % with 1 thread, #3976) ([transport](https://wow.ahoo.me/guide/command/internals/transport#transport-spi)).
- **One dispatch executor per runtime.** Every dispatcher runs on one shared `KeyedExecutor`: `wow.dispatch.workers` threads (the CPU cores by default) instead of a thread pool per aggregate type and dispatcher kind, one mailbox per aggregate ID, a bounded in-flight window, and one receiver (Kafka consumer) per bounded context instead of per aggregate type, in the same consumer groups. A slow or retrying aggregate delays only itself; with 128 aggregates waiting on I/O, cold commands run 14–16× faster, and no benchmark row of the 9.3.0 gate is slower ([keyed executor](https://wow.ahoo.me/guide/advanced/keyed-executor), #3969, #3975).
- **Aggregate-level policies and one identity rule.** `@Spaced` and `@AggregateOwner(OwnerPolicy.…)` declare an aggregate's space and owner policy; one resolver decides tenant, owner, space and aggregate ID for REST, the gateway and sagas, and a request that contradicts the tenant or owner its route fixes is rejected ([request identity](https://wow.ahoo.me/guide/open-api#request-identity)).
- **Explicit API tiers.** Backend, transport and command-aggregate SPIs are marked `@WowSpi` (opt-in warning); wow-core's write interior and wow-query's admission internals are `internal` or `@InternalWowApi`. 9.3.0 removes the binary-only shims; application-facing APIs it replaces keep one `@Deprecated` cycle ([compatibility debt](https://github.com/Ahoo-Wang/Wow/blob/main/docs/compat-debt.md)).

> [!IMPORTANT]
> **Recompile everything against 9.3.0, and upgrade processing nodes before gateway-only services.** 9.3.0 keeps no JVM declarations for bytecode compiled against 9.2: a library built against 9.2 must be rebuilt. REST, storage, wire formats and Kafka topics and consumer groups are unchanged, and 9.2.x and 9.3.0 nodes can run side by side during a rolling upgrade; see [Compatibility boundary](#compatibility-boundary) and the [migration guide](https://wow.ahoo.me/guide/migration#upgrading-from-9-2-to-9-3-0).

## Breaking

**Policy.** 9.3.0 is a minor release that breaks the Kotlin API where the 9.3.0 refactor design justified it. It keeps **no binary-compatibility shims**: no `DeprecationLevel.HIDDEN` overloads, old constructors or non-bean copies of Starter methods are kept so that 9.2 bytecode links, so recompile every library built against 9.2. **Application-facing APIs** (annotations, DSLs and extension functions application code calls) that 9.3.0 replaces keep **one `@Deprecated` cycle**: they still compile, warn, and are removed in 10.0.0. Each is listed in [docs/compat-debt.md](https://github.com/Ahoo-Wang/Wow/blob/main/docs/compat-debt.md). Extension-point SPI that only backend, transport or framework implementers touch changes without a deprecation cycle. REST, storage and wire formats are frozen within v9 and unchanged (see [Compatibility boundary](#compatibility-boundary)).

Step-by-step replacements for every item below are in the [migration guide](https://wow.ahoo.me/guide/migration#upgrading-from-9-2-to-9-3-0).

### Kotlin / JVM

#### Every module

- **Binary-compatibility shims removed** (#3952). Gone: the 9.2 JVM constructors of `MessageSubscription` (without `runtimeOwned`) and of the Redis buses (without `retentionOptions`); the 9.1 constructors of `BindingError`, `AggregationGroup.Terms` and `AggregationGroup.Histogram`; the non-bean copies of `WebFluxAutoConfiguration.commandMessageExtractor`, `queryRequestScope`, `commandRouterFunction`, `pointReadAdmission`, of `CoSecAutoConfiguration.coSecCommandBuilderExtractor` / `coSecQueryRequestScope` and the three-argument `OpenAPIAutoConfiguration.routerSpecs`. **Affects:** bytecode compiled against 9.2 or 9.1 that is not recompiled. **Migrate:** recompile; source that used the defaults is unchanged.
- **Deprecated for one cycle, removed in 10.0.0** (#3935, #3942, #3980): `@AggregateRoute(spaced, owner)` and `AggregateRoute.Owner` → `@Spaced` and `@AggregateOwner(OwnerPolicy.…)`; `AggregateRouteMetadata.owner` (and its `AggregateRoute.Owner` primary constructor) → `ownerPolicy` and the `OwnerPolicy` constructor; the eight `ServerRequest` identity readers (`getTenantId`, `getTenantIdOrDefault`, `getOwnerId`, `getSpaceId`, `getAggregateId`) → `ServerRequest.identity(aggregateMetadata)`, which returns a `RequestIdentity`; calling `MessageBus.receive(subscription)` → `receiver(subscription).openedMessages()`; the static `RecoverableExceptionRegistrar.register` / `unregister` / `getRecoverableType` → `RecoverableExceptionRegistry.DEFAULT` (Java callers now go through `RecoverableExceptionRegistrar.Companion`; 9.2's `INSTANCE` is gone); `Throwable.toResponseEntity()` / `ErrorInfo.toServerResponse()` → `WebFluxErrorStrategy` (#3938).

#### `wow-api`

- **`@WowSpi`** (#3937): a new opt-in marker (warning level) for SPI that backend and transport implementers use. Using a `@WowSpi` type without `@OptIn(WowSpi::class)` (or `-opt-in=me.ahoo.wow.api.annotation.WowSpi`) is a compiler warning.
- **Conflicting aggregate declarations fail** (#3935): `@Spaced` / `@AggregateOwner` and `@AggregateRoute(spaced, owner)` with different values on one class, or `@StaticTenantId` and a different `tenantId` from `@BoundedContext.Aggregate` or a hand-written `wow-metadata.json`, now fail at startup (`IllegalStateException`) and at compile time (KSP), naming both values. Two `wow-metadata.json` resources on the classpath that disagree on an aggregate's tenant or type, or a context's alias, now fail startup naming both URLs; 9.2 logged an error and dropped the second resource depending on classpath order. **Migrate:** make the declarations agree.

#### `wow-core`

- **Write interior fenced** (#3948). 21 types and 16 functions or constants of the command-processing interior became `internal` (`SimpleCommandAggregate`, `CommandState`, `RetryableAggregateProcessor`, `CommandFunction` and its implementations, `AfterCommandFunction`, `MessageFunctionAccessor` and its implementations, `FunctionMetadataParser`, `LogResumeErrorMessageHandler`, the event-dispatcher bases `AbstractEventDispatcher` … `StateEventDispatcher`, the exchange attribute keys, `commandSentSignal`, the `toResult` factories); 14 types and 9 members became `@InternalWowApi` (`AggregateProcessorFactory`, `RetryableAggregateProcessorFactory`, `SimpleStateAggregate`, `FunctionAccessorMetadata`, `MessageFunctionRegistrar`, `CompositeEventDispatcher`, `EventHandler`, the `ServerCommandExchange` attribute accessors, …); `CommandAggregate`, `AggregateProcessor`, `CommandAggregateFactory` and `SimpleCommandAggregateFactory` are `@WowSpi`. `CommandAggregate.commandState` is gone. **Affects:** code that used the command-processing internals. **Migrate:** `@OnCommand` / `@AfterCommand` functions, `MessageFunction`, `StateAggregateFactory`; a command function that needs the current state takes a `ReadOnlyStateAggregate<S>` parameter instead of a `CommandAggregate`.
- **One receive entry on `MessageBus`** (#3941, #3952, #3980). `receiver(subscription)` is the one entry a bus implements and is now abstract; `runtimeReceiver` is removed, and the runtime asks for `receiver(subscription.copy(runtimeOwned = true))` (new `MessageSubscription.runtimeOwned`). **Affects:** custom buses that overrode only `receive`, or gave runtime receivers special behaviour in `runtimeReceiver`, and decorators. **Migrate:** implement `receiver` and branch on `subscription.runtimeOwned`; decorators forward `receiver`.
- **Aggregates compiled once** (#3951). `StateAggregateMetadata.toMessageFunctionRegistry(stateRoot)` is removed. **Migrate:** `StateAggregate.onSourcing(eventStream)` through `StateAggregateFactory`.
- **One result adapter** (#3954). `AbstractMonoFunctionAccessor`, `SimpleMonoFunctionAccessor`, `SyncMonoFunctionAccessor`, `FluxMonoFunctionAccessor`, `PublisherMonoFunctionAccessor`, `FlowMonoFunctionAccessor`, `SuspendMonoFunctionAccessor` and `BlockingMonoFunctionAccessor` are removed; `toBlockable` moved from the `BlockingMonoFunctionAccessorKt` facade to `BlockableKt` (Kotlin source unchanged). **Migrate:** `KFunction.toMonoFunctionAccessor()` / `MonoMethodAccessorFactory.create(function)`.
- **The command filter chain is removed** (#3955, #3963). `CommandFilter`, `AggregateProcessorFilter`, `SendDomainEventStreamFilter`, `SendStateEventFilter`, `ProcessedNotifierFilter` and `DefaultCommandHandler(chain, errorHandler)` are gone; `CommandHandler.handle(exchange)` became `handle(exchange, aggregateMetadata)`; `ServerCommandExchange.set/getAggregateMetadata` and `set/getAggregateProcessor` are gone. An `ExchangeFilter<ServerCommandExchange<*>>` bean, or an `ExchangeFilter` with `@FilterType(CommandDispatcher::class)`, now **fails startup** naming the bean. **Migrate:** a `CommandInstrumentation` bean for tracing, metrics and logging; `CommandValidator` or Jakarta validation for checks; an event processor, saga or projection to react to committed events.
- **Gateway and request-ID check** (#3963). `DefaultCommandGateway.close()` no longer closes the `CommandBus` it was given, and after `close()` `sendAndWait*` fails with `RejectedExecutionException`; `NoopRequestIdExistenceChecker` answers "absent" instead of "exists"; `sendAndWait` / `sendAndWaitStream` write the wait keys into a copy of the caller's message instead of the caller's message.
- **Header propagation and recoverable exceptions are beans** (#3964). `MessagePropagatorProvider` is removed → an injected `MessagePropagators` (or `MessagePropagators.DEFAULT`) and `me.ahoo.wow.messaging.propagation.propagate`; `toCommandMessage(…)`, `CommandBuilder.toCommandMessage()`, `toDomainEventStream(…)`, `SimpleCommandMessageFactory`, `SimpleCommandAggregateFactory`, `StatelessSagaFunction` and `StatelessSagaFunctionRegistrar` take a trailing `MessagePropagators` (defaulted); `RecoverableExceptionRegistrar` is now the interface providers register into; `CommandRequestHeaderPropagator` no longer reads a system property outside Spring; a chain wait plan whose `waitCommandId` is not the command's ID fails with `IllegalArgumentException`.
- **Local-first hand-off** (#3976). `LocalMessageBus.sendIfSubscribed(message): Mono<Boolean>` → `handOff(message): Mono<LocalHandoff>`; `LocalFirstMessageBus` has an abstract `distributedCopies: LocalFirstDistributedCopies`, which the three built-in local-first buses take as a constructor parameter. **Affects:** custom `LocalMessageBus` or `LocalFirstMessageBus` implementations and their decorators.
- **Transport SPI** (#3966, #3967, #3981). `MainDispatcher.receiveMessage` (and its overrides) is removed → `createMessageReceiver(subscription)`; the unused `me.ahoo.wow.messaging.handler.retryStrategy(...)` is removed → Reactor `Retry.backoff`; `DefaultDomainEventHandler`, `DefaultProjectionHandler`, `DefaultStatelessSagaHandler` and `DefaultSnapshotHandler` extend `FailureRecordingHandler` and take an optional `failureRecorder`. The new transport SPI shipped without `TransportMessage.headers` and `TransportRecord.nack()`, which no built-in transport implemented (#3981).
- **One keyed executor replaces the dispatch schedulers** (#3969). Removed: `AggregateSchedulerSupplier`, `DefaultAggregateSchedulerSupplier`, `MessageParallelism` (`DEFAULT_PARALLELISM`, `toGroupKey`), `ParallelismCapable`, the `wow.parallelism` system property, and the `parallelism`, `scheduler` and `schedulerSupplier` constructor parameters of `CommandDispatcher`, `AggregateCommandDispatcher`, `DomainEventDispatcher`, `ProjectionDispatcher`, `StatelessSagaDispatcher`, `SnapshotDispatcher`, `AggregateSnapshotDispatcher` and `CompositeEventDispatcher`; `AggregateDispatcher`'s abstract `parallelism`, `scheduler` and `T.toGroupKey()` are replaced by `T.mailboxKey(): Any`. `WowRuntime` and `RuntimeContext` gain a defaulted `keyedExecutor`. **Migrate:** drop the arguments and any `AggregateSchedulerSupplier` bean; size the workers with `wow.dispatch.workers` (new, with `wow.dispatch.max-in-flight` and `wow.dispatch.throughput`) or `WowRuntime(keyedExecutor = KeyedExecutor(workers = …))`.
- **One receiver per bounded context** (#3975). `MainDispatcher.newAggregateDispatcher(namedAggregate: NamedAggregate, …)` → `newAggregateDispatcher(namedAggregates: Set<NamedAggregate>, …)`, called once per bounded context; `AggregateDispatcher` is no longer a `NamedAggregateDecorator` and exposes `namedAggregates: Set<NamedAggregate>` (and optionally `metricProcessorName`); `AggregateCommandDispatcher<C, S>(name, aggregateMetadata, …)` → `AggregateCommandDispatcher(aggregateMetadata: List<AggregateMetadata<*, *>>, name, …)`, no longer generic; `AggregateSnapshotDispatcher.namedAggregate` → `namedAggregates`. **Affects:** custom dispatchers. Default child dispatcher names become `<context>-…Dispatcher`; metric tags are unchanged.
- **Durable intake suspension** (#3993). `MessageReceiver` takes a trailing `durableIntakeSuspension: () -> Unit = {}` (recompile; Kotlin source unchanged); new `RuntimeComponent.suspendDurableIntake()`, `MessageReceiver.suspendDurableIntake()` and `TransportReceiver.durable` (default `false`). **Affects:** custom transports, whose receivers keep the 9.2 shutdown behaviour until they declare `durable = true`.
- **Unused JSON record classes removed** (#3970): `FlatEventStreamRecord`, `DelegatingMessageRecord`, `DelegatingNamedBoundedContextMessageRecord`, `toMessageRecord()`, `toBoundedContextMessageRecord()`. **Migrate:** implement the record interface directly.
- **`@Order` is a topological sort** (#3954, #3965). Constraint cycles fail startup with an `IllegalStateException` naming the cycle, and an ordered list can come out differently from 9.2 even where 9.2's order met every constraint (`X @Order(100, before = [Y])`, `Y @Order(0)`, `Z @Order(50)`: 9.2 `[X, Y, Z]`, 9.3 `[Z, X, Y]`).
- **Kernel outcomes of a failed command** (#3982). See [Behaviour changes](#behaviour-changes): `@OnError` runs on the committed state and the reported `aggregateVersion` is the committed one.

None. REST, storage and wire behaviour of existing aggregates is unchanged; no exception to the v9 freeze is taken. ## Behaviour changes

### REST-visible

- **Contradictory identity is rejected** (V3, #3942). A command body `@TenantId` / `@OwnerId`, or a `Command-Tenant-Id` / `Command-Owner-Id` header, that differs from the tenant or owner the route fixes (static tenant, `{tenantId}`, `{ownerId}`, or `{id}` of an aggregate owned by its ID) answers `400 IllegalArgument`; before, the body silently won and the header was ignored. A tenant header against a static tenant is still ignored. On an aggregate owned by its ID, a command on a route with `{id}` but no `{ownerId}` takes the aggregate and its owner from the path. A blank `{id}` on the event-load, compensate, regenerate and tracing routes answers 400 like every other route, and a blank `CoSec-Space-Id` / `CoSec-Request-Id` counts as absent. A blank body `@OwnerId` counts as no value only on an aggregate owned by its ID, whose owner comes from `{id}` (the owner is then the aggregate ID, as in 9.2); against `{ownerId}`, and a blank `@TenantId` against the static tenant or `{tenantId}`, it is a contradiction (#3981). **Who notices:** clients or gateways that send one global `Command-Owner-Id` or `Command-Tenant-Id` on every request. **Mixed cluster:** a 9.2 node accepts such a request, a 9.3 node rejects it.
- **SSE and batch errors of unexpected exceptions** (#3938). An SSE error event or batch result for an exception the error strategy does not classify is `InternalServerError` with "Unexpected server error" instead of `BadRequest` with the exception's own message, as on JSON routes; classified errors keep their code and message. A custom `WebFluxErrorStrategy` now reaches SSE and batch errors through `toErrorInfo`. **Mixed cluster:** the same failure is `BadRequest` from a 9.2 node and `InternalServerError` from a 9.3 node.
- **A failed command reports the committed version** (#3982, §8 Q20). When the append fails, `CommandResult.aggregateVersion` and the wait signal report the committed version N; 9.2 reported the unpersisted N+1. After a version conflict, the reloaded state that `@OnError` sees can be newer than N (N+k, written by the concurrent command), while the result still reports N. **Mixed cluster:** the processing node's version decides which one a client sees.
- **A resent create is `DuplicateRequestId`** (#3965, pinned by #3982, §8 Q16; see [Fixes](#fixes)). **Mixed cluster:** until every node runs 9.3, either code may come back; HTTP 400 is unchanged.
- **A gateway-only service lets a request-ID Bloom hit through** (#3963). On a service without an `EventStore`, a resent command now succeeds at the `SENT` stage and is rejected by the processing node (`DuplicateRequestId`) without running the handler; wait for `PROCESSED` to see it. A resent `@VoidCommand` is no longer rejected there (treat void commands as at-least-once).
- **Local-first `SENT`** (#3976). A handed-off local-first command reaches `SENT` once it entered the local sink, not after the local dispatcher admitted it, and a failed distributed copy no longer fails it (it is logged and counted). A refused send (no routable receiver, a closed route, a hand-off error) still waits for its distributed copy and fails with it, as in 9.2.
- **Chain-wait SSE streams** (#3964). `sendAndWaitStream` with a chain target no longer carries the tail signals of other sagas that react to the same event.

### Command processing

- `@OnError` runs once on the committed state, reloaded when the failed attempt applied events that were not stored (a create gets a new aggregate from the factory); if that reload fails, `@OnError` is skipped, an ERROR is logged and the original error is returned with the load error suppressed (#3982, §8 Q15). After a version conflict the reloaded state can be newer than the N the result reports (§8 Q20). Before, it saw the state with the unstored events applied.
- Decide, apply and append are one atomic unit (#3982, §8 Q14). 9.2.3 already applied the events before appending them; what is new is the failure path: when the apply or the append fails, the half-applied instance is discarded and never reused, no `StateEvent` is sent, and the version stays N. `VersionAware.version` is set after every sourcing function of the stream ran (#3954).
- A command whose handler is declared with a superclass or interface parameter is handled by the nearest one instead of failing as undefined; duplicate handlers and unresolvable non-nullable injected parameters log a WARN (#3951).
- An exception thrown by a function returning `Flow` before it returns the flow arrives unwrapped instead of as `InvocationTargetException`, for command, event, saga and projection functions (#3954).
- The processing node checks the request ID before the handler runs, against its own Bloom filter and `EventStore`; `wow.command.idempotency.enabled=false` turns off both checks (#3963). Upgrade processing nodes before gateway-only services.
- Saga commands get IDs derived from the event (#3965, #3982): a command body or `CommandBuilder` that names no aggregate gets an aggregate ID derived from the event, the saga function, its index and the target type, in the target generator's format (time-based CosId and Snowflake generators; segment and custom generators keep random IDs); a returned `CommandMessage` without its own request ID gets `<event ID>-<index>-<producer hash>` (§8 Q17). Body and builder request IDs stay `<event ID>-<index>`, as in 9.2. A retried saga create is rejected as `DuplicateRequestId` and skipped, so it no longer creates a second aggregate.
- A chain wait's tail reaches only the commands of the saga function the chain waits for (#3964).
- `wow.messaging.propagation.request` is read from the Spring environment (#3964).

### Messaging and runtime

- **Redis Streams retries a failed receive** like Kafka (3 consecutive retries from 10 s, `wow.redis.message-bus.receiver.retry-*`) instead of stopping the runtime on the first error; with Redis down at startup, readiness fails after about 70 s instead of at once (#3967).
- Kafka `RetriableException`s and Redis connection failures and timeouts are `RECOVERABLE`, so `RetryableFilter` and the append resolution retry them in-process; keep non-idempotent writes in projections and sagas idempotent (#3967).
- A failure whose in-process retries were exhausted is recorded as its cause: its `ExecutionFailed` record carries the cause's error code, message and `recoverable`, so a cause declared unrecoverable is no longer compensated automatically. The compensation record is written after the wait notifier signalled (#3967).
- New `wow.event.ack-on-unrecorded-failure` (default `true`, unchanged): `false` leaves a failure no recorder recorded unacknowledged for redelivery. New counter `wow.processing.outcomes` (#3967).
- **Local-first** (#3976): a send completes on local hand-off and the distributed copy is sent asynchronously, in send order per aggregate, with the 9.2 `local_first` marker meaning. A sender cancelled before the local hand-off result still has its copy sent exactly once, carrying the true local decision: no duplicate, no loss (§8 Q18). A hand-off result that does not arrive within the copies' `handOffTimeout` (30 s) counts as a refusal and the copy goes out unmarked, so another member may process the message a second time. A refused send (no route, a closed route, a hand-off error) waits for its copy and fails with it; local sinks for domain and state events are unbounded, with the backlog gauge `wow.local_first.backlog` and a warning at `…bus.local-first.backlog-high-water-mark` (default 10000); queued copies are sent within `wow.shutdown-timeout` and cancelled after it. There is no ordering guarantee across topics or buses (§8 Q19), and a handed-off message not yet processed is lost if the process crashes; disable local-first where a message must survive a crash.
- Kafka-received messages are read-only; Redis rejects an entry whose message belongs to another stream (`RedisRecordDecodeFailureReason.TOPIC_MISMATCH`) and leaves any undecodable entry pending (#3966).
- **Redis consumers**: a starting receiver deletes consumers of its group that have nothing pending and have been idle for `wow.redis.message-bus.retention.consumer-idle-timeout` (default `30m`; `reap-idle-consumers: false` turns it off). Stream trimming (`max-length` or `max-age`, `MAXLEN ~` / `MINID ~`) is available and off by default; it needs Redis 7.0 or later (#3946).
- **Shutdown** (#3945, #3981): Mongo and Elasticsearch batch writers and Kafka senders join the runtime (`RuntimeResources`, first component) and flush after the dispatchers within one `wow.shutdown-timeout`, instead of up to 30 s each after it; the Kafka producer close is bounded by `wow.kafka.close-timeout` (default: `wow.shutdown-timeout`). Lifecycle threads come from one bounded pool plus one deadline timer.
- **Shutdown under sustained traffic** (#3993): a graceful stop first suspends durable intake. Kafka and Redis Streams receivers stop requesting records (Reactor Kafka pauses the partitions and keeps committing acknowledged offsets; Redis stops reading), the records already pulled and the in-process work derived from them drain, and what was not pulled stays uncommitted / unread or pending for the group. Before, traffic arriving more often than `wow.shutdown-quiet-period` kept the runtime from becoming idle until `wow.shutdown-timeout` force-stopped it. In-process sends are admitted until global admission closes, as in 9.2.
- `@Order` constraint chains that 9.2's single pass got wrong are honoured (#3954).
- **Dispatch** (#3969): handlers run on `wow-dispatch-N` threads (at most `wow.dispatch.workers`, default the CPU cores) instead of `<Dispatcher>-<aggregate>-N`, and `suspend` / `Flow` message functions resume on them instead of `Dispatchers.Default`. Per-aggregate order is unchanged. A waiting handler (I/O, a version-conflict retry backoff) delays only its own aggregate, not every aggregate hashed to its group. Each receiver holds at most `wow.dispatch.max-in-flight` (256) unfinished messages, shared by its aggregate IDs: one aggregate with about 241 unfinished messages stops the receiver and pauses its Kafka topics. A force stop discards the messages still queued in mailboxes before it returns, as disposing the 9.2 schedulers did, and leaves them unacknowledged for redelivery. **Performance** (§8 Q9 gate, main before and after): in CI no row is slower — command send 7 faster and 5 within noise ([run 37557218922](https://github.com/Ahoo-Wang/Wow/actions/runs/37557218922)), aggregate handling within noise ([run 37550851420](https://github.com/Ahoo-Wang/Wow/actions/runs/37550851420)); locally the sustainable command-send rate is up to 66 % higher and cold commands beside 128 slow aggregates 14–16× faster. Tables in #3969.
- **Kafka consumers per bounded context** (#3975): each dispatcher has one consumer per bounded context, subscribed to all of its aggregate topics, instead of one per aggregate topic; group IDs and topics are unchanged, and consumers and rebalance participants per group drop from aggregate types to bounded contexts. The in-flight window and `max-deferred-commits` are shared by the context's topics: a backlog on one aggregate pauses all of the context's topics for that dispatcher, and a fatal handler error fails the dispatcher's whole context receiver instead of one aggregate type's.

### Edge, query and tooling

- A custom `RequestExceptionHandler` reports SSE errors through `handleInBody`; one that implements only `handle` no longer logs SSE error events or batch failures (#3938).
- A schema refresh keeps the published schema when nothing changed, and the 9.1 declaration location is scanned once, at the first load (#3944).
- The route catalog generates no schemas; the OpenAPI document's schemas are generated at startup only when the document is served (`wow.openapi.enabled` and Springdoc present) (#3961).
- `wow.bi.script.omit-sensitive-fields` (default `false`): on, BI expansion columns leave out every `@Sensitive` state property and every raw JSON column that contains one; generated scripts are unchanged by default (#3960).
- View store: an HTTP event-stream query reached outside the router answers `ViewScopeRequired` / `ViewAppRequired` before `ViewEventStreamClosed` (#3947).

## Compatibility boundary

**Unchanged:** REST routes, request and response headers, JSON bodies, SSE frames, error codes and HTTP statuses, apart from the approved items under [REST-visible](#rest-visible); the persisted event, snapshot and state formats, indexes and unique keys of every store; command, event-stream and state-event JSON, message keys and message header keys (including `command_wait_*` and `local_first`), wait-signal JSON; Kafka topic names and consumer group IDs, Redis stream keys and consumer groups. The wire-format golden samples are unchanged since 9.2.3, the OpenAPI and route-contract snapshots are byte-identical, and the compensation commands are byte-identical to 9.2. The KSP processor writes the non-default `spaced` / `owner` of an aggregate into `wow-metadata.json`; those keys are informational and 9.2 ignores them.

**Mixed 9.2/9.3 cluster.** The mixed-version gate (`MixedVersionClusterTest`, CI image `ahoowang/wow-example-server:9.2.4`) runs the released 9.2.4 server and the 9.3 build on one MongoDB and one Kafka, in the same consumer groups, and proves in both directions: a command sent by one version is processed by the other and its `PROCESSED` wait returns; a state event appended by one is snapshotted by the other; a saga on one handles the events the other appends; with local-first on, each version filters the other's locally handled copies; and a rolling restart, first of the 9.3 member and then of the 9.2.4 one, while commands and saga-driven orders flow, loses and duplicates no command although 9.2 consumes per aggregate topic and 9.3 per bounded context in the same groups (#3975). While both versions run, a request can get a different answer depending on the node: a contradictory identity is accepted by 9.2 and rejected by 9.3; an unexpected SSE or batch error is `BadRequest` from 9.2 and `InternalServerError` from 9.3; a resent create may be `DuplicateAggregateId` or `DuplicateRequestId`; a failed command reports N+1 from a 9.2 processing node and N from a 9.3 one; a saga create retried across a 9.2 and a 9.3 node can still create two aggregates, as every retry did in 9.2.

**Upgrade order.**

1. Upgrade to 9.2.4 first if you run an older 9.2.x; the gate runs against 9.2.4.
2. Recompile every application and library against 9.3.0 (no binary shims).
3. Roll out the processing nodes (services that host aggregates and an `EventStore`) before gateway-only services: a 9.3 gateway-only service lets a request-ID Bloom hit through, and a 9.2 processing node does not check request IDs before the handler, so a duplicate would run its handler again until the append rejects it.
4. Keep the mixed window short; the differences above end when every node runs 9.3.

## Fixes

- A command route with path or header variables, and the command facade, answer `400 IllegalArgument` when the body does not bind (a missing required field, a field of the wrong type), as routes without variables do; 9.2 answered `500` (#3986).
- A create resent with the request ID that created the aggregate answers `DuplicateRequestId` also outside the request-ID window; 9.2 answered `DuplicateAggregateId` there although the request is a replay. A create with another request ID is still `DuplicateAggregateId` (#3965 introduced it in the append outcome resolution; #3982 pinned it; §8 Q16).
- A retried saga create targets the aggregate the first attempt created instead of creating a second one, when the target aggregate uses a time-based CosId or Snowflake ID generator; segment and custom generators keep random IDs (#3965), and two sagas that return a `CommandMessage` for the same event no longer share a request ID (#3982).
- A gateway-only service no longer rejects a legitimate command on a request-ID Bloom-filter false positive (#3963).
- Wait handles emit their signals outside their lock, so a subscriber that uses the handle from another thread while handling a signal no longer blocks (#3963).
- A chain of `@Order(before/after)` constraints is honoured; 9.2 could violate it (`head after middle after tail` came out `[head, tail, middle]`) (#3954).
- A handler that sends a command reactively from its own completion no longer starves the other aggregates of its dispatch group until their commands time out (#3969).
- A Redis Streams receive error (a failover blip, a command timeout) no longer stops the runtime at once (#3967).
- `XINFO CONSUMERS` no longer grows with every deploy (#3946).
- Batch writers and Kafka senders stop within `wow.shutdown-timeout`; before, shutdown could take `shutdownTimeout + 30 s × writers` plus an unbounded Kafka flush (#3945, #3981).
- Point-read, regenerate and compensate handlers report identity errors through the route's `RequestExceptionHandler` instead of throwing out of the handler (#3981).
- An SSE stream or batch result no longer returns the message of an unexpected internal exception (#3938).
- `wow-apiclient`: typed snapshot query clients (`interface CartQueryClient : ReactiveSnapshotQueryApi<CartState>`) decode through a Spring HTTP interface proxy, and the deprecated `count(Condition)` sends the equivalent `FilterExpression` (#3971; also in 9.2.4).
