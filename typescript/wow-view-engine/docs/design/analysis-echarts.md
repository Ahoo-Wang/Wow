### 1.3 分析模型能说什么、不能说什么

| 能说                                                                                                                   | 证据                                                                                                        |
| ---------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| 维度：TERMS（可设空值组）、HISTOGRAM（固定宽度区间）、DATE_HISTOGRAM（年～秒、时区、首尾之间补齐）                     | `src/model/analysis.ts:69-81`                                                                               |
| 指标：记录数、总和／平均／最小／最大／标准差／方差、任一值、去重计数、百分位（近似）、派生（公式）；每个可带自己的条件 | `src/model/analysis.ts:98-128`                                                                              |
| 展开链、只保留、排序、前 N 条（缺省 100，上限缺省 1000，D42）、合计行（另发一次无分组查询）                            | `src/model/analysis.ts:193-204`，`src/analysis/defaults.ts:41`、`:63-76`，`src/analysis/compile.ts:143-164` |
| 截断由多要一行的探针判定                                                                                               | `src/analysis/compile.ts:111`                                                                               |

不能说的，按分析师会问的问题列：

- **跨行的计算**：累计、移动平均、趋势、较上一桶的变化、占全部的比例，模型里都没有。唯一的例外是指标卡——它在内核里拿最后一期与上一期比（`src/analysis/metricCard.ts:230-250`）。
- **与另一段时间比**（上一期整段、去年同期）：没有。
- **一张图画一组统计量**（箱线图的五个数）：模型能各自算出最小、三个百分位、最大，但图表规格没有把它们认作一组的槽。
- **轴**：`AxisSpec` 只有标题、最小、最大与格式，没有对数刻度；`ScatterSpec` 连轴规格都没有（[todo.md](todo.md) 的线索）。
- **参考**：`ReferenceLine` 只有常数，没有平均线、目标区间。
- **拆分超过八条**：循环取色（Q9 搁置）。
- **框选出的一段**：追问只收一行（`drillConditions`，`src/analysis/drill.ts:190`），不收一段桶。

### 1.4 Wow 聚合查询在服务端能算什么

TypeScript 与 Kotlin 两边是同一套：`typescript/wow-client/src/query/aggregation.ts:24-70`、`:170-258`，`wow-api/src/main/kotlin/me/ahoo/wow/api/query/AggregationQuery.kt:25-400`。

| 服务端能算                                                                                              | 服务端不能算（在客户端算，或要改服务端）                                                      |
| ------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| 三种分组至多 32 个；六种指标至多 64 个；逐行派生（只在同一行的指标之间算）；只保留；排序；limit ≤ 10000 | **窗口计算**：累计、移动平均、排名、较上一行——一条都没有，只能对拿回来的行在客户端算          |
| 百分位（近似）、最小、最大：箱线图的五个数一次查询就能拿到                                              | **首值、末值**：「任一值」不保证每次一样（D20），画不了 K 线的开盘与收盘                      |
| 另发一次查询：换一段时间范围、去掉拆分维度——引擎已有先例（合计行的 `compileAnalysisTotals`）            | **拆分的「其他」**：要一次按横轴、不按拆分的查询，再减去前七条；只对可加指标成立              |
| 固定宽度的数值区间（直方图）                                                                            | 自定义分箱、回归、地理编码——服务端都没有；地图只要维度值是区域编码 TERMS 就够，缺的是地图数据 |

**客户端计算的一条约束**：跨行计算只在**行是完整的**时成立。被「前 N 条」截断、被「只保留」筛过、或时间轴上有不确知的洞时，累计与移动平均会悄悄算错。内核已有同一个判据——补 0 只在确知没有记录时补（`absenceReader`）——新的计算照用它（Q53）。

### 2.4 性能

- **行数上限就是点数上限**：`maxAnalysisRows` 当时缺省 10000（`src/model/limits.ts:101`；D42 起缺省 1000，对齐 Wow 的 HTTP 守卫，宿主可以调回 10000）。D21 实测 SVG 下 1 万点散点 7ms、10 万点折线 19～91ms，所以**不换 canvas、不做 progressive**（那是 canvas 的分帧绘制，对 SVG 意义不大）。
- **折线与面积**：点数多于绘图区宽度时按 LTTB 采样，读屏表、提示框与表格仍是全部数值；柱不采样。
- **柱与散点**：多于一千点时开 large 模式（一条路径画完），同时不写值标签。
- **热力图**：格内数字已由 `heatmapLabelsFit` 按格子尺寸决定写不写，不另做。

## 4 裁定

用户 2026-09-24 全部按推荐拍板，结论与理由记在 [D33](decisions.md#d33-分析视图释放-echarts-能力的九条裁定2026-09-24)；下面保留提出时的推荐与理由。

- **Q51 缩放要不要随视图保存**：推荐**不保存**，每次打开看全范围。理由：缩放是「这次看哪一段」，和滚动位置一样是瞬时的；要长期只看一段，出路是框选后的「只看这段时间」，它写进范围、看得见、能撤。存下缩放会让保存的视图悄悄只画范围的一部分，而状态条说的是整个范围。
- **Q52 框选之后做什么**：推荐**弹出与点一组同一个追问菜单**，不直接改当前视图。理由：D20 的追问「都开在旁边、不改写这一个」；Metabase 框选即改问题，但本包的视图是保存过的观察方式，框一下就变脏违背 D20 的修订。仪表盘上多一项「设为〈时间筛选〉」，与点击筛选同一口径。
- **Q53 趋势、移动平均、累计在行不完整时**：推荐**置灰并说原因**（「结果只显示了前 N 组，累计不完整」），不画一条带警告的线。理由：画错的累计线比没有更糟，与「补 0 只在确知时补」同一条原则。
- **Q54 图型多到十二张以上时网格怎么排**：推荐**分两组**——「适合这个结果」在上，其余折进「其他图型」，都仍是磁贴、灰的仍写原因；**不**加定义层的图型声明，并改正 1.1 那处文档（已改）。理由：形态已经决定灰不灰，研发再声明一遍没有新信息；Metabase 的图型选择器也分这两组。
- **Q55 首发新增哪几种图**：推荐**瀑布图与矩形树图**，日历热力图可选。理由：瀑布是财务与运营常用的读法、零包体；矩形树图回答「类目多于八个的构成」，是 Q9 的一条正路；其余的理由见 2.1。
- **Q56 结清 Q9：超过八条系列或八片**：推荐——可加指标的拆分**画前七条加一条灰色「其他」**（多发一次不按拆分的查询再相减，与饼图的「其他」同色同义）；不可加指标的拆分超过八条时，显示页提示「超过 8 条，颜色会重复，建议改用热力图或表格」并照画；不可加指标的饼图**置灰**并写「占比只对可加的指标成立」。理由：份额与「其他」只对可加的数有意义；多一次查询的代价只在超出时付。
- **Q57 花纹（decal）何时画**：推荐**跟随系统的「提高对比度」**（prefers-contrast: more）自动开，宿主可钉开或钉关；工作台里不放开关、不进配置。理由：花纹是读者的可达性需要，与 D30 Q41「宿主的外观不进配置」同理；八色里亮色的青、黄、品红对卡片不到 3:1（[ui/analysis.md](ui/analysis.md)），花纹正是它们的补救。
- **Q58 导出图片的格式与内容**：推荐 **PNG 与 SVG 两种，图里带标题、图例与一行范围说明**，入口与分析的「导出数据…」在同一个菜单。理由：今天的图例是 HTML，不在库画的 SVG 里，只截库的画面会丢图例；导出时另出一份带标题与图例的 option 在无界面环境渲染，导出的图才能离开页面被读懂。
- **Q59 与上一期、去年同期整段对比**：推荐**首发后做**，首发前只在提示框写较上一桶的变化。理由：它要第二条查询、按 `periodOf` 平移范围、运行时多一条失败路径，面与合计行相当；提示框的环比不发查询，覆盖最常见的问题。

- **包体**：图表块今天 gzip 212.7KB（esbuild 压缩后 619KB，与 D21 的 214KB 一致，只在第一张图时加载）。逐个实测的增量：批 A 的 dataZoom（inside 与 slider）14.3、aria 1.1；批 B 的 markArea 1.4、markPoint 0.6；批 C 的 brush 8.6；批 D 的矩形树图 11.8、日历 3.8；导出若由库画图例与标题，legend 5.4、title 0.7。**首发全部合计约 +47KB，到 260KB 左右（+22%）**。首发后的桑基 9.8、地图含 geo 32；toolbox 15.1 不引。超出预期时可以按家族再切一块（矩形树图、日历只在选中时再注册），第一张图的成本不变。量法：以 `src/ui/charts/echarts.ts` 的注册表为入口，esbuild 打包压缩后取 gzip；每批 PR 写实测数。**批 A 实测**（与批 D 同一量法，`gzip -c`）：在批 D 之上加 dataZoom（inside 与 slider）与 aria，压缩后 668,957 → 702,880 B，gzip 229,248 → 239,941 B（+10.4KB，估的是 +15.4KB）；批 D 之前的 217,173 B 起算，两批合计 +22.8KB。**批 B 实测**（同一量法，esbuild 0.21.5 打包压缩、`gzip -c`）：在批 A 之上注册 markArea 与 markPoint，压缩后 702,880 → 710,455 B（+7,575 B），gzip 239,946 → 241,987 B（+2.0KB，估的是 1.4 + 0.6 = 2.0KB）；批 D 之前起算三批合计 +24.8KB。**批 C 实测**（同一量法，esbuild 0.21.5 打包压缩、`gzip -c`）：在批 B 之上注册 BrushComponent，压缩后 710,455 → 733,884 B（+23,429 B），gzip 241,988 → 250,152 B（+8.0KB，估的是 +8.6KB）；批 D 之前起算四批合计 +33.0KB。**批 E 实测**（同一量法，esbuild 0.21.5 打包压缩、`--external:react`、`gzip -c`）：图表块的注册表一个组件都没加，压缩后 734,114 B、gzip 250,294 B，**增量 0**。导出图片的头部（标题、条件、图例）用已注册的 graphic 组件画、十字准星随已注册的 tooltip 带来，所以方案估的 legend 5.4 与 title 0.7 没有花；实测若注册库的 legend 与 title 两个组件，压缩后 +20,325 B、gzip +6,053 B（约 +5.9KB，与估的 6.1KB 相符）。批 D 之前起算五批合计仍是 +33.0KB。
- **计时断言**：`typescript-storybook-gate` 是 main 的必过项，墙钟断言在慢 runner 上抖一次就挡住所有合并（批 B 的 PR 上「一万天重画」两次 567～627ms、第三次 393～403ms）。所以故事里只守**回归线**——比见过最慢的 runner 高约三倍（1500ms），拦得住数量级的变慢；真正的**预算**（500ms）写在批 A 判据与故事说明里，每次运行把实测数打进日志。批 B 的故事不含墙钟断言。
