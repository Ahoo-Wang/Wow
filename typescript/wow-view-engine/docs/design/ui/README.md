## 措辞与 MessagesProvider

- 措辞在 `ui/`：`model` 只带 `code` 与 `params`，`ui/messages.ts` 给出每个 code 的英文句子，`ViewSurface` 与四个工作台（`RecordWorkbench`、`AnalysisWorkbench`、`DashboardWorkbench`、`EmbeddedView`）的 `messages` 属性按 key 覆盖，这也是本地化的入口。每层 `MessagesProvider` 合并在上一层之上而不是默认值之上，应用在外层设一次，面里面仍然生效；
- 目录按前缀分文件放在 `ui/messages/`（`save`、`header`、`record`、`filter`、`config`、`scope`、`view`、`manage`、`analysis`、`dashboard`、`status`、`definition`），每个文件 `as const satisfies Record<string, string>`，`messages/en.ts` 把它们铺成英文目录——一份平铺的目录看不出哪些键还活着。`ui/messages.ts` 仍是所有组件 import 的那一个模块，它组合这些文件，并导出 `ViewMessages`、`defaultMessages`、三个格式化函数与前缀回退；
- **key 是类型**：`MessageKey = keyof typeof en`，`MessageFormatters.label(key, params?, fallback?)` 只收它，所以删掉一个键或拼错一个键是编译错误而不是屏幕上的一行 code。由运行时值拼出的 key 走收紧后的源类型（`ViewKind`、`ViewAudience`、`RecordLayout`、`DateShape` 都是闭合联合，模板字面量因此可判）。界面上能选的闭合枚举一律整套命名，不留派生拼写：`label.operator.*` 覆盖 `FilterOperator` 全部成员（`operatorKey()` 只是把这个家族拼一次，不再有断言），`label.chart.type.*`、`label.group.type.*`、`label.metric.function.*` 同理——目录只命名一半的集合根本没法翻译，`messages={zhCN}` 时下拉里照样是 `eq`、`between`、`date histogram`。`label.relative.unit.*` 与 `label.relative.preset.*` 是同一条规则的后两套——相对日期控件以前把标识符本身摆在屏幕上（`hour`、`thisWeek`），于是换了目录它照旧是英文；单位沿用控件原本的拼写，时段沿用摘要条原本读出的那个带空格的写法。派生拼写只作为宿主能力数据给出未知成员时的兜底，`test/messages.test.tsx` 按枚举与这两套集合逐个核对，缺一个就失败。全包已无 `MessageKey` 断言；
- **屏幕上的名字用字段的标题，不用字段的 id**。`label.relative.unit.*` 那条规则对一行条件同样成立：`ConditionPill` 的四个无障碍名（`condition-of`、`operator-of`、`value-of`、`remove-of`）都拿 `field.label`（取不到才退回 `leaf.field`），所以「状态 条件／状态 操作符／状态 值」是一个词，而不是两个词加一个标识符。（见 test/filterPanel.test.tsx「names every control on a row after the field, not its id」）
- **vendored 组件写死的文案在调用处合缝**。`ui/components/**` 不手改，而 `spinner.tsx` 把 `aria-label="Loading"` 写死在里面，宿主换目录也换不掉它；所以目录里有 `label.status.loading`，三处渲染 `<Spinner>` 的地方（`RefreshControl`、`SaveActions`、`SaveAsDialog`）把它当 `aria-label` 传进去——`DashboardWorkbench` 只把 `busy` 交给 `RefreshControl`，自己不画 spinner。目录测试只证明键在两本目录里都有，调用处那一条断言才证明它真的传了。（见 test/refreshControl.test.tsx 与 test/saveActions.test.tsx「announces … in the host catalogue, not in English」）
- 宿主的覆盖仍是 `Readonly<Record<string, string>>`：宿主可以放自己的 key，本包从不读它不认识的 key。包里带第二份目录 `zhCN`（`ui/messages/zh-CN.ts`，类型是 `satisfies Record<MessageKey, string>`，少一键多一键都编译不过），与 `en` 一同从 `/ui` 导出；宿主整份交出去，或者铺开再覆盖几句：`messages={{ ...zhCN, 'label.x': '…' }}`。zh-CN 是没有任何组件 import 的叶子模块，只引组件的打包不会把它带进去。**Storybook 里的 view-engine 故事整册默认跑 zh-CN**（`stories/view-engine/fixtures.ts` 的 `HOST_LANGUAGE`，`messages={zhCN}` 加 `locale="zh-CN"`）——夹具数据本身是中文的（订单号、待出库），英文目录配中文数据是一屏两种语言；`RecordWorkbench` 的 `English`（「英文目录」）是唯一反过来的那一条，英文目录的回归就在它身上；
- 工作台自己的提示渲染在它所画的面之外，所以用 `useViewMessages(messages)` 读同一份合并结果。缺失的 key 沿点号回退到最长的已知前缀（`/react` 把命令与 store 结果拼成 `view.open.failed.not_found` 这类 code），再退回 key 本身，因此永远不会渲染空白。`test/messages.test.tsx` 扫描源码里所有 `issue(...)` 的 code，少一条就失败——否则 `record.summary.unsupported` 这样的键会直接出现在界面上；同一份测试断言 `Object.keys(zhCN)` 与 `Object.keys(en)` 相同，且英文句子里的每个 `{param}` 在中文里也在。（见 test/messages.test.tsx「the message catalogue」「the Chinese catalogue」「components write no copy of their own」）

## 两级 severity 与 StatusStrip

- 两级 severity 在界面上分开呈现，而且都是**单行状态条**（`StatusStrip`）而不是整块 Alert：结果区始终留着上一次成功的结果，一条阻塞不了什么的提示不该把它顶下屏幕。状态条有 warning／error／info 三种 tone，error 以 `role="alert"` 播报，其余以 `role="status"`；
- **一行高是布局的决定，不是不用组件的理由**（D16 裁定 7）。状态条就是 shadcn 的 `Alert`，穿它的**紧凑变体**：`ui/alerts.tsx` 的 `LineAlert` 用一层 cva 扩展把 registry 的块状网格改成一行会换行的 flex，把钉在右上角的 `AlertAction` 放回行尾，别的一概不动（vendored 文件不手改，D16 裁定 8）。句子是 `AlertTitle`，动作是 `AlertAction`，**没有 description**——一句话就是全部内容，标题底下没东西的标题是空段落的抬头（D1）。tone 一次决定三件事：颜色（`border-destructive`／`border-warning`／`border-border`）、图标（`TONE_ICON`：error 是圆圈、warning 是三角、info 是 i，两个 callout 各挑各的图标等于教给读者两套词汇）、以及怎么播报（error `role="alert"` 打断读屏，其余 `role="status"` 排队）。`frame` 只有两种：`box` 是自成一条的带边横幅，`bare` 不带边框与底色、走 13px（`TEXT_UI`）——对话框里一行接一行的那种，以及嵌在一排控件里的槽位；
- **每一处 callout 都走这一份配方**，没有第二份：工作台状态行（`StatusStrip` 及其 `WarningStrip`／`ErrorStrip`／`QueryStrip`）、写入结局的那一行（`OutcomeActions` 的两个 surface：视图是 `box`、管理器行是 `bare`）、导出窗口的超上限告知（`export-over-limit`）、条件编辑器的超预算告知（`filter-too-large`，tone 为 `info`——这棵树没有哪里是这一屏能改对的，Clear 才是出路）、以及 `RenderBoundary` 的 compact 面（`bare` + `inline-flex w-auto`，它站在一排控件中间，带边的横幅会把那一行撑断）。手写第二份配方，就是两条 callout 开始对「warning 长什么样」各执一词的那一刻；重试按钮不写 `text-current`：`outline` 不声明文字色，本来就跟着周围的 tone 走；
- 多于一条时只显示一句概述与「{count} more」（`label.status.more`），展开才逐条列出。**那颗按钮两态两句话**：折着时说还有几条（`label.status.more`），展开之后那几条已经在屏幕上，再说「还有 N 条」等于指着看得见的东西说没给你看，所以换成收起（`label.status.less`）——读屏靠 `aria-expanded` 不会被骗，这一条修的是眼睛看到的那句；`error` 阻塞：条件级的 error 就地标在 pill 上并禁用应用按钮，所以工作台的 error 条只报**条件以外**的那些，由编辑器控制器交出的 `filter.unmarked` 给定（判断在 `filter/marks.ts` 的 `unmarkedErrors`：code 以 `filter.` 开头、且路径在草稿树上确实解析到一条被渲染的条件——谓词内部的条件也算——才交给编辑器；畸形子节点被条件带跳过、分组本身也不带标记，这些没有 pill 的照样报在状态条里，否则它们会禁用 Apply 却无处可看）。`ErrorStrip` 自己不做这件事，它只画交给它的那些；标题 `label.view.needs-fixing`／`label.dashboard.needs-fixing`（`WorkbenchShell` 按 kind 选）；
- `EmbeddedView` 没有编辑器，没有任何一条被标在别处，因此全部报出，并以它取代结果（查询失败是例外：上一次成功的结果还在时，失败条与结果并排，取代结果的只有「什么都还没回来过」那一种——条里那句 `label.query.stale` 说的就是它身旁的东西）（warning 仍照常显示在旁，两级并存时两级都说）。`warning` 不阻塞，但"报出而不阻塞"要求它被看见：warning 条用主题的 `warning` token（`text-warning`／`border-warning`，与 `destructive` 并列，宿主用 `--fve-warning`／`--fve-dark-warning` 定制），只有一条时那句话本身就是标题，多条时标题是 `label.view.warnings-count`；
- **宿主的收窄被拒，说的是收窄而不是视图。** `EmbeddedView` 收到的 `scopeFilter` 若不被这份定义接受，屏幕上是一条 destructive 的 `Alert`——标题 `label.scope.refused`（「页面的作用域条件对这个视图不适用」），正文逐条列出被拒的理由——而**不是** `label.view.needs-fixing`：坏的是页面加上去的那一条，视图好好的，而宿主改不了别人存的视图，那句话对它无事可做。**第一次打开就被拒与后来被拒是同一回事**（[decisions.md](../decisions.md) D17-5）：被拒的收窄根本不生效，视图照作者存的样子跑，**没收窄的那份结果留在屏幕上**、告警压在它上面——页面要的范围没生效，不等于连宽的那份也不给，那正是这条 alert 存在的理由。两件事也可以同时发生：配置自己有 error 时照旧是状态条上的「这个视图要先修正才能运行」并取代结果，收窄被拒的那条 alert 仍在它上面各说各的。（见 test/embeddedView.test.tsx 与回归 story「ScopeRefused」「ScopeRefusedOnOpen」）
- 同 code 同 params 的 warning 只说一句（`dedupeIssues`）——Dashboard 对全局条件自己校验一次、映射到每个面板再校验一次，两片叶子也可能触发同一条规则，句子相同就不重复。查询失败也是一条 error 状态条：标题是失败本身那句话，右端一个 Retry，若上一次结果还在屏幕上，展开处附一句 `label.query.stale` 说明看到的是旧结果——失败从不清空结果，一次断线不该把人正在读的东西拿走。（见 test/statusStrip.test.tsx「StatusStrip」「dedupeIssues」「WarningStrip」「ErrorStrip」）

- **结果自己的 warning 与配置的 warning 并排。** 一条发现说的可能不是"这份配置有问题"，而是"屏幕上这些数字不等于它们看起来的意思"：汇总行退回本页口径（`runtime.summary.page-only`）、分析结果正好填满上限（`analysis.result.at-limit`）。这类发现随结果走（`ProjectedView.issues`，见 [../runtime.md#规则](../runtime.md#规则)），因为 `state.issues` 每次 `edit` 都重算，放进去就会在用户敲下一个键时消失，而它描述的数字还在屏幕上。`RecordWorkbench` 与 `AnalysisWorkbench` 把两者拼起来交给 `WorkbenchShell` 的 `warnings`，`EmbeddedView` 并进它自己那条——嵌入式视图没有编辑器、没有工具栏，那条状态条是页面上唯一能纠正行上那个词的东西。状态条对二者一视同仁，本来也该如此：都是视图必须说出口的 warning。

`FilterPanel` 的条件 pill 见 [FilterPanel 的布局](#filterpanel-的布局)。

## 值按字段显示

- 值按字段显示，规则在 `ui/display.ts` 的 `displayValue`（这个文件只管值怎么显示；已应用条的措辞在 `ui/summary.ts`）：Wow 把时间存为毫秒时间戳、把枚举存为代码，原样打印就是一列十三位数字和一列常量。声明了 `options` 的字段按选项标签显示（数组逐项，未知的码原样）；
- `cell ?? kind` 为 `datetime` 时经 `Intl.DateTimeFormat` 以 `dateStyle`／`timeStyle: 'medium'` 显示，为 `date` 时只显示日期；**`datetime` 上不带时刻的挂钟字符串（`2026-01-31`）只显示到日**——它指的是一整天（[kernels.md](../kernels.md#日期条件一个字符串算哪一刻)），旁边印一个 `00:00:00` 是在陈述一个没人选过的时刻，在筛选摘要上更是把查询真正跑到的那条边（当天最后一毫秒）说反；
- 不带偏移的字符串（`2026-09-18`、`2026-09-18T09:30:00`，Java 的 `LocalDate`／`LocalDateTime` 即此形式）是挂钟时间，筛选内核按引擎时钟读它，显示时原样保留而不换算时区，否则日历日在西半球会显示成前一天，`09:30` 会随浏览器与引擎的时差移动；
- 日历上不存在的挂钟时间（`2025-02-29`、`24:00`）不交给 `Date` 顺延到下个月或下一天，原样显示；
- DATE_HISTOGRAM 的键按单位显示为它起始的年、季度（`2026 Q3`）、月、日或时刻，年、季度、月按公历命名——Wow 按公历切桶，波斯历或伊斯兰历的月份会指向桶并不覆盖的时段——季度序号按阿拉伯数字计算，不受语言数字体系影响。数字仍按 `numberFormat`，布尔仍走措辞——分析表格与图表类目共用 `valueText`，货币分组在坐标轴上也不是裸数字——宿主给了 `renderCell`／`renderValue` 就由宿主决定。语言取 `ViewSurface` 的 `locale`，缺省为运行环境的语言；
- 工作台的同名属性透传，与 `messages` 是同一个选择，一个管文字，一个管值。时区取 `ViewSurface` 的 `timeZone`，工作台传入引擎的 `environment.timeZone`：相对日期"今天"按它解析，未声明时区的 DATE_HISTOGRAM 按它切桶，界面也按它显示，一行按什么时钟被筛选、被分组，就按什么时钟显示；
- 分组自己声明了时区的，键按那个时区读。表格、卡片与图表的类目（坐标轴、透视系列、饼图、散点、热力图、分组漏斗的阶段、metric 卡片的趋势）共用这一规则：`RecordColumnView` 带上 `options`，`RecordCardField` 带上 `kind`、`cell`、`options` 与 `numberFormat`，`AnalysisColumnView` 见 [kernels.md#compileanalysis-与-projectanalysis](../kernels.md#compileanalysis-与-projectanalysis)，`AnalysisChart` 经 `AnalysisView.schema` 拿到它们，不受表格选列影响。`numberFormat` 若 Intl 构造不出来（`zh_CN` 这类语言标签、缺币种的货币样式），先放弃语言、再放弃格式，数字按无格式显示，而不是让整张表在渲染中抛错。`spec.colors` 的键仍是内核标出的原值，不随显示文本变。（见 test/display.test.ts「displayValue」）
- **数字也按界面的语言**：`formatNumber(value, format, locale)` 先取定义里 `numberFormat.locale`，没有就取 `ViewSurface` 的 `locale`——zh-CN 的页面上一个 `CN¥2,450.00` 是给别人格式化的数字，表格、卡片、汇总行三处都传 `display.locale`。

## 控制器输出合同

- 控制器输出只读状态与动作函数，不输出 JSX、类名与供应商类型。受控值合同统一：是否受控由值属性决定，回调只通知，一次逻辑交互最多一次通知。命令一律以状态兑现而不是抛出：`useSaveCommands` 的每个动作都 resolve，结局落在 `state.error` 与 `state.write`，因此点击处理器不需要 try/catch。加载态由"手上的答案属于哪一次请求"推出而不是在 effect 里同步 setState，这也是 React Compiler 规则要求的形状。

- 排序与列的改动立即 `edit` 后 `apply`：表格渲染的列与行来自上一次成功结果，由内核按执行时的配置投影，因此不重跑就看不到改动；筛选则等提交。

## shadcn 与两个样式边界

- `ui/` 用 shadcn + Base UI 实现默认视觉。落地约定：注册表组件原样落在 `ui/components/`，由 `shadcn add --diff` 升级，因此不启用 Tailwind 前缀——前缀会让每个文件都要手改并从此无法跟随上游；
- 隔离由**两个样式边界**承担，全部 token 与 base 规则都挂在它们上面，宿主页面不受影响。Tailwind 的 preflight 与工具类按其写法都是全局的——preflight 重置整页的 `*`、`html`、标题、列表、链接与按钮，工具类是宿主可能撞名的裸 class（`.flex`、`.container`、`.collapse`），栅格库的 `.react-grid-*` 亦然——所以 `scripts/scope-utilities.mjs`（`postcss-prefix-selector`）在构建时给每条规则的主体加上 `:where(.fve-root, .fve-root *, .fve-tokens, .fve-tokens *)`：用 `:where` 是为了不改变特异性，用「边界或边界内」而不是后代前缀是因为弹层自己带着根类；
- **两个边界里只有一个是 surface**（D17-10）。`.fve-root` 是 `ViewSurface` 渲染的那块面：token、utility、base 规则，加上它自己涂的那张底（`--background`／`--foreground`）与 `data-theme` 钉住的模式。`.fve-tokens` 是宿主给**自己的 chrome** 戴的那个类：同一份 token、同一份 utility、同一份 preflight（所以戴上它的那片区域里，宿主自己的标题、列表与按钮也一起被 preflight 重置了，这是换取本包原语的代价），但**不涂底、不认 `data-theme`、不是面**——想要本包那张底就自己写 `bg-background text-foreground`，明暗只跟祖先上的 `.dark` 走。两个类不要戴在同一个元素上；`RecordTable` 这类视图组件仍然只在面里渲染，`fve-tokens` 是给 `Card`／`Button`／`Separator` 与排版 utility 用的；
- `html` 这种主体永远不在边界内的规则就此失效，宿主的排版因此保持。自定义属性也不例外——宿主会读它们：Tailwind 发到 `:root` 的主题变量（`--spacing`、`--radius-md`……）会与宿主自己的 Tailwind 互相覆盖，而 `--radius-md: calc(var(--radius) * .8)` 只有在 `--radius` 所在的边界上才有效——所以 `:root`／`:host` 一律改写为 `.fve-root, .fve-tokens`；
- 只有 `@property` 注册天然全局，它注册的也只是宿主 Tailwind 会同样注册的 `--tw-*` 名字。`verify-package` 对构建产物守住这条：两个边界之外没有任何规则，也不再有 `:root`；并且**每一处作用域都必须同时点到两个边界**——少了任何一个，就是整整一个边界悄悄不画了（宿主 chrome 没有 utility，或者面没有主题），构建当场失败。Storybook 走同一个插件、且只作用于主题文件，所以 story 看到的就是发布的规则。`cn` 取自同名包（shadcn 2026-09 起的约定），不再自写 `clsx + tailwind-merge`。主题以独立入口 `/styles.css` 交付，应用显式导入。

- **vendored 组件的颜色与边框只在包装里扩展，不在调用处**（D16-8）。两条规矩本来在这里打架——`ui/components/**` 是上游源码、不手改，而调用处的 `className` 只写版式、不写组件自己的颜色。第三条路是**在组件旁边放一层薄包装**，包装持有自己的 cva：vendored 一个字不动、照旧组合（包装先挑好注册表的 variant，再在它上面加一层），调用处传的是一个 variant 而不是一串颜色。今天有两个这样的文件：callout 的 `ui/alerts.tsx`（`LineAlert`，见上）与其余四处的 `ui/variants.tsx`——`ToneBadge`（徽章的四档语气，见 [record.md](record.md#徽章的颜色由定义说了算但只能从主题里挑)）、`DestructiveAction`（破坏性确认里执行的那一颗，见[保存与视图管理](#保存与视图管理)）、`PillInput` 与 `PillSelectTrigger`（条件 pill 里不画自己那圈边的输入框与选择器，`chrome="box"` 把它要回来——借出去的两处是分组块的与／或和分析编辑器的行数框）、`SidebarItem`（侧栏当前项的那根 `primary` 条与它的悬停档）。**版式不在此列**：宽度、间距、`justify-start` 本来就是 `className` 的事，留在用它的地方。从前 `ToneBadge` 那三行颜色写在 `record/cells.tsx` 的 `TONE_CLASS` 里、pill 那两行写成 `[&_[data-slot=input]]:border-transparent …` 从父元素往下够两层、当前项那串写在 `ViewList` 的 `Button` 上——最后一种是上游改个 slot 名就会无声失效的写法。
- 注册表组件是上游源码：覆盖率、Prettier、ESLint 与 Codacy 都排除 `ui/components` 与 `ui/lib`，它们保持与上游逐字一致，否则每次 `shadcn add --diff` 都会变成整文件冲突；本包测的、也负责的是其上的组合。
- **一列行只有一个配方**（[decisions.md#D16](../decisions.md#d16-站在-shadcnbase-ui-肩膀上审计后的八条裁定) 裁定三）：视图管理行、列设置行、排序条目、卡片正文、链接面板，从前是五份各写各的 flex——各自的 gap、各自的截断、各自的对齐——现在都是注册表的 `Item`：`ItemMedia` 领头（手柄、勾选框、序号），`ItemContent` 吃掉中间那段（`ItemTitle` 是这一行的主语，`ItemDescription` 是它的副题），`ItemActions` 收尾，折到下一行的那条（列设置的说明句、管理行的写入结局）是 `ItemFooter` 或一句 `basis-full`。包里那层薄包装是 `ui/RowItem.tsx`，只拿着两样：行自己的状态色（`data-dragging` 的底色、`data-broken` 的灰字——裁定八要的是「调用处不带颜色」，不是「不许有颜色」）与一个 `density` 变体（弹层与对话框里的行用 `dense`，注册表 `xs` 的内边距会把每一行撑高半行）。状态标记本身仍留在调用处：测试与浏览器故事是按 `data-slot` 与 `data-dragging` 认行的。**能拖的那三列（列设置、排序条目、视图管理行）连把手也只有一份**：`ui/DragHandle.tsx`——同一枚 `GripVerticalIcon`、同一组方向键（↑／↓ 各移一位，库拿着行时让路）、同一条拖动途中静音（`IconButton` 的 `silent`），调用处只给名字、禁用的理由（连同它指向的那句说明）、`icon-xs`／`icon-sm` 与移动回调；从前是逐字相同的三份，谁多认一个键、谁少一句名字都没有可比之处。落下那一步同理：**算不算一次放下**（没取消、两端都在、不是落回原处）是 `ui/dragDrop.ts` 的 `dropped()`，各处在它之上再问自己的那一句——位置是否属于本列表（`sort/drag.ts`）、两行是否同一受众（`manage/drag.ts`）、落点按整份列表数第几位（`ColumnSettings`）。（见 test/dragHandle.test.tsx）
- **一个控件加一句话就是一个 `Field`，不是一个 `<label>` 加一段 `<p>`**（shadcn 的 forms 规矩）：标签用 `FieldLabel`（指向控件，屏幕上的那个词就是它的无障碍名——再挂一个 `aria-label` 是给同一个控件起了第二个、读屏听到的偏偏是屏幕上没有的那个），成组的勾选框与单选用 `FieldSet` + `FieldLegend`（`aria-label` 命名的组只有读屏读得到，其余人看到两个选项而没有题面），说明用 `FieldDescription`，拒绝用 `FieldError`（它自带 `role="alert"`），**无效态两处都要写**——`data-invalid` 在 `Field` 上（管标签与说明的颜色），`aria-invalid` 在控件上（管控件自己，也是读屏唯一听得到的那一处）。一个词要同时命名四个控件时 `FieldLabel` 就不成立（`ColumnRow` 的列名），各控件自带 `aria-label`、共用一条 `FieldDescription`。

## 主题、弹层与明暗

- 主题的全部 token 与基础规则都挂在两个边界上，而弹层（Select 列表、菜单、Popover、Tooltip、Dialog、Combobox）经 Portal 渲染到 body、在根之外，因此本包自己的组件一律从 `ui/popups.tsx` 引入各 `*Content`——它给弹层加上 `fve-root` 类与所在 `ViewSurface` 的主题（钉住的值，或面从自己的 `color-scheme` 计算值里解析出的跟随结果，因此宿主的 `.dark` 不必在 `<html>` 上），并把层级 `z-index: var(--fve-popup-z-index, 50)` 以 style 写在 **positioner** 上（D11：positioner 被写上 `transform` 自成 stacking context，内容里的 `z-50` 出不去；而它不带 `fve-root`，registry 给它的 `isolate z-50` 在钉过作用域的样式表里谁也没匹配上）。为了够得着 positioner，这六个弹层都是照 registry 的结构**自己组装** Portal／positioner／popup，而不是包一层 vendored 组件；vendored 的 `ui/components/**` 原样不动、照旧用 `shadcn add --diff` 更新，抄来的那份由 `test/popups.test.tsx` 两边各渲染一次、逐字比对类名与内部结构守住——唯一一处有意不同的是破坏性对话框的遮罩与那圈边（`forceRender`、`ALERT_DIALOG_BACKDROP_DIM`、`ALERT_DIALOG_RAISED`，理由见[保存与视图管理](#保存与视图管理)），比对时按名归一化而不是放行，所以注册表把那圈 ring 换成别的 token 仍然算 drift；第二处是 **Popover 多出来的那两个滚动类，它们各自报上名来**（`PopupKind.adds`，见下面那一条），报过名的才放行、还要真是多出来的，其余一个字都不许差。层级则由 `RecordWorkbench.test.stories.tsx` 的 `PopupsOverRaisedHostLayer` 在真浏览器里对着宿主抬起的一层逐种弹层验。`architecture.test.ts` 按导入记录守住引入规则——整模块导入、`export *`、转导出、动态导入与 `.ts` 文件都算在内。明暗也只有一套判定：`dark:` 变体与 token 用同一组选择器——`.fve-root[data-theme='dark']`、`.dark .fve-root:not([data-theme='light'])` 及其后代，外加 `.dark .fve-tokens` 与它下面**那些不归某块面管的**后代（`:not(.fve-root, .fve-root *)`）——宿主用祖先上的 `.dark` class 让视图跟随，`ViewSurface` 的 `theme` 则用 `data-theme` 把一处钉住，`verify-package` 断言构建产物里这两处集合一致；
- **面不嵌套，这一条不打折**：每个工作台与 `EmbeddedView` 各渲染一个根，包内没有根套根，宿主也不该把一个根塞进另一个根。坏在哪儿说得出来：CSS 没有「最近祖先」选择器，内层根把 token 重新声明在自己身上所以 token 是它自己的，而 `dark:` 工具类认的仍是外层那个根——内层一旦钉成相反的模式，得到的就是**浅色 token 配深色 utility**，屏幕上谁也画不出来。两层都不钉、跟着同一份级联走时看上去是对的，但那只是碰巧没出事。`test/styleBoundary.test.tsx` 把这两屏的实际取值钉住：嵌套那一屏 `useSurfaceTheme()` 说 light、utility 却是 dark；`fve-tokens` 那一屏钉成 light 的面从 token 到 utility 一路都是 light。
- **宿主拿本包原语画自己的 chrome，戴 `fve-tokens`**（D17-10）。它读什么：祖先上的 `.dark`，跟 surface 读的是同一个——`.dark .fve-tokens` 给暗色 token，没有 `.dark` 就是亮色。它**不读**什么：自己身上的 `data-theme`（没有这一路，钉模式是 surface 的事）、自己身上的 `.dark`（和 surface 一样，`.dark` 要在祖先上，这是 Tailwind 生态的写法）。它**不做**什么：不涂底（`bg-background`／`text-foreground` 只挂在 `.fve-root` 上，宿主想要就自己写）、不发 `MessagesProvider`／`TooltipProvider`／语言与时区（那些是 `ViewSurface` 的 props）、不当弹层的根（portal 出去的弹层带的是 `fve-root`）。它**让出**什么：`.dark .fve-tokens` 下面凡是一块面或面里的东西，暗色 utility 一律交还给那块面自己判断，所以宿主页面是暗的、嵌进去的视图钉成亮的，这一屏是对的——这正是它比「套两层根」强的地方。`stories/view-engine/EmbeddedView.stories.tsx` 的假宿主页就是这么写的；
- **动效让给 `prefers-reduced-motion: reduce`，会说话的那两种不让**。屏幕上会动的东西没有一件写在调用处：弹层由 vendored 组件带着 `data-open:animate-in zoom-in-95 slide-in-from-top-2` 进场（实测 `animation-duration: 0.1s`，中途缩到 0.986、淡到 0.727），对话框带遮罩淡入，按钮／徽章／行普遍 `transition-all`。所以让步在主题里做一次——`styles.css` 的一条 `@media (prefers-reduced-motion: reduce)`，两个边界都点到，时长削到 `0.01ms !important`——而不是去改三百处 class，理由与两处 vendored 字号钉在同一个地方一字不差：`ui/components/**` 不手改，成打的调用处也不传 class。**削到察觉不到而不是削到零**：Base UI 的弹层靠自己退场动画结束的那一下卸载。**reduce 不等于 remove**：`[data-slot='spinner']` 说的是「还在写／还在查」，`[data-slot='skeleton']` 的脉动说的是「这些还不是数据」，停掉它们是把「进行中」画成「卡住了」，这两个 slot 因此排除在外。媒体查询在故事里开不动（Playwright 的 `reducedMotion` 只在测试进程里有），所以 `RecordWorkbench.test.stories.tsx` 的 `ReducedMotionIsHonoured` 量的是规则本身：在不在、两个边界点没点全、真实弹层匹不匹配、被排除的两个 slot 匹不匹配，以及它此刻要削的是多长一段；
- 每个 token 读 `--fve-<token>`（暗色块读 `--fve-dark-<token>`）并以内置值兜底，宿主在 `:root` 上赋值即可定制，portal 弹层同样继承到；`--fve-popup-z-index` 是同一条路上的第二个旋钮：宿主自己的 chrome 堆得比 50 还高时，在 `:root` 上改这一个值，所有弹层一起抬；
- （见 test/popups.test.tsx「popups carry the theme out of the root」「a dialog themes its backdrop as well as its surface」）`verify-package` 断言两个 token 块无一例外。根默认涂 `--background`——钉住另一种模式的视图必须自带底色——宿主要让嵌入视图透出自己的底色，就把 `--fve-background` 设为 `transparent`；
- **Popover 也有自己的滚动口**：抄来的那份比 registry 多 `max-h-(--available-height)` 与 `overflow-y-auto` 两个类——Select 列表、菜单、Combobox 本来就有，registry 的 Popover 是按「三五行的短弹层」写的，而本包在 Popover 里开的是与字段一样长的列表（列设置一列一行，20 列的表就长过视口）。portal 出去的弹层不跟着页面滚，自己没有滚动口就等于够不到底下那几行。Base UI 在每个 positioner 上都写 `--available-height`，Popover 的也不例外，所以这两个类拿到的就是「触发器到视口边还剩多少」；
- 控件的那圈边（未勾选的 `Checkbox`／`RadioGroupItem`、`Input`、`Select` 触发器）画的是 `--input` 而不是 `--border`——分隔线可以淡，而"边就是控件"的那一类按 WCAG 1.4.11 要 3:1，两个主题都钉在 ≥3:1 上，由 `RecordWorkbench.test.stories.tsx` 的 `ControlBordersInLightTheme`／`ControlBordersInDarkTheme` 在真浏览器里量层叠之后的真颜色（连控件自己那层 `bg-input/30` 一起合成）守住；宿主覆盖 `--fve-input`／`--fve-dark-input` 时同样欠这一条。**没有底色的徽章是同一种情形**：把那圈边拿掉就没有徽章了，只剩一个词——所以 `outline` 档的徽章也画 `--input`。registry 给的是 `border-border`，量在标题栏上 **1.26:1**（暗 1.77:1），改后 3.64:1／3.77:1（`RecordWorkbench.test.stories.tsx` 的 `OutlineBadgeEdgesInLightTheme`／`InDarkTheme`）。它写在 `styles.css` 而不是 `variants.tsx` 的包装里：表内那几枚**有语气**的徽章只有一部分要改，那是 D16-8 说的包装的用武之地；而「这块面上的 outline 徽章一律如此」是无条件的，六处调用里还有一处是宿主拿本包 `Badge` 画自己的 chrome。规则问的是 `group/badge` 加 `data-variant`（两样都是 registry 自己写在每一枚徽章上的），**不是** `data-slot`——那是 `useRender` 的 state，调用处的同名 prop 会把它顶掉，「已修改」那一枚正是这样（`data-slot="view-unsaved"`），按 slot 问就恰好漏掉屏幕上最常见的那一枚。
- **焦点只有一种画法，因为按钮只有一种**。vendored `Button` 以 1px `border-ring` 加 3px `ring-ring/50` 光晕表示焦点，指示的是那 1px 边、光晕只是强调。屏幕上曾有两个裸 `<button>`（表头的排序、已应用条的 ✕），各自带一份抄来的同款配方常量 `FOCUS_RING`；抄一份配方不如用生产它的那个组件——两处现在都是 `Button variant="ghost"`（表头 `size="sm"`，✕ 是 `size="icon-xs"`，与视图名旁边那颗"未保存"里的撤销同形），常量已删。顺带修掉两件事：✕ 从 14px 的点击目标长到 24px（WCAG 2.5.8 对目标尺寸的下限），排序箭头不再手写 `size-3.5`——`Button` 自己就把里面的图标定到这个尺寸。表头按钮以 `-mx-2.5` 把自己的内边距抽回去，列名仍与下面的值对齐。`--ring` 与 `--input` 一样钉在两个主题都 ≥3:1（WCAG 1.4.11 对焦点指示的要求），由浏览器故事 `FocusIndicatorsInLightTheme`／`InDarkTheme` 聚焦三种控件量层叠色；暗色的 `--border` 提到 20% 白，行线在暗色卡片上 ≥1.5:1（`DarkHairlines`）。分隔线不是控件，不欠 3:1，但看不见的行线就是没有行线。

## 字段目录与选择器分组

- 列出字段的三个选择器（添加条件、列选择、分析的分组与指标）都经 `fieldGroups(fields, definition.fieldGroups, key)` 分组：未被任何分组列出的字段在前、无标题，其后按目录顺序列出各分组并带标题，组内按该分组自己的 `fields` 顺序；
- **列设置是三者里唯一有既定顺序的那一个，所以它有两条自己的读法**（[record.md](record.md#列设置的目录分组与搜索)）：目录只嵌在**中间区**里（左右两区按构造就短），而组内的行按**表格画的顺序**排，不按分组自己的 `fields` 顺序——另外两个选择器没有顺序要守，这一份列表本身就是列序；
- 选择器常常只列一个子集（尚未成为条件的字段、能做列的字段），所以没有字段的分组不显示。目录声明在 `DataViewDefinition.fieldGroups`（`{ id, label, fields }[]`），字段定义本身不记录归属：一个组有哪些字段在一处读完，组序与组内序都不被字段顺序绑住（字段顺序同时决定默认列序），列了未声明的字段名或把一个字段列进两个组都在定义准入时报错。Dashboard 的全局字段与元素字段没有目录，不分组。

## 版式：三块、一套间距、一种选项控件

五条规则，后来的改动按它们判。落到代码上是 `ui/layout.ts` 一处（`SPACE`、`TRAY`、`TEXT_UI`），不是各处手写的 class。

- **主列是三块，不是一摞行**。视图头（identity + 保存 + 视图级控件）是 **banner**：`border-b` 划一条线，不做卡片——给"说明这是哪一页"的那一行套个卡片，等于给整页套卡片。这条线以 `-mx-4 px-4` 穿过 `main` 的内边距通到工作区的边，与侧栏头下那条线（`view-list-header` 的 `border-b`）接成一条：两段各差 16px 的短线读成两个头，一条线读成一个头。条件区是一块**托盘**（`TRAY`：`rounded-lg bg-muted/40 p-3`，一层浅色底、不加边——条件 pill 才是带边的东西，托盘再加边就是框套框）；结果块是**一圈边**（`rounded-lg border`，无内边距）：工具栏是第一行、分页是最后一行、表格通到这圈边（D12）。块只在有内容时才存在：空卡片是一个"这儿有东西"的空头承诺。这条对结果块同样成立——分析视图跑之前既没有结果、也没有已应用条件条、也没有状态条，三样都不画的时候整块就不渲染，而不是留一个空边框。结果块由工作台组合，外壳只给那一圈边——仪表盘以 `resultFramed={false}` 退出，它那一格格面板卡片因此仍只有一层。
- **间距是一把有级差的尺子**，不是到处 `gap-2`：块与块 16px（`SPACE.BLOCKS`）、块内行与行 12px（`SPACE.ROWS`）、行内控件组之间 8px（`SPACE.GROUPS`）、组内 4px（`SPACE.WITHIN`）。分组要看得见，而两块之间的距离若等于两个按钮之间的距离，就没有什么是成组的，眼睛无处落脚。**主列的块间距归外壳**：`WorkbenchShell` 已经把 `SPACE.BLOCKS` 发给 `<main>`，工作台不再往 `className` 里塞自己的 `gap-*`——`cn` 让调用处赢，Record 曾因此把三块压到 8px，比块里的行还紧。vendored 组件自带的、不在尺子上的间距同样在调用处合缝：`FieldGroup` 的 `gap-5`（20px，比块与块的 16 还宽）由 `AnalysisEditor` 以 `className={SPACE.ROWS}` 覆掉——那是因为 `FieldGroup` 没有一个能问的 prop；能问的就去问（分段控件就是，见下）。（见 test/recordWorkbench.test.tsx 与 test/analysisUi.test.tsx 钉 class，stories/view-engine/ 的 `BlockSpacing`、`EditorRowSpacing` 量真实像素）
- **字号只有三档**：13（`TEXT_UI`）、14（`text-sm`：正文、表身、控件）、16（`text-base`：定义名那一级标题）。从前是四档——`text-xs` 的 12（分组标签、列头、徽章、分页、工具栏那句提示）与 shadcn `sm` 控件的 12.8（`text-[0.8rem]`，侧栏视图项与所有小按钮）只差 0.8px。0.8px 不是级差，是同一档画了两遍：侧栏里 12.8 的视图名压在 12 的分组标签上，读起来不像两级，像一级画歪了；12.8px 又不落在像素栅格上，中文在这一档渲染发虚。两档并成 13px，写在 `styles.css` 的 `--text-ui`（`var(--fve-text-ui, 0.8125rem)`，宿主可改；长度不分明暗，和 `radius` 一样不在暗色块里重声明）。自家标签走 `TEXT_UI`（字号连行高）；vendored 的两处——`sm` 控件的 `text-[0.8rem]` 与 `Badge` 的 `text-xs`——由 `.fve-root` 下一条作用域规则钉到同一个变量上，因为它们成打的调用处根本不传 class，而 `ui/components/**` 不手改。**真正低一级的地方仍是 12**：画在图表**里面**的标签（密度就是目的）、vendored 的菜单／选择器分组标题与快捷键提示、加分组菜单里 `AND`／`OR` 那个代码字样——它们都不与上面那一档并排读。（见 stories/view-engine/RecordWorkbench.test.stories.tsx 的 `TypeScaleIsThreeRungs`：真浏览器里量侧栏项、分组标签、列头、徽章与分页都是 13px，表身 14、定义名 16，整屏再没有一个 12.8px）
- **一屏只有一个 primary，它是跑查询的那一个**（D17-3）：三种工作台里都是编辑带底部的 Apply，同屏的第二个提交入口——Analysis 的 Run——降成 `outline`，因为 `useAnalysisEditor.submit` 与 `useFilterEditor.submit` 调的是同一个 `runtime.apply()`，是一次执行的两个入口而不是两次执行；宿主的全局动作同样不用 primary（见[动作槽位](#动作槽位)）。（见 test/analysisUi.test.tsx「carries one primary button on the screen, and it is Apply」按 variant 的 class 钉住，jsdom 不套样式表、量不到颜色）
- **互斥选项是一个控件，永远不是一排按钮**。判据按选项的多少与长短走：**≤3 个短选项** → 分段控件（segmented），一圈外框、内部无缝；**选项是一句话，或多于三个** → `Select`；**同一职责下的几个动作** → `ButtonGroup`；**一个主动作带几种变体** → 拆分按钮（`SaveActions` 就是）。踩过的坑是 `ToggleGroup variant="outline"` 的**默认间距**：每一项自带边框、组又给了 gap，读起来就是三个各自独立、碰巧挨着的按钮。合缝的东西 registry 自己就有——`ToggleGroup spacing={0}`：`data-[spacing=0]` 那几条规则把 gap 归零、内角拉直、相邻两项共一条边。曾经这里手写过一份同样效果的 class 常量，理由是"vendored 的 `ui/components/**` 不手改"；**传一个 prop 并没有改它**，手写的那份只是把上游已经维护好的配方抄了一遍。三处（筛选的简单／高级、结果工具栏的布局、分析编辑器的表／图）都只传 `spacing={0}`。唯一没随尺寸走的是外角：`sm` 的组盒子自己是 8px，首尾两项却固定 `rounded-l-lg`／`rounded-r-lg`（10px），与旁边 8px 的 `sm` 按钮并排就成了两套控件——这一条在 `styles.css` 里按 `[data-size='sm'][data-spacing='0']` 钉回去，和两处字号钉在同一个地方、同一个理由。（见 test/resultToolbar.test.tsx「ResultToolbar grouping and weight」）
- **registry 没有那个组件时，往下一层拿 Base UI 的原语，而不是自己写一个**。形制照 `ui/popups.tsx`：`ui/` 里一层只加 `data-slot` 的薄包装，`ui/components/**` 一个字不动。目前只有一处——`ui/toolbar.tsx` 包 Base UI 的 `Toolbar`（`npx shadcn@latest search @shadcn -q toolbar` 查无此人），结果工具栏用它拿到 `role="toolbar"`、`aria-orientation` 与漫游焦点（[record.md](record.md#resulttoolbar-的三组)）。包装里的 `ToolbarItem` 有没有工具栏都能用：在工具栏里它是 `Toolbar.Button`（登记进漫游序），不在时原样渲染收到的那个元素——Base UI 自己的 `Toggle`／`ToggleGroup` 就是这么认组的，而列设置、排序、导出这三个控件本来就会被单独渲染。判据仍是那一条：换了解决什么。解决不了什么的部分不换——`Toolbar.Group` 之于 `ButtonGroup` 就是。

## 工作台骨架

- 工作台的骨架自上而下是（[decisions.md#D12](../decisions.md#d12-一屏七块每块只回答一个问题)）：**标题栏 → 状态行 → 筛选托盘 → 结果条件带 → 结果块（工具栏 → 结果 → 汇总 → 分页）**。每一块回答一个问题，一个问题只在一处回答：标题栏答"我在看哪个视图"，托盘答"视图问什么"，结果条件带答"这些行是在什么条件下取来的"，工具栏答"我能对结果做什么"，结果就是结果。`ViewHeader` 一行说清这是哪个视图——种类图标、视图名、受众（名字后的一个灰字，`data-slot="view-audience"`，窄于 `@md` 时只留给读屏）、以及"屏幕上的东西存过没有"的标记（`saved === null` 是 `label.header.new-view`，`saved && dirty` 是 `label.header.unsaved`），保存命令紧跟在名字之后；上一次写入的结局（`WriteOutcome`：冲突、未知、拒绝）落在标题栏下方一行。**状态行**（`data-slot="status-line"`）紧贴标题栏之下，只装 `ErrorStrip`（`filter.unmarked`）与 `WarningStrip`，`empty:hidden` 让它在无话可说时不占位；查询失败不在这里——它是结果块自己的状态（Record 的 `QueryStrip` 经 `strips` 槽画在结果块里、**工具栏那一行之下**，带重试；见 [record.md#结果块有结果才有工具栏是第一行](record.md)）。状态行上**只有一条 error 时直接说那句话**，两条起才是标题加「还有 N 项」的折叠，行尾还带一条 surface 给的出路（`ErrorStrip` 的 `action`，Record 给「打开列设置」）。`EditorBand` 是编辑器所在的折叠带：已保存的视图打开时折起——作者已经决定过了，结果才是要看的东西——没存过的展开，折叠状态属于这一次打开，以 `runtime.id` 为 key 重置，不入库也不记忆。（见 test/editorBand.test.tsx「EditorBand」与 test/viewHeader.test.tsx「ViewHeader」）Analysis 与 Dashboard 本轮只接标题栏、状态行与结果条件带，编辑器形态照旧。
- 这副骨架由 `WorkbenchShell` 画，三个工作台共用一份：侧栏（`ViewList`，`manager` 只在 `manager.can.anything` 时交出去）、`LeaveDialog`，以及主列——打不开时是一块**空态形制**的「无法打开」（见下），没有任何视图可开时是同一形制的「还没有视图」（`ui/workbench/NoViews.tsx`，带「新建视图」按钮，列表加载失败时换成失败那句；没有创建权限时只有标题），否则是 `ViewHeader` → 状态行 → `editor` 槽（托盘） → `AppliedBar`（结果条件带） → 结果块（`toolbar` 槽 → `strips` 槽 → `result` 槽，顺序就是 D12 Ⅳ 的「工具栏是第一行」）。**结果块只在有结果、有在途请求、或 `strips` 槽真会画东西时才存在**（`ui/workbench/ResultBlock.tsx` 的 `resultBlockShown`，F-14）；不带边的那一种（`resultFramed={false}`）没有框可空，`result` 槽有东西就画。**正在打开**（`opened.loading`）时主列是 `ui/workbench/OpeningSkeleton.tsx`：一块标题栏骨架（种类图标、视图名、两颗控件）加一个结果块骨架（工具栏那一行 + 三行行），形状与打开之后一致，边跟着 `resultFramed`；侧栏折起时不画标题栏那一块——那个位置上外壳已经画了返回按钮与切换器。整块 `aria-busy="true"`，里面一个 `role="status"` 的 sr-only 句子（`label.workbench.opening`）说一次，其余一律 `aria-hidden`；`aria-busy` 不挂在那个活区上，否则它一直是 true、那句话永远播不出去。此前这里只有一条 `h-8` 的灰条，它说的是"有东西在加载"而不是"正在来的那一页长这样"（P-13）。props 是 `{ workbench, kind, title, theme?, messages?, locale?, timeZone, actions?, freshness?, editor, editorLabel?, editorModeLabel?, editorModes?, editorOpen?, defaultEditorOpen?, onEditorOpenChange?, editorPending?, toolbar?, strips?, result, errorAction?, defaultSidebarOpen?, onSidebarOpenChange?, expandable?, hasResult?, resultPending?, warnings?, onRenderFailure?, className? }`——`hasResult`、`resultPending` 与 `warnings` 留给自己没有结果、且告警由面板分担的 Dashboard 覆盖，其余两种读开着的那个视图本身（`state.result != null` 与 `state.query.status === 'loading'`）。要画什么几乎全部读自一个 `WorkbenchController`（[react.md#useworkbench](../react.md#useworkbench)），只有三样例外，因为它们既不属于视图也不属于列表：**侧栏收起没有**、**编辑带展开没有**、**视图有没有铺满屏幕**。这三样都只属于此刻这一屏——不入库、也没有一条离开守卫要问的东西——所以由外壳自己持有，而不是让三个工作台各写一遍同样的 `useState`；
- **结果区是一圈边，边只有这一圈**（D12 Ⅳ–Ⅶ）。`ResultBlock` 是 `rounded-lg border overflow-hidden`，**没有内边距、没有底色、没有行距**：留白按槽位给——`[data-slot=result-toolbar]` 是第一行（`border-b px-3 py-2`），`[data-slot=record-pagination]` 是最后一行（`border-t bg-muted/40 px-3 py-2`），状态条 `m-3`，空态 `my-6`，卡片 `p-3`，表格什么都不给、通到边。第一版没有这圈边：工具栏、表、分页读成三件碰巧叠着的东西，「正在显示 …」与工具栏之间没有过渡（用户 2026-09-21 的复核）。一圈边把四块说成一件事，代价是表不能再画自己的外框——否则又是框套框。仪表盘的结果是一格格面板卡片，它以 `resultFramed={false}` 退出，那是这个 prop 唯一的用处。（见 test/workbenchShell.test.tsx「the result block」）
- **「无法打开」与空结果是同一副形制**：`Empty` + 图标 + 标题（`label.view.unopenable`）+ 那条 `Issue` 作描述 + 一个动作「回到默认视图」（`label.view.open-default`，走 `workbench.choose(list.defaultInstanceId)`）。整块红字说的是「这个应用坏了」，而实际发生的只是**某一个视图不在了**——链接、书签、被删掉的视图都会正常地走到这里，周围的页面好得很。动作只在默认视图确实是**另一个**视图时才画：一个按下去把刚才打不开的视图再打开一遍的按钮，效果只是重画这一屏。`role="alert"` 留着——形制变温和了，事实仍然是「你要的东西不在屏幕上」，看不见页面变化的人得被告知。**这一屏上面那条栏和有视图时是同一条**：它由外壳在 `ViewHeader` 之外画，所以也由外壳给一个 `@container/header`——定义名按的是 `@md/header`，没有容器可问时它在任何宽度都不显示，而这正是全屏唯一还能说出「这是哪个定义」的地方（1280 收起侧栏：修前 `display: none`，修后 27px 的「订单 /」；420 两者都不显示，因为那条栏只有 288px，与有视图时同一条规矩）。切换器这时背后没有视图，标签与可及名都是**「选择视图」**（`label.workbench.choose-view`，列表尚未答话时同理）：空按钮上写「切换视图」，等于给一个并不存在的视图提议离开；看到的词与读屏念到的是同一句，控件才能被照着念出来要（WCAG 2.5.3）。（见 test/recordWorkbench.test.tsx「offers the default view as the way out of one that cannot open」、test/sidebarCollapse.test.tsx「collapsing with nothing to switch to」，浏览器故事 `CannotOpen`）
- **两级标题，一页一视图**：定义名是 `h1`——侧栏的标题（`view-list-title`，`text-base font-semibold`），侧栏收起时是标题栏 `leading` 槽里的那个（`definition-title`，后面一个灰色 `/`，与切换器连成一条路径「订单 / 待出库订单」）；视图名是 `h2`。此前两处定义名都是与视图名同级、比视图名还小的灰字，用户 2026-09-21 指出它读起来像注释——它是这一屏的名字，不是注释。**收起侧栏只是把 `h1` 挪个地方，不是把它降一级**：`definition-title` 与展开时的侧栏标题一样是 16/600，切换器里的视图名是 14/500。此前搬过去就成了 14/600 配 13/500——切换器吃的是 registry `sm` 按钮的 `text-[0.8rem]`，被主题钉在 13px 那一档（侧栏行与分组标签的那一档），于是「订单 / 待出库订单」两半只差了一级的一半，这一屏的名字反而比它装着的那个视图名还小。切换器的 `text-sm` 写在调用处，因为那是**字号**不是颜色，`cn` 顺手把 vendored 的那个 utility 合并掉、钉 13px 的规则也就不再匹配它（见 stories/view-engine/TitleBar.test.stories.tsx 的 `CollapsedPathIsTwoLevels`，真浏览器里量层叠之后的字号字重）。`ViewHeader` 的视图名是 `h2`（`headingLevel` 可由宿主定级），`main` 以它的 id `aria-labelledby`——只在标题真的在屏幕上时才指，指向不存在的 id 是一个坏标签而不是一个缺标签。（见 test/accessibility.test.tsx「the open view names the region it is drawn in」）
- **标题栏是两组，之间不串**。左边是「我在看哪个视图」：`data-slot="view-identity"`——`leading` 槽、种类图标、视图名（`h2`）、受众灰字、未保存标记，以及 `SaveActions`。保存命令跟着视图名走而不是站在行尾：它改的就是这个名字底下的那份配置。**还原就在「已修改」那个标记上**（`UnsavedMark`，`data-slot="view-unsaved"`）：标记是那个词加一颗 ↺ 图标按钮（名字与 tooltip 都是「还原」，写入在途或结局未结清时禁用），从没存过的视图只有「尚未保存」一个词、没有可回的地方。**按下去先问一句**：↺ 丢的是整份草稿，而运行时只会把**已保存**的那一份放回来——没有任何办法还原任意一份草稿，所以「已还原 · 撤销」这种条子许诺不出来；同样丢这份草稿的切视图早就要问，于是这一下问的是同一句话、用的是同一个形状（`AlertDialog`、`DestructiveAction`、文案键 `label.revert.*`，确认那一颗仍叫「还原」）。能撤销的动作前面摆对话框是摩擦，不能撤销的动作前面它是用户唯一一次说了算的地方。答完之后焦点落在视图名上（`finalFocus`）——「继续编辑」回到原来的 ↺，「还原」那一颗把标记连同 ↺ 一起带走了，默认的返还目标已经不在（见 test/viewHeader.test.tsx「ViewHeader, taking the edits back」）。此前还原是保存菜单的第二项——在一个 chevron 底下按两下，去做唯一回答这个标记的那个命令；用户 2026-09-21 的判断是它太深了，命令该挨着它撤销的那个事实。保存拆分按钮的菜单因此只剩「另存为」，没有另存为时连 chevron 也没有。所以视图名是 `w-0 max-w-max min-w-[6em] grow`：它吃掉的是**自己需要的**宽度而不是整行，受众字与保存于是紧贴着名字，而不是被推到右组跟前。右边是「我在怎么看它」：`data-slot="view-controls"`——先是**框架功能**一组：编辑带的开关（拆分按钮，带「改过没应用」的点，菜单选简单／高级）、刷新（拆分按钮，主键立即刷新、菜单选自动间隔——`freshness` 槽，三种工作台都用）、铺满屏幕；一根竖线之后是**业务功能**：这根线分的是两种**作者**（本包的视图级控件／宿主自己的动作），是这块面上唯一一条非看见不可的分隔线，所以它是 `variants.tsx` 的 `SectionDivider`（注册表 `Separator` 自己的 `--border`、20px、`self-center`）而不是调用处写了颜色的 `Separator`——它曾被涂成 `--input`（本包的 `--input` 是中灰）以量到 ≥3:1，结果是一排浅边按钮中间一根黑杠，整行唯一不属于这一行的线，而且注册表竖向分隔线的 `self-stretch` 撞上包装给的固定高度就贴顶不居中（用户 2026-09-22 两条都指出）；分隔线靠比组内间距高（28px 行里 20px，对着组内 8px）被读出来，不靠比旁边的边更黑，非文本对比度的下限是给控件的边的（见 stories/view-engine/TitleBar.test.stories.tsx 的 `TitleBarDividerInLightTheme`／`InDarkTheme`：与宿主按钮的边同色、站在行正中）。别的线可以淡——它们分的是同类（行与行、菜单里的两组），淡也仍读作「这是一份清单」；这一条分的是两种来历，一条看不见的线不是更克制的分隔，是没有分隔而那段间距照样花掉了。用间距说话是另一条路，没走：这一行的尺子只有组内与组间各 8px 一档，标题栏在窄处还会换行，16px 的空档读起来像换行的起点。宿主自己的全局动作永远排在最后，这样宿主加一个按钮不必知道它挨着什么；但它**不是** primary，用 `outline`——排在最右说的是「这是业务的去处」，不是「这是这一屏最该按的东西」（[动作槽位](#动作槽位)，2026-09-21 用户裁定，D12 Ⅰ 原本相反的措辞随之改写）。视图级控件由内向外读：编辑带管「视图问什么」，刷新管「答案多久换一次」，铺满管「答案得到多大地方」。**功能一律是带边的图标按钮**（图标带名字与 tooltip），只有同时报告状态的控件才带文字——编辑带开关带当前模式，刷新带当前间隔。
- **标题栏窄下来时，只有名字让步——但让步有下限**。这一行按「一组一根弹簧」摊开：每一组按**自己内容**定尺寸，组里恰好有一个会缩的成员——`view-identity` 里是视图名（`w-0 min-w-[6em] grow`），收起侧栏后是 `view-collapsed` 那一组（`grow`）里的 `ViewSwitcher`（`w-0 min-w-[calc(6em+3.25rem)] max-w-fit grow`）。`view-header` 自带 `flex-wrap`，于是两组并排放不下时右边那组整组换行，而不是压在左边那组上面；`view-controls` 带 `ml-auto`，所以它落到第二行时仍然右对齐，而不是缩到种类图标底下去。
  - **`min-w-0` 只给底下真有弹簧的组**。`min-w-0` 允许一个 flex 项被压到比自己内容还窄；`view-identity` 的成员除名字外一律 `shrink-0`，所以它以前会报「我 96.8px 就够」而装着 206.9px 的东西——父级信了这句话，`flex-wrap` 因此永远不触发，`SaveActions` 被画在 `view-controls` 底下 102px。375px 视口上，`Save` 左缘、正中、右缘三点 `elementFromPoint` 全答筛选开关：键盘够得着，指针一下也点不到；
  - **`truncate` 自己做不到这件事**。一行不折的标题即便 `overflow: hidden`，仍按整串文字向父级要宽度，所以按内容定尺寸的组会跟着名字一起长出去——溢出换了条路而已（`max-w-fit` 同理无效）。`w-0` 是一个**确定**的尺寸，组据此把名字算作零，`grow` 再把剩下的空间全给它：名字因此是这一行唯一会缩、也唯一会被截断的东西；
  - **被截断的名字仍带着全名**。`h2` 外面是一个 `Tooltip`，触发器 `render` 的就是那个 `h2` 本身（不多包一层，标题栏那套 `w-0 grow` 的伸缩算术因此原封不动）：截断只是视觉的，读屏照旧读得到整串，省略号之后指针用户却没有别的路回到全名。从前这里是原生 `title=`（D16 之前 `ConditionPill` 的字段名也是），而 `title` 只对鼠标开——键盘与触摸都够不着它，而这个标题恰恰是可聚焦的。（见 test/viewHeader.test.tsx「carries the whole name it may have to truncate」）
  - **名字的下限是 6em，而下限同时是那一组报上去的数**。没有下限的弹簧会让到看不见：375 宽、侧栏收起时切换器里的名字只剩 **40px**（「待出…」），旁边 74px 的受众徽章与 93px 的 `Save` 一寸不让——这一行存在的理由被挤掉了，而没有存在理由的东西还在。`min-width` 又正是一个 flex 项向上报的那个数，所以这一条同时是上面那句「换行而不是压扁」的开关：识别组要不到 6em 时，它如实报出自己要多少，`flex-wrap` 于是把右组整组挪到第二行。
  - **下限写在哪一个元素上，由「谁把整串文字向上要」决定**。`view-title` 自己带 `w-0`，所以 `min-w-[6em]` 写在它身上就够：一个有确定首选尺寸的 flex 项，向上报的是那个尺寸被 min/max 夹过之后的数，于是正好是 6em。切换器不行——名字在按钮**里面**的那个 `span` 上，`white-space: nowrap` 让它不论 `overflow` 如何都按整串文字向上要（和 `truncate` 那条是同一个陷阱），识别组会因此在**任何**宽度上都溢出。所以夹断的那个 `w-0` 留在按钮上，下限也就得写在按钮上：6em 的名字，加上图标、两个 gap、chevron 与左右内边距（`3.25rem`）。`span` 自己那个 `min-w-[6em]` 只是别让图标吃掉名字。
  - **缩无可缩时，先退化再溢出**。退化的判据是**这一栏有多宽**，不是视口有多宽——`view-header-band` 是一个名为 `header` 的容器查询容器（`@container/header`），窄于 `@md`（28rem）时受众徽章只留图标、`SaveActions` 上的词进 `sr-only`（名字不变，只是不占像素），窄于 `@2xl`（42rem）时定义标题不画。用视口问这件事是问错了对象：1440 页面上的一块 360px 面板里，`definition-title` 的 `sm:inline` 照显「订单」，而视图名挤成了「全…」。
  - **退化完还是放不下，就老实溢出，而不是互相盖住**。图标、`Edited`／`Not saved yet` 这类没有图标可退的词缩不动——一个被截断的「共享」比一次老实的溢出更糟——所以栏宽小于这些东西的和时，标题栏比它所在的那一栏宽，由外面裁掉。它不许做的是靠把自己的一组画到另一组上面来「放下」。（见回归 story「标题栏/回归」：三套内容各走一趟宽度阶梯，逐档量 `getBoundingClientRect()` 与 `elementFromPoint()`，并逐档断言名字不低于 6em、右组右缘与栏右缘重合——jsdom 不排版也不做命中测试，这条只能在浏览器项目里跑。阶梯的下沿就是那一套内容的不可再减宽度：已保存的一套走到 300px，加上 `Edited` 徽章的那一套走到 364px）
- **只有图标的按钮，把名字挂在 hover 上**（D12「功能一律用图标按钮（带名字与 tooltip）」）。名字只有一份，走两条路：`aria-label` 给读屏，tooltip 给指针，两处是同一个字符串——写第二种说法就是给同一个控件起了两个名字，日后只会改一处。配对只在一个地方做：`ui/IconButton.tsx`。`IconButton` 管常见形状（`Tooltip` → `TooltipTrigger render={<Button/>}` → `ui/popups.tsx` 的 `TooltipContent`，弹层在根外也跟着主题走）；触发器本身已经是按钮时用 `IconTooltip` 把那个元素原样收下——菜单的 `DropdownMenuTrigger render={<Button/>}`、分段开关的 `ToggleGroupItem`、chip 上那个自带几何的 `<button>`。**状态变，名字跟着变**：铺满开关 hover 出来的是它此刻会做的事（「铺满屏幕」／「退出铺满」），不是按下去之前的那件。拖动途中把手静音（`silent`，底下是 `Tooltip` 的 `disabled` 而不是受控的 `open`——后者一旦按住就再也不会开），键盘聚焦照旧说：把手能答的方向键没有写在别的地方。tooltip 与它所包的菜单不打架：点击把它关掉，指针停在触发器上有时又会把它带回来——两种都由 Base UI 自己定，而标签落在按钮**上方**、菜单落在下方，所以哪一种都不挡路。回归 story `AMenuIsNotCoveredByItsOwnTooltip` 守的是看得见的那一半：菜单每一项在自己盒子的中点仍是点得到的那一个，标签与菜单不重叠。同一个元素上外层触发器的 `data-slot` 会盖掉里层的（`render` 的合并里，外面的 props 赢），所以按 `data-slot="dropdown-menu-trigger"` 找一个带 tooltip 的菜单触发器是找不到的，按 `aria-haspopup` 找。**这条规则由测试守着**：`test/iconTooltips.test.tsx` 渲染三个工作台连同它们开出来的弹层，凡自身没有文字的 button 都必须带着 tooltip 触发器留下的印记——新加一个不说话的图标按钮，是这条测试失败，而不是靠谁想起来。
- **被截断的内容也把全文挂在 hover 上，而且是 `Tooltip` 不是 `title`**（D16-6）。原生 `title` 只对鼠标开：键盘聚焦打不开它，触摸屏根本没有 hover，于是「省略号之后还有什么」成了只有一种输入设备够得着的东西。chrome 上的七处因此换成 `Tooltip` + `TooltipTrigger render={…}` + `ui/popups.tsx` 的 `TooltipContent`（触发器 `render` 的就是原来那个元素，不多包一层，版式因此原封不动）：视图名（`ViewHeader` 的 `h2`）、条件 pill 的字段名、**记录表的列名**（`record/SortableHeader.tsx` 的 `column-label`，可排序的那一半在按钮**里面**的那个 span 上——tooltip 属于那个名字，不属于包着它的按钮）、合计行的数字（哪个字段的哪一种合计）、紧凑渲染边界里那一行说不下的失败原因，以及仪表盘面板的告警标与拖动把手——后两个已随`IconTooltip` 与可键盘编排一起落地。列名这一处此前连 `title` 都没有：800 上「订单号」画在它要的 37px 里的 18px（「订..」），1280 的宽表上「运单号」17px、「件数」25px 里的 16px，省略号之后那截字任何输入设备都够不着。**留着 `title` 的只有单元格**：记录表被裁掉的单元格、`cells.tsx` 的多行文本、热力图的格子——一张千格的表配一千个 `Tooltip` 实例，换来的那点可达性抵不过它的代价，这三处是明写的例外而不是漏网。（见 test/viewHeader.test.tsx、test/recordTable.test.tsx「carries the whole column name it may have to truncate」、test/renderBoundary.test.tsx；故事 `ATruncatedColumnNameIsOneHoverAway` 在真浏览器里量那一截字并把它 hover 出来）。**上面那三个名字现在装得下了**：表头里那颗排序按钮的天花板从格子的内容盒改成内边距盒（`HEAD_BUTTON`，见 [record.md](record.md#表格-chrome层次与冻结列)），此前它比自己那一格窄 16px。于是这枚 tooltip 管的是**用户自己把一列拖窄**之后的那个名字，而不是一张刚画出来的表上本来就该看得见的名字
- **一块面一个播报区**（`ui/Announcer.tsx` 的 `useAnnouncer`）。三处（列设置、排序编辑器、视图管理器）各有一个方向键一按即移的快捷方式，它绕过了 `@dnd-kit` 的 `KeyboardSensor`，所以库自带的那个 live region 说不出这一步——于是从前三处各手写了一份 `role="status" aria-live="polite" sr-only`。区域本身不是三处里有意思的部分（有意思的是措辞，在 `dragAnnounce.ts`／`columns/drag.ts`／`manage/drag.ts`），所以它只写一处：钩子交回 `say` 与 `region`，调用处把已经组好的句子递进去，并把 `region` 放在它那块面里。**一处一个**是这个钩子存在的理由——同一处两个 polite 区域就是两个抢着读的人，读屏用户分不清是哪一个在回答刚才那一下。**「一处」按谁答哪一下按键划**：工作台的面上只有结果块那一个（下一条），列设置与排序编辑器的那一个随弹层 portal 出去、只在弹层开着时存在，视图管理器的在对话框里——它们各答各的事件，polite 区域又是排队而不是打断，所以固定一列这种一按两件事（钉住了，并且重跑了查询）的操作是依次读出「仓库 已固定到左侧」「正在查询」「共 4 条记录」，而不是两个声音抢同一句。回归故事 `ToolbarAndFoldByKeyboard` 按这个口径数：面里一个、弹层里一个、`@dnd-kit` 自己那个另算；`data-slot` 由调用处给，所以测试照旧读得回某一块面说了什么。（见 test/columnSettings.test.tsx、test/sortSettings.test.tsx、test/viewManagerUi.test.tsx）

- **视图能铺满屏幕**，开关（`ViewExpandToggle`，`data-slot="view-expand"`）在标题栏右组、编辑带开关之后，带 `aria-expanded`；措辞是 `label.workbench.expand-view`／`collapse-view`（「铺满屏幕」／「退出铺满」——不叫「全屏」，浏览器自己那个 F11 才是，它连地址栏一起收走）。状态归 `WorkbenchShell`，与侧栏折叠同一类——只属于此刻这一屏，不入库、不记忆、不经离开守卫；三个工作台各自声明并透传 `expandable`（默认 true），宿主用主入口就能把这个控件去掉，不必放弃工作台自己去拼 `WorkbenchShell`。规则与理由：
  - **就地展开，不是 portal**。`useViewExpansion(target, toggleRef, enabled)`（`ui/ViewExpansion.tsx`）只在一个 `.fve-root` 上写一个 `data-view-expanded`——`target` 指到视图里面任何一个元素都行，hook 自己 `closest('.fve-root')` 解析到那个根，否则页面会被锁在一个根本没长大的面后头。重新挂载会把用户正看着的草稿、选择、滚动位置与正在组字的 IME 一起丢掉，面还会离开宿主那个带 `.dark` 的祖先，所以什么都不搬家。`ViewSurface` 因此把调用方的 `ref` 与自己那个合并（它自己要靠根读回明暗），并**把 callback ref 的清理函数原样透传**：React 19 允许 callback ref 返回一个卸载清理，宿主用 ref 装 `ResizeObserver` 就是这么还的，吞掉返回值等于让那个观察器跟着页面活到最后；
  - **顶层（top layer）不用**：`requestFullscreen()` 与 `popover="manual"` 都能一举绕开 containing block，也都被否掉，理由是同一个——本包所有弹层都 portal 到 `document.body`，字段选择器、筛选菜单、保存拆分按钮与视图切换器会整片落到铺满的面**后面**去（全屏下干脆不渲染）。一个打不开菜单的视图不算铺开了；
  - **留在普通层，只与宿主比高低**：铺满的面取 `z-index: 0`——自成一个 stacking context，但不高出一级。弹层不在这笔账里：它们自带一层（D11，`z-index: var(--fve-popup-z-index, 50)` 写在 positioner 上），怎么都在面前面。所以这个 `0` 说的只是面与**宿主页面**的关系：盖住宿主的普通内容，而宿主自己刻意抬起来的东西（一条 `z-index: 10` 的吸顶栏）仍会盖住它。自成 stacking context 是为了里面的部件（下面那个吸顶的出口）只和自己人比，不去和宿主的比。这条当初是反过来写的——那会儿弹层停在 `z-index: auto`，面取 `1` 或 `40` 就把列设置弹层埋了（Chromium 1280×800 实测），面因此不得不留在 0；D11 把层级搬到 positioner 上之后，约束没了，取值不变；
  - **`position: fixed` 不等于视口**：祖先只要有 `transform`、`filter`、`perspective`、`backdrop-filter`、`will-change`、`contain`、`container-type`，它就成了 containing block，`inset: 0` 于是只铺满**那个容器**——动画面板与要 GPU 提示的栅格外壳天天这么写，而 `EmbeddedView` 本就要落进任意宿主。逐个列举触发条件是一份会过期的清单，所以改为**量**：面上去之后读一次 `getBoundingClientRect()`，不是视口，差值就是修正量，写回 `--fve-expanded-x/y/w/h`（样式表里这四个的兜底就是 `inset: 0` 的长写法，常见情形一行 JS 也不写），`resize` 时重算。祖先若不只是**移动**、还**缩放**（`transform: scale()`、`scale`、`zoom`），还要再量一次：`getBoundingClientRect()` 报的已经是屏幕像素，而这四个属性是按元素自己的坐标读的，一个本地像素等于 `scale` 个屏幕像素——把差值原样写回去，偏移和尺寸会一起差同一个倍数。所以第二遍也是量出来的：写完朴素值再读一次盒子，**要的和到手的之比就是那个 scale**，除掉即可（回归故事 `FillTheScreenInScaledHost`）。剩下三种它治不了、也没有任何「留在原地」的方案能治：祖先自己**裁剪**（`overflow: hidden`、`contain: paint`）仍会裁掉，祖先把自己的 stacking context 抬到 portal 弹层之上仍会盖住，祖先**旋转或斜切**则根本不存在一个能盖住视口的轴对齐盒子——一个 inset 加一个尺寸表达不了一次转动；宿主遇到这三种应把工作台放到那个容器外面；
  - **不是模态，并且以「什么都不声明」说出这一点**：没有 `aria-modal`、不困住焦点、页面其余部分也不设 inert。什么也没在问、没有要回答的东西——这就是刚才那些内容，还在原处，还是宿主 DOM 的后代。声称模态等于告诉读屏器宿主页面不可用，而那是一个关于**内容**的承诺，我们没有资格做；把「其余部分」设成 inert 则要从这个元素一路往上、在每一层给兄弟节点加 inert——那是 portal 的活，而 portal 正是那个要拿草稿去换的东西。困住焦点更糟：非模态里唯一的出口会变成一个要靠猜的键。`test/accessibility.test.tsx` 在铺满与还原两种状态下都跑 axe；
  - **从模态那里只借一样**：背景不滚。一次看不见效果的滚动就是一个悄悄丢掉的滚动位置。锁写在**真正滚这一页的那个元素**上（`document.scrollingElement`，标准模式下就是 `<html>`）：body 的 overflow 只有在 html 还是 `visible` 时才传到视口，宿主只要写了 `html { overflow: auto }`，一个只锁 body 的面背后照样能滚。锁**按 important 写**——宿主的样式表可能正拿 `html { overflow: auto !important }` 或 Tailwind 的强制 utility 管着这一页，普通内联声明压不过它——并且**两个轴分开存、分开还**（`overflow-x`／`overflow-y`，各带各的优先级）：简写既读不出「只设了一个轴」「两轴值或优先级不同」的页面，写简写又会把两个长写法一起替掉，从简写还原等于把宿主另一个轴上原有的样式永久抹掉。锁按 `document` 计数：同一页上一个仪表盘面板的工作台与一个嵌入视图可以同时铺满，先收的那个不能把页面还回去，后收的那个必须还。计数归零时连记下的值一起丢掉，下一次铺满读的是那时候的页面而不是当初那个。卸载走的是同一条清理路径，所以「铺着屏幕直接跳走」也不会把页面锁死；
  - **Esc 收起，但前面有东西时轮不到它**：对话框、菜单、列表框，以及**原生 `<dialog open>`**（它的 role 是隐含的，不是属性，`[role="dialog"]` 永远匹配不上；document 上的监听器又跑在浏览器自己的默认关闭之前，不点名它，第一次 Esc 会把对话框和视图一起收掉），还有焦点仍停在 `data-popup-open` 触发器上的那种，都先于它拿到这个键（判据与 `FilterPanel` 的 Enter 提交同一个标记），`defaultPrevented` 的也一样放过。**正在用输入法组字时这个键也不归它**：Esc 那一下是给候选框用的，事件本身照样是 `Escape`、照样没被 prevent，收起视图等于把打了一半的词和焦点一起带走——判据是 `event.isComposing`，外加 `keyCode === 229` 这个不设 `isComposing` 的浏览器上的同义写法。判定用的是**事件自己那个文档的 `Element`**：iframe 里的节点对顶层 realm 的 `instanceof Element` 答 false，用错构造器等于对最可能被嵌入的那些面跳过整套检查。同时铺开的几个面共用一个 document，所以谁答这个键按**文档顺序**判——它们的 `z-index` 是同一个，谁盖着谁只由文档顺序决定；按「谁后铺的」记，宿主先铺了文档里靠后的那个、再铺靠前的那个时，Esc 会收起**底下**那个而用户正看着的那个纹丝不动。**焦点交给收完之后仍在前面的那个面的控件**——而且是那个面**身上**的那一个：前面那个面盖住宿主自己的按钮，和盖住这个面的按钮一样彻底，所以它的开关若不在它里面（嵌入视图的形态），焦点该落在它露出来的那个出口上——都收完了才回到自己那个：点按钮收起时什么都没重新挂载、焦点本来就在那儿，而在铺满的一整屏里按下 Esc，焦点会掉到 body 上；另一个面还铺着时把焦点丢回自己那个按钮，等于把它丢到一块看不见的内容里去。Esc 这条路由按钮上的 `aria-keyshortcuts`（只在铺着的时候）说出来，不为它单开一个 tooltip；
  - **控件没了，铺满就结束，不是存着**：`enabled` 转 false 时内部状态在渲染里就被清掉（不是放进 effect——那会先让屏幕上存在一个没有出口的铺满面），否则控件一回来视图就会在没人要求的情况下重新占满整页。**同一扇门的另一侧**：`enabled` 已经是 false 时调 `toggle` 直接什么都不做，而不是翻一个被 `on` 遮住的状态——宿主的控件可能比 `enabled` 活得久（快捷键还绑着、按钮还没卸载），存下那一下等于让控件一回来就占满整页，和上面那条是同一个陷阱。工作台传的是 `expandable && (open || opened.loading)`：切换视图释放旧 runtime、新的还在加载的那一下**不**结束——铺满是工作区的姿态，不属于某一次打开（Q7，与编辑带折叠不同）；只有切到的视图打不开时才结束，因为那时没有标题栏、也就没有开关；
  - **目标节点晚到、或者中途没了，都得算数**：`target` 是一个 `RefObject`，React 填它、清它都不出声，而那个 effect 没有别的理由再跑一次——宿主在内容还没挂载时就按下开关，API 会一边报 `expanded: true` 一边没有任何元素带上属性、页面也没被锁；铺着屏的那个面被宿主摘掉，页面会被永远锁在那儿而上面什么都没有。所以**铺着的时候盯 document**（`MutationObserver`，只在铺着时装，且只有「解析出来的节点和上一轮定下来的那个不是同一个」才惊动 effect）。宿主若只是把一个还活着的 `RefObject` 悄悄指向另一个已在屏上的面，这里无从看见，应当先收起再铺开；
  - **高度给结果，因为铺满是为了行**。只有根被拉到视口高而结果仍停在自己的 `max-height`，换来的是更多的**列**而不是更多的**行**，下半屏还空着。所以铺满时这条链成为定高弹性列：根 `overflow: hidden`，侧栏与主列各自 `min-height: 0` + `overflow-y: auto`，结果块 `flex: 1 1 auto; min-height: 0`，`RecordTable` 的滚动容器 `flex: 1 1 auto; min-height: 0; max-height: none`——它因此吃掉标题栏、状态条、工具栏与分页之外的全部高度。**只给自己在滚的那一个**：`RecordTable` 带 `data-scrolls` 标出自己是哪一种，`scrolls={false}`（仪表盘面板里顶着外层滚的那种）不吃这条规则，否则粘性层底下会被重新塞进一个滚不动的 scrollport。编辑带与条件块封顶在 `max-height: 50%` 并自己滚：它是条件的折叠带，不是视图被铺开的理由，一棵长筛选树把行顶下屏等于把整个手势作废；
  - **表格的粘性两种状态下都成立**：铺满改的是「哪个盒子高」，不是谁在滚——表头粘在顶、两行汇总粘在底、冻结列粘在侧（见 [record.md#表格-chrome层次与冻结列](record.md#表格-chrome层次与冻结列)），回归故事 `FillTheScreen` 与 `FillTheScreenInTransformedHost` 在真浏览器里按实测几何两种状态各量一次；
  - **嵌入视图铺满时，根自己就是 scrollport**：上面那几条把高度交给工作台的 `main`，再交给自己在滚的那个 `RecordTable`；而 `EmbeddedView` 把结果直接画在根上——没有 `main`，`RecordCards`、`AnalysisTable`、`DashboardGrid` 一个也不匹配——长结果会被根自己的 `overflow: hidden` 在屏幕下沿切掉，而背后那一页正锁着、够不着剩下的部分。所以 `:not(:has(> main))` 的根拿 `overflow-y: auto`；嵌入里的记录表仍吃上面那条、自己滚自己的，这条只兜它兜不住的；
  - **`EmbeddedView` 不长自己的开关**：它是结果本身、别无他物——没有标题栏、没有工具栏、没有保存——为了装一个按钮给它造一行 chrome，就是在宿主的订单详情页上摆一件那页没要、也放不到合适位置的东西。它欠宿主的是**办法**而不是按钮：`ref` 透传到它画的那个根，`useViewExpansion` 从 `/ui` 导出，宿主把控件放在自己 chrome 里，指向拿到的那个元素（或视图里任意一个元素）即可；
  - **但开关不在面里时，面自己长一个出口**：宿主的控件是这个面的兄弟节点，面一铺满整屏就把它盖住了——桌面用户也许会猜 Esc，触屏根本没有 Esc，那就是一块没有出口的屏幕。`ViewSurface` 因此在每个面上都画一个 `data-slot="view-exit"`（文案复用 `label.workbench.collapse-view`），平时带 `hidden`——不在页面里、也不在无障碍树里——只有 `useViewExpansion` 发现管着这次铺满的控件**不在**这个元素里时才把它露出来；工作台的开关本来就在标题栏里，所以工作台上永远看不到它。它不带自己的 handler：知道怎么收起的是持有这次铺满的那个面，点击由它接（于是 `ViewSurface` 一点铺满状态都不必知道）。它在根的 flex 列里占一整行（`order: -1`，右对齐）而不是浮在内容上——把一个按钮压在别人第一行数据上，正是嵌入视图存在的理由所反对的那种 chrome——并且 `position: sticky; top: 0`，因为它出现的正是根在滚的那种形态，滚走了的出口不算出口。（见 test/viewExpansion.test.tsx 与回归 story「FillTheScreen」「FillTheScreenInTransformedHost」）
- 留给扩展的缝还在：`ViewHeader.leading` 与 `ViewHeader.trailing`、`data-slot="view-sidebar"`、以及 `defaultSidebarOpen`（不给就由外壳量）／`expandable` 这两个布尔——折叠与铺满都是一处的改动，不是它旁边每一块的布局改动。

## 刷新是一个拆分按钮

- **主键一次刷新，`▾` 选间隔**（`RefreshControl`，`ui/RefreshControl.tsx`）。它是框架功能，落在标题栏右组（`freshness` 槽），三种工作台一样；主键是一颗图标按钮，名字是「刷新」，按钮上唯一的文字是**离下一次自动刷新还有多久**（D12：功能用图标，报告状态的才带字）。两半是一个控件，因为它们答的是同一个问题——屏幕上这些数字怎么更新；拆成两个按钮会把难得用一次的那个抬到天天按的那个的份量上。主键的行为与从前一字不差；
- **间隔改的是 `ViewConfigBase.refresh.interval` 本身**，选中即 `edit({ refresh: { interval } })` 加 `apply`——与排序、列设置同一条路（D3 的例外）：计时器读的是 `applied`，只 `edit` 不 `apply` 就只改了配置、没改任何会跑的东西。它因此像任何一次编辑一样让视图变脏，`Save` 才落库；配置里没有第二份间隔，草稿、计时器与屏幕说的是同一个数；
- **档位只有三档**（30 秒、1 分钟、5 分钟），并且**按内核会不会跑来裁剪**：整数且落在 `runtime.limits` 的 `[minRefreshInterval, maxRefreshInterval]` 里——`validateRefresh` 拒绝小数（`config.refresh.not-an-integer`）与越界是同一件事，所以这里也是同一个判断；不允许的档位**不存在**而不是禁用（D4）。选中的那个若跑得起来就并进梯子里（与每页条数同一条读法，梯子要能勾得上正选着的那一档），跑不起来则不并——那份配置本就被准入拒绝、状态条已经在说，菜单要给的是出路（关闭，或一个能用的档位）而不是那个坏掉的数；同理，`applied` 里一个跑不起来的数也不摆到按钮上冒充节奏；
- **`▾` 什么时候不出现**：梯子空、没有在跑的间隔、`refresh` 这个成员也没有被准入说过话，三者同时成立才不给——那时它能开出来的唯一一项就是视图已经在的那个状态。反过来说，**梯子空也要给**：一个正在跑的间隔总得有地方关掉；而 `refresh` 成员本身被拒时（缺失、不是对象、小数、越界）更要给，因为「关闭」写下的 `{ interval: null }` 正是这几种拒绝的修法——菜单此时把自己藏起来，用户就被钉在一份 Apply 与 Save 都过不去、屏幕上却没有任何控件能修的配置上——**报了错的那一项，一定够得着**（[record.md](record.md) 的同一条规矩，这里照办）；
- **开着时按钮上带一处凭据，而且它在走**：计时器武装着时按钮写的是**剩下多久**（`30s → 29s → … → 1s`），刷新随即发生（图标换成 spinner，与从前一样），落地后从头再数。数的是 runtime 公布的 `nextRefreshAt`（[runtime.md#自动刷新](../runtime.md#自动刷新)），界面不另起一只钟并行猜测；那只每秒重画的钟摆（`useRefreshCountdown`）也只在这个控件挂着、且确实有东西可数时才跳，卸载即停。只说「30s」的凭据答的是「多久一次」——那是菜单已经说过的话；人对一块自己会动的屏幕真正要问的是「什么时候」；
- **读法与停表时说什么**：单位词仍是 `label.refresh.seconds/minutes/hours`，向下取整到还填得满的最大单位（5 分钟那一档从 `5 min` 起，整个第五分钟都写 `4 min`，不足一分钟才逐秒数到 1）。不用 `mm:ss`——秒表的脸要求被精确地读，而这里没人在计时，它只是说「大概还有多久下面这些数字会动」。**请求在途时写 `0s`**：倒数确实到了零，旁边的 spinner 说明这是哪一种零；此时把字清掉会让它左右的按钮在用户正盯着这一处时挪位。runtime 因**另外三条**理由停表时（编辑器有焦点、页面不可见、草稿被拒）没有到期时刻，也没有刷新在跑，于是退回那一档本身（`30s`）——「这个视图每 30 秒刷新一次」仍然是真的，表只是停了，而冻在 `7s` 上的倒计时是在说谎；
- **宽度不许抖**：`tabular-nums` 只保证两位数字与另两位数字同宽，保证不了 `10s` 与 `9s`、`1 min` 与 `59s` 同宽。所以那处凭据是一格 grid：当前读数之上叠着该档位每个单位带最宽的那个读数（至多三个字符串），`invisible` 铺出宽度，右对齐，数字缩短时单位词不动。不用 `min-w-[Nch]` 算——单位词是目录的，`min`、`秒` 与数字不等宽，字符数预测不了宽度；
- **倒计时不念给屏幕阅读器**：整格 `aria-hidden`，朗读的是主键那一句 `label.refresh.on`（`aria-description`，说的是**节奏**不是倒数）。一个每秒都在变的数被每秒念一遍，正好是「告诉我这个按钮是干什么的」的反面。它说的是「这个视图在自己刷新」，是关于视图的事实，不是三态凭据（D2）之外的第四个点——点属于「改过、没应用」，在编辑带的开关上；
- **凭据读 `applied`，菜单勾 draft**——控件两半答的是同一个成员的两个时刻。凭据是一句「正在发生什么」，只能跟着计时器真正读的那一份走，与 `AppliedBar` 读 `result.own` 而不读 `applied` 是同一条理由；菜单勾的是草稿，因为那是编辑器的值、也是 `Save` 会写下的那个数，和布局切换、每页条数读草稿一样。两者只在**草稿被准入拒绝、`apply` 落不下去**时分开：此时结果上方的状态条正在说这份草稿为什么被拒，而旧的那个数才是真的。若两处都读草稿，按钮就会挂着一个没有任何东西在跑的节奏——把「关掉刷新但被拒绝」也一并说反：什么都没关掉，计时器还在原来那一档上等着；
- **停表的时机一律由 runtime 说了算**（草稿有 error、编辑器有焦点、页面不可见、请求在途，四条见 [runtime.md#自动刷新](../runtime.md#自动刷新)），界面不发明第五条。查询在途时禁用的只有主键那一半——再按一次只会把自己顶掉；仪表盘上「在途」要问面板：它自己不跑查询、`state.query` 永远是 `idle`，所以那一半读 `dashboard.resolving || dashboard.loading`（后者聚合子 runtime，与 `DashboardViewRuntime` 自己的计时器在开火前问的是同一件事），否则十二个面板正在查也照样点得下去，把它们全部顶掉且毫无提示；`▾` 照常可选，因为换间隔是关于下一段时间的决定，而 `applied` 变化时替换在途请求本就是 runtime 的既定行为。（见 test/refreshControl.test.tsx 与 stories/view-engine 的 `AutoRefresh`）

## 三态各有一处凭据

- 三处，不是四处：刷新按钮上那一档 cadence 说的是「这个视图在自己刷新」（见[刷新是一个拆分按钮](#刷新是一个拆分按钮)），是关于视图的事实，不参与下面这三处说的「屏幕上的东西走到哪一步了」；
- 三种状态各有一处凭据，互不重复：**草稿未应用**是条件 pill 与应用按钮上的那个点（`data-pending`），折起来时汇总成折叠行上的 `label.editor.pending` 计数。**基准是整份配置，不只是筛选树**（D17-6，`runtime/pending.ts` 的 `comparePending`：`draft` 与 `applied` 逐成员比较，条件按节点比、其余成员各算一项——它放在 runtime 层，因为 `dequal` 是 runtime 的，也是 `revert` 用的那一把尺）：`edit` 之后不 `apply` 的控件（筛选模式、分析编辑器的分组／指标／排序／`limit`／图表／合计，全都等 Run）与 `edit` 加 `apply` 但 apply 被拒的控件（草稿里有 error 时 `apply` 不落地，表头读的是草稿的 `sort`、分页条读的是草稿的 `pageSize`，行还是上一次执行的）从前都没有一处说得出来。于是 Apply、折叠行的计数与分析编辑器的 Run 都带那个点，被拒的 apply 同样算「没应用」；`useFilterEditor.pending`／`pendingCount` 读整份配置，pill 上的 `isPending(path)` 仍只比那一个节点，「撤销筛选修改」只在**条件**不同（`conditionsPending`）时出现——它只放回条件，一个等着应用的排序它碰不到。超预算的树不逐节点走（可能带环），算一项；**不进查询的成员不算**：筛选编辑器的简单／高级模式、记录视图的表格／卡片布局，切换即完成，同一批行照画，点上去的 Apply 什么也不会跑（分析视图的布局不同——内核只为跑过的那种布局整形图表，所以它的 `setLayout` 当场应用）；
- **已应用**是结果块顶部的 `AppliedBar`——它是这批行的说明文字，所以属于结果块而不是浮在编辑器与工具栏之间；它读 `state.result.own.filter` 而不是 `applied`——应用会启动一次查询，在查询答复之前 `applied` 已经走在前面，跟着它的条会描述还没到屏幕上的行；
- Dashboard 没有自己的结果，面板各跑各的查询，所以那里读 `state.applied.filter`，而「有没有结果可描述」由工作台看面板来答（任一面板已有结果或已经开始查询）；
- **未保存**是标题旁的标记，Save 按钮只在 `dirty && can.save && !pending` 时可按。AppliedBar 保留树的逻辑：根下每个直接子节点一个 badge，分组子节点合成一个；
- badge 的文字由 `ui/summary.ts` 的 `summaryText` 按部件拼，不是 `FilterSummaryItem.text`——那句是内核给宿主的英文兜底，摆在中文页面上就是唯一没被翻译的一行。字段名来自定义，操作符走 `label.operator.<OP>`（未知成员仍回退到派生拼写），值按 [值按字段显示](#值按字段显示) 的规则，与表格里同一套：定义给过名字的值用那个名字，其余按 `cell ?? kind`——所以 `cell` 和 `kind`、`numberFormat` 一样跟着摘要项走，否则声明了 `cell: 'date'` 的数字字段在表里是日期、在条上是十三位数——日期按 `ViewSurface` 的 `locale`／`timeZone` 显示，数字按 `numberFormat`，相对值按 `bound` 分成两句——区间用 `label.relative.window.<direction>`（`last {amount} {unit}`／最近 {amount} {unit}），边界用 `label.relative.instant.<direction>`（`{amount} {unit} ago`／{amount} {unit}前）——命名时段用 `label.relative.preset.*`。多值与组内各项之间的分隔符本身也是措辞（`label.filter.join`：英文 `, `，中文 `、`）；
- 分组以自己的操作符词起头（`label.filter.all-of`／`any-of`／`none-of`）再接各项，再嵌套的分组加括号；只有一条条件时 `all-of` 与 `any-of` 都不加那个词——它们什么也没多说——而 `none-of` 是否定不是连接词，有几条都要说。谓词条件（`ELEMENT_MATCH`）按同样的方式读出它持有的那些条件，谓词里什么也没问时说 `label.filter.any-entry`；
- 值读不出来的那一项只说字段名（这正是内核给的 `blank`）；字段已消失的那一项连操作符一起说——值读不出来，问题还在。✕ 的可访问名用的是同一段文字，所以读屏器听到的与屏幕上的一致；
- 每个 badge 带一个 ✕，把对应条件的值设回未填写（分组则组内每条）并重新应用，字段行留在编辑器里，这是 `clearValue(path)` + `submit()`；
- 没有条件而已有结果时显示 `label.applied.all`，还没有结果时整条不渲染。宿主注入的作用域条件（`scoped`）排在可编辑 badge 之后，以 `variant="outline"` 加 `data-scoped` 单独成组，不带 ✕，并由 `label.applied.scoped` 说明它由页面设定——它不在 draft 里，也没有一条编辑器的路径指向它，给一个删不掉的 ✕ 等于许诺一次做不到的放宽；再往后是**没人写下却在生效的口径**（`implied`，`variant="outline"` 加 `data-implied`，读屏附 `label.applied.implied`「缺省口径」）：定义声明了 `deletion` 一维而视图自有条件与作用域都没作答时，源只回未删除的记录，条上就要说「仅未删除」（D17-2）——它不在配置里，没有 ✕；改口径的办法是把那个字段加进条件并作答。三组都空才显示 `label.applied.all`；
- 嵌入式视图（`EmbeddedView`）整条 bar 都是只读的（`readOnly`），连自有条件的 ✕ 也不渲染。（见 test/appliedBar.test.tsx「AppliedBar」）

## 保存与视图管理

- 保存与视图管理分两处。`SaveActions` 是一个拆分按钮组：主按钮说此刻该做的那一件事（能存就是 Save，否则是 Save as；**从没存过的视图**（`commands.state.isNew`）按 Save 打开的是另存那张表——`SaveAsDialog` 的 `intent: 'first'`，标题「保存视图」、预填当前名字、提交写「保存」——因为它的第一次保存就是创建，此时菜单里也没有「另存为」），菜单里放其余的（Save as、Revert）；
- `pending` 时显示 `label.save.saving`，落地后 2.5s 内显示 `label.save.saved` 并向读屏器播报一次；
- 写入在途、或结局仍为 `unknown`／`conflict` 未结清时，Revert 与菜单一并禁用——在保存自己的编辑时撤销，会把被保存掉的那份配置变成新基线之上的脏草稿；
- 结局未结清时撤销，紧接着落地的 Retry 或「保留我的」会把它一并撤回。`hasErrors` 只在主按钮真的是就地 Save 时禁用它：不能写就地时主按钮做的是 Save as，副本去的是另一个受众，那里的准入由对话框自己判（共享仪表盘引用个人视图这类，正是在当前受众被拒而在个人受众成立），拿当前受众的判决锁住它，等于把只读视图的唯一出口一并锁死。改名、删除、排序、设默认都不在这里——它们改的是列表而不是眼前这个视图——而在侧栏标题旁的管理器（`ViewManager` + `useViewManager`）里，每个按钮按许可**存在或不存在**而不是置灰，系统视图没有改名与删除；
- 未打开实例的写入结局显示在它自己那一行。删除确认把后果拼出来：基础句，shared 再加一句，目标正是当前打开且 dirty 时再加一句；
- 键盘与焦点三处对齐（见 [management.md#列表偏好与默认视图](../management.md#列表偏好与默认视图)）：`ViewManagerRow` 的改名输入框 Enter 提交、Escape 取消并 `stopPropagation`（和 `SaveAsDialog` 一样接 Enter，不再只有 ✓ 能提交）；`DeleteDialog` 收一个 `finalFocus`，管理器传自己的标题进去，免得删完之后焦点落到 `<body>`；`SaveActions` 与 `WriteOutcome` 另给一个 `onCreated`——只有另存**创建**了视图才回调，就地保存不回调——`WorkbenchShell` 据此把焦点送到新视图的标题。这一组回调是 `ui/WriteOutcome.tsx` 上的 `ViewWriteCallbacks`，**只声明一次**：`WriteOutcome` 整组收下（落地与恢复都在它这里报出来），`ViewHeader` 整组转手，`SaveActions` 用 `Pick` 只取它真正会调的 `onSaved` / `onCreated`——从前它也照单声明了 `onRenamed` / `onDeleted` / `onRecovered`，却一个都没解构，宿主接上去只会等一个不会来的回调；
- 删除遇到冲突时「保留我的」不直接覆盖，而是用 `write.remote` 刷新后的摘要再确认一次（见 [management.md#冲突与未知结果](../management.md#冲突与未知结果)）——第一次确认说的是列表里的那个视图，冲突报回来的已经不是它。顺序是**拖出来的**：每行行首一枚手柄（`label.manage.drag`），拖动只在行所在的受众组内生效（个人与共享各是一个 sortable group，另一组的行不是放置目标），键盘等价物在同一枚手柄上（方向键移一位，空格拿起／放下，Esc 取消），落位播报走目录且只在落库之后说一次；落下提交**整个定义的完整顺序**（`moveTo(id, index)`，`index` 按该行自己那一组计数），落库失败不回滚——屏幕本来就没动——而在列表那一行报出来。一行的两件职责分在两头而不是一排散按钮：行首是排序的手柄，行尾是处置（设为默认／改名／删除）的一个 `ButtonGroup`；因为按钮按许可存在或不存在，各行带的动作数不同，动作簇是一个**每种动作一格的网格**（`ItemActions` 里的 `ButtonGroup` 带 `grid grid-cols-3`：设为默认／改名／删除），这一行带得起的那几个从头一格排起，好让同一个动作在每一行都落在同一个横坐标——槽宽由格子里的按钮自己量出来（三个 `icon-sm` 正是 84px），不再是手量一遍写死的 `w-21`，多一种动作只改那个 3；也不为对齐把缺席的动作画成置灰按钮（见 [management.md#列表偏好与默认视图](../management.md#列表偏好与默认视图)）。**就地改名走 `InputGroup`**：标题变成输入框时，✓ 与 ✕ 画在**框里**（`InputGroupInput` + `InputGroupAddon align="inline-end"` + `InputGroupButton`，registry 就有这件事的组件，forms 规则也只认这一种），而不是占用行尾那几格：它们是这个输入框的两个答复，不是这一行的另外两个动作；那个网格存在的理由（「改名」永远压在上一行的「改名」上）说的是一行**没在改名**时的事。改名途中 `ItemActions` 因此整个不画，两颗按钮的可及名字与 tooltip 一字未动（`label.manage.rename-confirm`／`rename-cancel`，仍经 `IconTooltip` 配对）。**输入框按它所改的那个视图命名**（`label.manage.rename-of`「改名 {title}」）：管理器是一列这样的输入框，从前每一个都叫「标题」，读屏沿着列表走下去听到的是同一个词重复 N 遍，从没说过光标下的是哪一个视图——而正在编辑的那个标题恰恰是它们唯一的区别。默认视图那一枚星星**实心**并带 `aria-pressed`，不只靠标题旁的徽章说。对话框打开时焦点给标题（`initialFocus`），不落在第一行的手柄或星星上。`rejected` 的那一行也带一个 `label.rejected.dismiss`，所有恢复按钮在 `manager.pending` 非空时禁用（见 [management.md#冲突与未知结果](../management.md#冲突与未知结果)）。管理入口本身按 `manager.can.anything` 决定给不给：顺序、默认与任一行的改名／删除全都不可用时，工作台根本不把 manager 交给 `ViewList`。（见 test/saveActions.test.tsx「SaveActions, the split button group」「WriteOutcome」与 test/viewManagerUi.test.tsx「ViewManager rows」「the manage button on the view list」）

落到文件上：「结局→一句话加一排按钮」只有一处，`ui/OutcomeActions.tsx`，打开的视图（`ui/WriteOutcome.tsx`）与管理器的行（`ui/ViewManagerRow.tsx`）共用它，两边的差别只是 `surface`——行在对话框里是一行小字小按钮（`LineAlert` 的 `bare`），视图是标题栏下的一条框（`box`）；两者是同一份 callout 配方的两种 frame，而不是两串手写类名（见[两级 severity 与 StatusStrip](#两级-severity-与-statusstrip)）。tone 也由它定：冲突与拒绝是 error（打断读屏），可能已经落库的未知是 warning。**冲突那一行的三条出路一律 `outline`，并按代价从小到大排**：使用最新版本 · 另存为我的副本 · 覆盖为我的版本（管理器的行没有「另存」，它没有地方放副本）。从前最危险的「覆盖为我的版本」是实心 primary——整屏唯一被强调的东西，正是那条最该想一想的路；而哪一条损失最小取决于两份配置里各有什么，屏幕替不了谁作主，这也正是取服务端那份与覆盖都要再问一遍的原因。同屏唯一的 primary 始终是跑查询的那个 Apply（[动作槽位](#动作槽位)，2026-09-21 用户裁定）。（见 test/saveActions.test.tsx「offers the three ways out of a conflict, safest first and none of them emphasised」）各自留下的是只有自己有的那部分：`WriteOutcome` 的复制出口与落地通知，加上 `ui/ConflictConfirm.tsx` 的双栏确认；管理器的删除后果对话框是 `ui/DeleteDialog.tsx`，第一次确认与冲突后的二次确认是同一个。这三处问的都是「会丢东西」的问题，所以用的是 `AlertDialog` 而不是 `Dialog`（`role="alertdialog"`，主题副本在 `ui/popups.tsx` 的 `AlertDialogContent`）：点旁边关不掉、焦点被按在两个答案上、角上也没有那枚 ✕——一次删除、一次弃稿、一次二选一，都不该被一下误点当成答案。

破坏性确认这三处的**问法、答法与层次**是一套，不是各写各的：

- **问句点名**。`label.delete.confirm` 带 `{title}`（「删除「{title}」？」／`Delete “{title}”?`），因为这个对话框**正好盖住它说的那一行**——从管理器某一行按下垃圾桶，弹出来的框压在列表中间，「删除这个视图？」指的就是读者此刻看不见的那一条；冲突后的二次确认更是在说一个此后变过的视图。后果句不变，仍是基础句加按需的两句。
- **执行那一颗是实底的 destructive**，`ui/variants.tsx` 的 `DestructiveAction`（`DeleteDialog`、`LeaveDialog`、`ConflictConfirm` 的「覆盖为我的版本」三处共用一个组件，调用处不写颜色——D16-8）。注册表的 `destructive` 按钮是 `bg-destructive/10` 配 `text-destructive` 的淡彩，与[徽章那一条](record.md#徽章的颜色由定义说了算但只能从主题里挑)是同一个陷阱：底色被朝字的色相挪过去，14px 上量到 **3.97:1**，够不着 1.4.3 的 4.5。改成拿 token 填色、拿 `--destructive-foreground` 写字之后是 **4.76:1**（亮）／**6.84:1**（暗）。底色照样写两遍（`bg-destructive dark:bg-destructive`），理由与徽章一字不差。
- **上面那一层要看得出在上面**。Base UI 默认**不画**嵌套弹层的遮罩，而删除确认正是从管理器（一个 `Dialog`）里抬起来的：原本它一层遮罩也没有，下面那张列表一点没被压暗，两张 `bg-popover` 互量 **1.00:1**——一张掉进列表里的白卡片。`ui/popups.tsx` 的 `AlertDialogContent` 因此给遮罩加 `forceRender`，并把它夹到 `ALERT_DIALOG_BACKDROP_DIM`（黑 50%，只有破坏性这一种对话框用；另存、管理器、导出窗口仍是注册表的那抹 10%，它们是「做事的地方」而不是「有代价的问句」）。暗色下这还不够：两张卡片都是 `oklch(0.205)`，黑纱再厚也压不出差（**1.09:1**），所以卡片自己那圈边加到 `ALERT_DIALOG_RAISED`（`ring-foreground/40`）。实测两层之间取底色差与边线差里大的那个：亮色 **3.98:1**（底色）、暗色 **3.68:1**（边线），都过 1.4.11 的 3:1。这一圈边是这份副本唯一加在 vendored 类名之上的一条，`test/popups.test.tsx` 比对两边渲染时按名归一化它，所以注册表把这圈 ring 换成别的 token 仍然算 drift。（见 test/viewManagerUi.test.tsx「names the view it is about in the question」「confirms with a solid destructive button」、test/popups.test.tsx「dims what is behind it harder than a plain dialog」，浏览器故事「DeleteActionContrastInLightTheme／InDarkTheme」）

## 离开保护

从侧栏切到另一个视图会释放当前 runtime，而未保存的草稿只活在 runtime 里，所以那是一次删除工作：`useLeaveGuard`（`/react`，见 [react.md#useworkbench](../react.md#useworkbench)）在 `dirty` 或写入结局为 `unknown` 时先问一句，没有东西可失去时一句也不问——每次切换都拦的守卫，人会学会不读就点掉。该问的时候问什么是无状态的，`/ui` 这边只剩 `LeaveDialog({ leave, messages? })` 照着 `leave.asking` 画，两个按钮分别接 `confirm` 与 `cancel`；它是一个 `AlertDialog`——点旁边关不掉，因为「留下」是一个要按出来的决定，而不是没做决定的默认结果；它渲染在承载文案的 `ViewSurface` 之外，所以要单独把 `messages` 递给它。

**守的不止是这一次切换。** 关标签、后退、点走一个外链同样带走草稿，而它们一次也不经过 `request`——没有哪个组件会被告知。所以同一条判据（`dirty` 或写入结局为 `unknown`）还挂一道 `beforeunload`（D18 Ⅸ，落在 `react/workbench/leaveGuard.ts`，`/ui` 什么也不用做）：脏或未知时挂上，干净时摘下，卸载时摘干净。处理器只做 `preventDefault()` 与 `returnValue`（后者是 Chrome／Edge 119 之前的旧路径），**不带任何措辞**——浏览器早已不显示自定义文案，能由我们措辞的那一句是上面那个对话框。**嵌入场景不挂**：`EmbeddedView` 没有编辑器、没有草稿、没有保存，压根不调这个钩子，一张只是展示某人存好的视图的业务页面，不该在关闭时被拦一下。宿主要整个关掉就传 `guardUnload: false`（`useWorkbench` 的选项）——那句提示属于整份文档，一个只占页面一角的工作台替所有人说话，是宿主该拍板的事。（见 test/workbench.test.tsx「useLeaveGuard」「beforeunload」）

## 动作槽位

- 三层业务动作走 render 槽位（`RecordActionSlots`）：`global` 在标题栏，`bulk` 在有选择时的结果工具栏，`row` 在表格最后一列（sticky，滚不走）与卡片页脚，统一裹在 `RowActions` 里。**槽位里的按钮不要用 primary**：同屏唯一的 primary 是编辑带里的 Apply（[版式](#版式三块一套间距一种选项控件)），宿主的全局动作用 `outline`／`secondary`，否则编辑带一展开就是两个 primary。这一条是规矩本身，D12 Ⅰ 原本写着「宿主的主功能按钮，同屏唯一 primary」，2026-09-21 用户按这一条裁掉了那句；故事里的宿主按钮（`RecordWorkbench.stories.tsx` 的 `WithActions`，「新建订单」）因此是 `outline`，它同时是这条规矩给宿主看的样板。动作是代码——它开表单、发命令、跳页面——所以由宿主交出来，不按字符串键注册，也不进配置：存下来的是"看法"，能对记录做什么属于挂载工作台的那个应用。（见 test/rowActions.test.tsx「RowActions」）
- **批量命令的结局有一条标准的条**（`ui/BulkOutcome.tsx` 的 `BulkOutcomeStrip`）：宿主把 `useBulkCommand` 的 `outcome` 与 `dismiss` 交给它，剩下的措辞、语气与出口都不用再写一遍（[react.md#usebulkcommand](../react.md#usebulkcommand)）。它就是写入结局那一份 callout 配方（`LineAlert`，见[两级 severity 与 StatusStrip](#两级-severity-与-statusstrip)）用在宿主自己的命令上——同一屏上「这条失败了」不该有第二套说法。三种读法对三档语气：全做完是 `info`（这是预期的结尾，预期的结尾不该喊），做了一部分是 `warning`，一条没做成是 `error`；本包没有 success 档，为这一条加一个就是只在这里出现的第四种颜色。**它的位置在工作台旁边而不是工具栏里**：`run` 成功后清掉选择，bulk 槽位随选择一起卸掉，条留在里面等于没有。故事 `RecordWorkbench.stories.tsx` 的 `WithActions` 是那份样板（导出所选 · 已取消的订单导不出，于是读到的是那条 partial）。（见 test/bulkCommand.test.tsx「BulkOutcomeStrip」）

## 渲染边界

- **宿主交进来的 React 各有一道边界**。三层动作槽位（`RecordActionSlots`，D6）与仪表盘面板里的 markdown 都在工作台自己的渲染树里，React 遇到抛错会从最近的边界往上整棵卸掉——没有边界时，一个抛错的行动作会把标题栏、编辑带和还没保存的草稿一起带走。所以 `WorkbenchShell` 给**标题栏的全局动作槽**、**编辑带**与**结果块**各一道 `RenderBoundary`（`ui/RenderBoundary.tsx`，`react-error-boundary`），`DashboardPanel` 给**每个面板的正文**一道，`EmbeddedView` 给自己的正文一道。落到边界上的那一块换成可复原的错误态——一句"这一块没能画出来"（`label.render.failed`）、错误自己的原话、一颗"重试"——`role="alert"` 就地播报；边界之外照常可用。全局动作槽的那道是单行的（`compact`），因为它站在一排控件里——它是同一份 callout 配方的 `bare` frame（见[两级 severity 与 StatusStrip](#两级-severity-与-statusstrip)），整块那一面仍是 registry 的 `Alert`，两面戴同一枚 error 图标。
- **错误不被吞掉**。每次落到边界都以 `RenderFailure { boundary, panelId?, error, componentStack? }` 交给宿主的 `onRenderFailure`——三个工作台、`DashboardGrid` 与 `EmbeddedView` 都收这个 prop——能修它的只有宿主。重试只是再画一次：原因还在就再落一次、再报一次。
- **失败属于它发生的那一次打开**。边界以 `runtime.id`（面板以子 runtime 的 id）为 reset key：切到另一个视图时各块重画，错误态不跟着人走。（见 test/renderBoundary.test.tsx「RenderBoundary」「the workbench boundaries」「the dashboard panel boundaries」；故事「Record 工作台/回归」的 `RenderFailure`）

## FilterPanel 的布局

- `FilterPanel` 的布局：分组是带边框的块，头部是**操作符选择器**与删除，主体是一条条件带：等宽栅格，能放几列放几列，pill 在格子里对齐，字段名、操作符、值上下对齐；操作符读作它对底下条件下的那句话——「满足全部条件」／「满足任一条件」／「全部条件均不满足」——而不是编译成的那个布尔：一次只显示一个，它就得自己把意思说全。三个操作符在任何位置、任何模式下内核都受理，所以没有一个会以禁用的样子出现（三个操作符在 `model/filter.ts` 的 `FILTER_GROUP_OPERATORS` 里是平的一组，选择器、加分组菜单与准入读的是同一份）；
- 条件带的轨道是 `minmax(min(20rem,100%),1fr)`，不是 `minmax(20rem,1fr)`：后者的 20rem 是一条**即使带子比它还窄也照钉不误**的下限，于是 375 上每一列都是 320px，pill 的右缘 366 冲出 342 就结束的编辑带。夹到带子自己的宽度之后，有 20rem 就用 20rem，没有就用带子有多少；
- 持双输入的条件（区间、日期）在条件带放得下两列时占两格；
- **值控件只要 pill 剩下的那点宽度，不自带下限**。它从前写 `min-w-40`：160px 是一条 flex 项**不管容器有多少都照样向上报**的下限，于是枚举选择器长出了 pill 自己的边——1280 上钻到 ✕ 底下 37px、越界 6px，420 上 104px 与 73px，而那颗 ▼ 在它自己的坐标上已经不是 `elementFromPoint` 答出来的那个元素了。现在是 `w-full min-w-0`：有多少要多少，选中的值由 registry 自己的 `*:data-[slot=select-value]:line-clamp-1` 夹断，而不是由 pill 夹断（见 test/filterValueEditor.test.tsx「lets the value select shrink to whatever room the pill has」）；
- **一句话放不下时，值另起一行**。pill 是 `flex-wrap`，值那一格带一条下限——单输入 6rem、双输入 9rem（`data-wide`）。条件带窄到字段名与操作符之后只剩 38px 时（420 的那一档），从前区间的第二个框会冲出 ✕ 31px，枚举选择器则只剩一颗 ▼、一个字也看不见；现在它整格掉到下一行，拿到 pill 的整幅宽度，✕ 跟着它走——一条读作「金额 介于 ／ 100 ~ 5,000 ✕」的 pill。轨道放得开的宽度上（一列 320px 起）什么也不折（见 stories/view-engine/FilterPanel.test.stories.tsx `TheValueStaysInsideItsPill`，它在 420／640／1024 三档上量每一个值控件的左右缘）；
- **区间的两端之间有一个 `~`**（`label.filter.range-join`）：并排的两个框是两个答案，而区间是一个——从前「金额 介于 100 ———— 5,000」读起来就是分别问的两个数。分隔符 `aria-hidden`，两端各自已经有名字（`label.filter.range-from`／`range-to`）；两端都是 `flex-1`，谁也不是那个让步的。**已应用条的摘要用的是同一个目录项**（`ui/summary.ts` 的 `range`），此前那个 `~` 是写死在那里的一个字符，改了目录也只改得动摘要、改不动编辑器。日期区间不在此列：它的两端是同一个触发器里的一句话（`2026年9月15日 – 2026年9月17日`），本来就是连着读的；
- 条件是内联的紧凑 pill（字段 · 操作符 · 值编辑器 · 删除），不独占一行，未填写时虚线边框，校验有 error 时标为 invalid（`data-invalid`，destructive 色），只有 warning 时标为 `data-warning`（主题的 `warning` 色）——条件照常执行，颜色只说"值得看一眼"；**边框读屏读不到，所以 error 还要落到控件上**：`aria-invalid` 按 issue 的 code 分派——`filter.operator.*` 是操作符选择器的，`filter.value.*` 是值编辑器的（`FilterValueEditor` 的 `invalid` 一路传到每个录入或选取值的控件：区间的两端、值列表的录入框、日期的三种形状都算，一个值是一句话，不论它占几个格子），`filter.field.*` 两个都标——字段没有自己的控件，它的名字就是 pill 最前面那个词；一条 pill 从左读到右就是一句话，所以 `label.operator.*` 每一项都是一句人话而不是枚举名的小写（`is`／`at least`／`more than`，不是 `eq`／`gte`／`gt`）：`ConditionPill` 与 `AppliedBar` 由枚举名推出的那份拼法只是宿主自定义 kind 的兜底，不是目录可以省事的理由（见 test/messages.test.tsx「says every comparison operator in words rather than in the enum」）；**取反是 pill 上的一个开关**（D18-7，P-15，2026-09-22）：与 ✕ 并排的图标切换（`data-slot="filter-negate"`，`aria-pressed`，名字「{field} 条件取反」），按下后句子里操作符前面多出一个词「不」（`label.filter.negated`，`data-slot="filter-negated"`），树里这条被包进一个只有它一个子节点的 `nor` 分组（`isNegation`，`negateAt`）——不是给每种 kind 各补一套否定操作符；`isSimpleTree` 认这种分组，所以简单模式写得出「不在这段时间内」而不用切到高级；简单模式的条件带把它画成同一颗按下的 pill（拾取器里这个字段仍是勾着的）——**这层包装只有内核知道**（A3）：条件带、pill 与字段拾取器都只问内核「这一条是什么、在哪儿」（`conditionOf`／`conditions` 给出 `{ leaf, index, path, negated }`，path 就是那片叶子的），✕ 一律是 `remove(path)`，由 `removeConditionAt` 连它那层 `nor` 一起删，UI 里再没有 `children[0]` 或 `path.slice(0, -1)`，高级模式则照树画成「全部条件均不满足」的分组块——高级模式有分组操作符，pill 上不再给开关，免得同一件事说两遍；已应用条把单叶 `nor` 说成「排除 …」（`label.filter.not-of`）而不是「都不满足 …」（见 test/filterPanel.test.tsx「negates a condition from its pill and says so in the sentence」）；
- 持有谓词的 `ELEMENT_MATCH` 条件和分组一样渲染为块，头部是字段与操作符，主体是它持有的分组。简单模式只显示根分组的条件带，高级模式显示根分组的块。**模式切换看外面有没有地方放**：它是「怎么编辑」而不是条件本身，所以外面一旦有更合适的位置，面板就把它交出去（`modes={false}`）——Record 与 Dashboard 的编辑器就是这块面板，模式因此挂在标题栏折叠带的下拉里（[工作台骨架](#工作台骨架)）。Analysis 不交：它的编辑器是这块面板**加上**分析编辑器，没有哪一个折叠带能用「筛选」这一个名字把两块都折起来，所以控件留在面板顶部（分段控件，见[版式](#版式三块一套间距一种选项控件)）。**一个存在却够不着的模式是丢掉的能力，不是更干净的界面**——`defaultAnalysisConfig` 从 `simple` 起步，控件一旦两头都没有，分析视图就再也写不出 OR／NOR 与嵌套分组。两处控件读的都是**生效的**模式而不是存下来的那个，简单模式画不出这棵树时那一项禁用，并把原因（`config.filterMode.not-simple`）挂在项上，而不是摊在旁边当一段散文。底部一行是这块面板的出入口（D12 Ⅱ：Add 靠左，Clear／Apply 靠右）：简单模式下它是**添加筛选 · 撤销筛选修改 · 清空条件 · 查询**；**高级模式下它只剩出口**——根分组这时已经是一个块，而每个块自带一套「在这个分组里添加 · 添加分组」，面板再摆一套，一个分组就有了四个入口、两两同义（`Add in this group / Add a group / Add / Add a group`）。**一个分组一套入口**：入口落在它作用的那个框里，出口仍在框底下那一行的右端（见 test/filterPanel.test.tsx「gives the root group one way in, not two」「keeps the single way in where the panel is the only way in」）。超预算的树画不出来，也就没有可加的地方，那一行于是只有「清空条件」这个出口。Apply 是同屏唯一的 primary 按钮——提交是显式的，面板里的任何输入都不会自己重跑查询；
- **条件区封顶 40vh，托盘挤不掉结果**：条件树装在一个 `max-h-[40vh] overflow-y-auto` 的滚动口里（`data-slot="filter-tree"`），底下那一行出入口在滚动口之外，托盘多高都看得见（高级模式下根分组自己的「在这个分组里添加」仍在它那个框里，跟着框滚——入口落在它作用的那个框里，见上一条）。两块各答一个问题：托盘是用来**改**条件的，结果是用来**看**的，手段让位给目的。实测 800×900、七条条件的高级模式：封顶前托盘 758px、结果工具栏在工作台坐标 974px（整块掉出首屏），封顶后托盘 424px、工具栏 640px。为什么是封顶而不是「条件多时默认折起内层分组」——折起会把**正在生效**的条件藏起来，而「我现在按什么条件在看」正是这一块存在的理由；40vh 是还能把另外六成留给标题栏、已应用条与结果头几行的最大值。空的简单模式不画这个滚动口：没有条件的时候整块不渲染，空框是一个没有内容的承诺；
- **添加筛选是一张勾选表，不是一次性的菜单**。点开是一个浮层：标题「选择筛选字段」、右上角「完成」、一个搜索框，底下是按目录分组的字段（未分组的在前、无标题，与其余字段选择器同一套 `fieldGroups` 布局），宽处两列、窄处一列（弹层自己的容器查询），可滚动。已经在面板上的字段是勾上的：勾上加一条条件（`addLeaf`），取消勾选把那条拿掉（`remove`）——「一个分组一个字段一条条件」这条规则让这个映射唯一，所以不存在「取消的是哪一条」的问题；已经填了值的字段也一样，勾就是这条条件在不在。浮层一直开着，`完成` 或 Escape 关闭，焦点回到触发它的按钮。建一个筛选本来就是挑好几个字段，每挑一个就关一次的菜单，四条条件要来回四趟；
- **嵌套分组另起一个控件**：分组块里「在这个分组里添加」右边紧挨一个 chevron，菜单是 `AND 满足全部条件`／`OR 满足任一条件`／`NOR 全部条件均不满足`（操作符代码在前，句子在后：已经用 AND／OR 思考的人一眼找到，没有的人读那句话）。它不再是字段列表的最后一段——一张让人勾字段的表里，容不下一个不是字段的条目；
- **Enter 即提交**：面板根上一个键处理器，`aria-keyshortcuts="Enter"`。四种情况不算：IME 组字中（`isComposing`）、按着修饰键（前两种是 `ui/filter/enter.ts` 的 `isPlainEnter`，自己答 Enter 的值编辑器问的也是它，于是带修饰键的 Enter 在面板里哪一格按下去都还是宿主的）、落在面板自己控件的弹层里（弹层 portal 到面板之外，React 事件却照样冒泡回来；判据与 `leavesEditor` 同一个 `[data-popup-open]` 标记），以及目标本身就吃 Enter 的控件（按钮、链接、textarea——在「添加筛选」上按 Enter 是打开选择器，不能顺带把查询也跑了）。`blocked > 0` 时和 Apply 按钮一样拒绝；
- **未填写的值显示「未设置」**（`label.filter.not-set`）：没填值是正常的编辑状态而不是错误，框里说清缺的是什么，比空着看起来已经填完要好。**每一种输入都归这一句管**，一种输入自己另起一个词（枚举与是否曾用「选择」）就等于说它缺的是别的东西；选择器的占位属于 `SelectValue` 而不是 `Select`（后者根本没有这个属性，传过去就是一个空盒）。日期是唯一的例外，它说的是 `label.date.pick`「选择日期」——两端各一个框，各缺一个日期，「未设置」说不清缺的是哪一个。**空值不读时钟**：刚加上的日期条件两端都是占位、草稿叶子保持空白，不拿「此刻」当起点画一个内核并不会编译的条件（相对与区间两种形态的默认值「最近 7 天」「今天」本身就是完整的答案，照旧）；未填写时也没有任何「清除值」的控件——pill 末尾那个 ✕ 删的是整条条件；
- **带时刻的字段（`withTime`）在日历下面给出时刻输入**（D17-1）：同一个弹层、同一个控件、一次提交——日历与钟表是同一条边的两半，任一半改动都把整条值重写一次；区间的两端各一个框（`label.date.time-from`／`time-to`），单边条件只有一个（`label.date.time`）。控件用原生 `type="time"`（registry 的日历示例就是这么配的），`step="1"` 让秒这一格出现：**秒是可选的**，只填到分存下来就是整秒。存下来的是不带偏移的挂钟串（`2026-01-31T15:30:00`），时区照旧由内核按引擎或条件自己的那一份解析——此前这里存 `toISOString()`，钉成了一个固定时刻，时区从此再没被应用过。**空着的框不是零点**：那条边存的就是日子本身，按区间读（起点 `00:00:00.000`、终点 `23:59:59.999`），框下面那一行（`label.date.time-hint`）把这件事说出来，因为一个空框本身说不出来。**没有日子就填不了时刻**：没选日子时框是禁用的——时刻要先有日子才是一刻，而拿「此刻」补一个日子正是上一条禁止的事。pill 上的触发器与已应用条的 badge 照这条规矩读回来：给了时刻就读到秒，没给就只读到日；
- **日历说的是这块面的语言**（`ui/filter/inputs/calendar.tsx` 的 `SurfaceCalendar`）。`react-day-picker` 的月份、星期与 ARIA 名字都从一个 **date-fns `Locale` 对象**里读，不给就退回 `en-US`——于是 `zh-CN` 的面上，触发器写着「2026年9月15日 – 2026年9月17日」，点开却是 `September 2026` 配 `Su Mo Tu We Th Fr Sa`，读屏听到的是 `Sunday, August 30th, 2026` 与 `Go to the Next Month`。`ViewSurface` 的 `locale` 是一个 BCP-47 标签而不是那个对象，两者之间没有哪种映射不等于把库里每一份 locale 都打进包里；而它逐项收 `formatters` 与 `labels`，每一项要的都是「某个日期在某种语言里怎么写」——这正是 `Intl.DateTimeFormat` 唯一会做的事，也是本包其余地方（`ui/display.ts`）一直在用的那条路，于是选择器与它旁边的单元格从此用同一套词说同一个月份。**日期格里是裸数字**（走 `Intl.NumberFormat`，跟着语言的数字体系走，但不带「日」——那个字属于读出来的日期，格子外面的表头已经说了是哪个月）。**一周从哪天起也归语言管**：`Intl.Locale#getWeekInfo` 按 CLDR 的 1（周一）到 7（周日）计，库按 0（周日）到 6（周六）计，取余就是全部换算；没有这个方法的引擎退回库自己的默认——问一句会抛异常的日历不是日历。`labels` 里那四句话没有哪个 formatter 产得出，走目录（`label.date.calendar-previous`／`-next`／`-today`／`-selected`）。**没覆盖的只有下拉式标题栏自己的名字**（`captionLayout="dropdown"`），本包不用那个形态（见 test/filterValueEditor.test.tsx「draws the calendar in the surface language, its chrome included」「SurfaceCalendar」、stories 的 `TheCalendarSpeaksTheSurfaceLanguage`）；
- **弹层按内容定尺寸，不按日历定**：`w-auto min-w-[17rem]`。只写 `w-auto` 时它就是日历自己那 212px——比开出它的那个 235px 触发器还窄，而底下的时刻控件只能在「一格格日期数字剩下多少」里排版：「起始时刻」分到 48px，在词中间折成两行，提示语折成三行。下限取日历自身的宽度（7 格加它的内边距），它下面的东西就不再由它上面那张表定尺寸。**时刻控件是「名字在上、框在下」**，也就是 `Field` 自己的默认形态与 registry 表单的形态；并排时 48px 既放不下「起始时刻」，也放不下 `From time`；
- 弹层本身带 `aria-label`（就是这条值控件的名字）：Base UI 的 popover 是 `role="dialog"`，没有名字的 dialog 读屏什么都不报，axe 也会报 `aria-dialog-name`；
- 落在条件上的 error 数（`filter.blocked`）大于零时它禁用，并在左侧以 `label.filter.blocked` 说还有几条要改；
- 草稿与已应用不一致时按钮上也带那个点。`submit={false}` 时底行整行不渲染，留给从别处提交的编辑器（比如 Dashboard 的全局条件带）。已应用条件的摘要不在面板里，在结果上方的 `AppliedBar`：根是 OR／NOR 时整体折成一个 badge 并说明；
- 宿主注入的作用域条件在那里另起一组只读呈现，不带删除。（见 test/filterPanel.test.tsx「FilterPanel tree editing」）
