## 1 目标与边界

**结构重构**（2026-09-25，[D46](decisions.md#d46-主题架构重构五条结构一张登记表2026-09-25)）：首发前按 [theme-architecture.md](theme-architecture.md) 重构主题的结构——品牌色成为每套预设都接受的输入（`brand` 预设删掉）、预设层（`--fvp-*`）与宿主层（`--fve-*`）分开、引擎自己的面成为一层角色、合同由一张登记表生成、图表从角色读出外观。本页描述的是 T1～T5 落地时的结构，批次落地后改写相应各节（S4 已改写 2.7 与 3.4.6）。

### 1.1 谁选、为什么要内置

**这份目录存在的两个目的**（用户 2026-09-24 定，T2 起每批都按它们验收）：

1. **研发能快速穿上自己品牌的外观。** 宿主选一套只要一行：一个属性、一个 prop，或引一个 CSS 文件；`brand` 从一个颜色派生出整套主题。两者照着文档就能用，不需要别的准备。快速上手页与主题指南页（中英文）正是这样写的，并带一张「我的品牌该选哪套」的表。
2. **证明主题系统可扩展、可定制。** 每套内置预设只经宿主也能用的公开合同搭出来：文档里记下的 `--fve-*` token、可选组、涨跌约定属性。没有私有选择器，不伸进组件内部，组件里也没有为哪一套预设开的代码路径。
   - `test/themeFiles.test.ts` 守住这一条：预设的每个变量都必须是主题登记表（`src/ui/theme/tokens.ts`，[theme-architecture.md](theme-architecture.md) 第 5 节）里给预设写的变量，`styles.css` 与 `src/ui` 读的每个宿主变量也都必须在登记表里（合同既被遵守，也是完整的）；README 的 token 表由登记表生成。
   - 包外有一套**宿主自己写的主题**作样板：Storybook「主题/宿主自定义主题」，自己的 CSS（`stories/view-engine/host-theme/acme.css`），用同一份合同，过同样的对比度与色板门。
   - 自查的手段是**写成文档的手工步骤**，不新增公开 API：Storybook「主题/预设 → 对比度矩阵」页粘贴自己的 `--fve-*`，对比度矩阵与色板三道门当场一起量（给宿主 CI 的自查脚本仍按 Q50 暂不做）。
   - 任何一套预设需要合同表达不了的东西，就是**机制的缺口**：记下来、在机制里修，不给那一套开特例。各批发现的缺口列在第 7 节的落地记录里。

项目的价值链是：研发声明「能怎样观察」，用户决定「这次怎样观察」，引擎负责编译、执行、渲染与保存（[README.md#定位与第一性原理](README.md#定位与第一性原理)）。主题不在这条链上，它是**宿主的外观**。所以：

- **宿主研发选**（已定）：他知道自己的产品穿什么衣服；终端用户只在宿主给了选择器时才间接选。主题不进 `ViewConfig`、`ViewInstance` 与仪表盘配置（D30 Q41）——同一份观察换一个宿主，必须穿那个宿主的衣服。
- **为什么企业数据视图产品要内置一批主题**：
  1. **接入成本**。今天宿主要么用 neutral，要么自己调 58 个变量、自己量对比度。多数企业宿主没有设计师，也不会去量焦点边是不是 3:1。内置预设把「调好、量过」的结果直接交出去：引一个文件、写一个属性。
  2. **归属感**。数据视图嵌在宿主的后台里。中国企业后台普遍长得像某个开源组件库，运维平台偏好紧凑的方角风格，面向业务人员的产品更像桌面原生应用。视图与周围 chrome 风格不一致，读起来就像一个外来的插件。
  3. **可达性是卖点，也是责任**。本包承诺的线（字 ≥4.5:1，控件边与焦点 ≥3:1，图表色觉间距）只对内置预设能证明。宿主自己抄的主题多半会丢掉这些线（shadcn 常见的 `--ring: var(--primary)`、`--input: var(--border)`，见 phase5 1.4）。内置的越贴近宿主想要的样子，宿主越不需要自己动手。
  4. **机制需要真实的使用者**。多主题的机制（图表重画、弹层继承、桥接）只有在真的有几套差别很大的主题时才会暴露缺陷——三套都是「灰配蓝」，圆角、字体、色板、密度这些轴就没有人用过。

### 1.2 一套主题包括什么

| 维度         | 进主题吗 | 说明                                                                                                                                                        |
| ------------ | -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 颜色（语义） | 是       | shadcn 那一整套，亮暗两半                                                                                                                                   |
| 圆角         | 是       | 一个 `--fve-radius`，其余几档由它乘出来（已有）                                                                                                             |
| 字体栈       | 是，受限 | **只许系统字体栈**（`system-ui` 一类），不许网络字体、不打包字体文件；不设就继承宿主（今天的行为）                                                          |
| 阴影（层级） | 是，受限 | 三档（sm／md／lg），只改阴影本身，不改哪里用阴影；卡片的浮起例外，归主题（`card-shadow`，[D43](decisions.md#d43-主题可以说面怎样分层控件怎样画2026-09-25)） |
| 边框         | 是       | `border`（分隔线，不要求对比度）与 `input`（控件边，≥3:1）两个颜色；线宽不进主题                                                                            |
| 图表色板     | 是       | 八个类别色（可选，见 2.5）；顺序色由第一色推导；发散色等有读者再加；涨跌色另起一条轴                                                                        |
| 涨跌色约定   | 另一条轴 | 「好坏」「红涨绿跌」「绿涨红跌」，与预设无关，由宿主按市场选（2.6）                                                                                         |
| 密度         | 另一条轴 | 紧凑／默认／舒适，与预设无关；预设只写「推荐」（2.4）                                                                                                       |
| 明暗         | 另一条轴 | 已有：`.dark`、`theme` 钉住、`theme="system"`                                                                                                               |

**刻意不进主题的**：

- **网络字体与字体文件**：体积、授权（例如某些系统字体只许在其平台上使用）、离线环境都成问题；宿主要网络字体就在自己的样式里加，`--fve-font-sans` 指过去即可。
- **字号阶梯与 `--text-ui`**：13／14／16 三档是为可读性定的（styles.css 的注释），不随风格变。
- **组件形状**：药丸按钮、浮动标签输入框这类「长什么样」的变体。它们改的是组件结构，不是 token；做了就是第二套组件库。
- **毛玻璃／半透明**：4.3 的数字说明在 Web 上守不住线，改用不透明的分层灰近似。
- **动效、图标、插画、背景图、渐变**。
- **布局尺寸**：仪表盘行高 80px（[D34](decisions.md#d34-搭板子时的格子是实心方块行高仍是-80px2026-09-24)）、固定宽度 1200px（D31）——存下的板子几何不能随主题变。
- **按视图的主题**：一个视图不带自己的主题（D30 Q41）。

## 2 主题模型与 token 分层

### 2.1 四层

| 层         | 谁写                     | 例子                                                                               | 规则                                                                                                          |
| ---------- | ------------------------ | ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| **输入层** | 宿主、预设               | `--fve-primary`、`--fve-dark-card`、`--fve-brand`、`--fve-font-sans`               | 唯一的公开入口，全部 `--fve-` 前缀；预设只给这一层赋值（`themes.css` 只含这种声明，已由 `verify-package` 守） |
| **语义层** | `styles.css`             | `--primary`、`--muted-foreground`、`--ring`                                        | shadcn 的名字；每个都写成 `var(--fve-<名>, 内置值)`，内置值就是 neutral，只有一处                             |
| **组件层** | `styles.css`             | `--row-hover`、`--quiet-foreground`、`--pin-shadow`、`--text-ui`、新增的密度 token | 能从语义层推导的就推导（`color-mix`），宿主一般不碰                                                           |
| **图表层** | `styles.css`，渲染时读回 | `--chart-1..8`、新增的 `--rise`／`--fall`、`--fve-chart-patterns`                  | `readChartTheme` 读回、转成 `rgb()` 交给 ECharts；读什么与观察什么是同一张表 `CHART_TOKENS`                   |

**不设公开的原始色阶层**（`--fve-gray-100` 这类）。理由：shadcn 的模型本来就只有语义层；多一层原始色阶，公开面翻倍，宿主改了 `gray-500` 却不知道它流到了哪几个语义 token 里，对比度也就无从量。色阶只存在于**写预设的时候**——每套预设的注释写明它取的是哪一档（`slate` 已经这样写），值落到语义层。

### 2.2 预设必须给什么，可以留给推导的是什么

- **必须给（成对量对比度的）**：`background`／`foreground`、`card`／`card-foreground`、`popover`／`popover-foreground`、`primary`／`primary-foreground`、`secondary`／`-foreground`、`muted`／`muted-foreground`、`accent`／`-foreground`、`sidebar` 那五个、`border`、`input`、`ring`、`destructive`、`success`、`warning`、`radius`，亮暗各一份。与 neutral 相同的写 `initial`（已有规矩）。**S2 起不再如此**（[theme-architecture.md](theme-architecture.md) 第 3 节）：预设写 `--fvp-*` 且只写它改的，`styles.css` 的复位规则（`@layer fve-reset`）在每个挂了预设的元素上先清空预设层，没有必给集合，也不再写 `initial`。
- **推导**：`destructive-foreground`（已推导）、`row-hover`、`quiet-foreground`（5A 已改成 `color-mix`）、`--rise`／`--fall`（默认取 `success`／`destructive`）、热力图的浅端（`mixColor`）、悬停色（`emphasized`）、柱内字色（`inkOn`）。
- **可选、全带或全不带**：图表八色（亮暗共 16 个）；阴影三档（亮暗共 6 个）；`--fve-font-sans`；推荐密度 `--fve-preset-density`。`verify-package` 的「每套赋同一整套变量」改成「必选集合相同；每个可选组要么全有、要么全无」。S2 起只剩图表八色与阴影两组要全给或全不给（登记表里 `whole` 的组）。

### 2.3 OKLCH

**采用，已经在用**：`styles.css` 与 `themes.css` 的每个颜色都写成 `oklch()`，与 shadcn v4 一致。继续用的理由不只是「跟上游」：

- **L 近似就是亮度**，对比度能在写的时候估出来。本页的品牌色派生（2.7）正是靠这一点：亮色主色把 L 夹在 0.40～0.54 之间，扫遍色相与 sRGB 色域内的全部彩度，白字最差也有 4.71:1（L=0.55 时最差 4.51，L=0.56 就跌破 4.5）；暗色主色夹在 0.68～0.80，配 `oklch(0.205 0 0)` 的深色字最差 5.27:1（2026-09-24 用 culori 扫的数，批 T3 写成单测）。
- **调一个预设只动一个量**：把 slate 的灰「移到同亮度」就是只换 h 与 C（5C 就是这样做的）。
- ECharts 读不了 `oklch()`，`readChartTheme` 已经统一转 `rgb()`，这条不变。

### 2.4 圆角、密度、字体、阴影怎样与颜色正交

| 轴         | 载体                                                                               | 谁赢                                                                                                                                                                        |
| ---------- | ---------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 预设       | `data-fve-preset`（已有），或面上的 `preset` prop                                  | —                                                                                                                                                                           |
| 明暗       | `.dark`、`theme`（已有）                                                           | —                                                                                                                                                                           |
| 圆角       | 预设里的 `--fve-radius`；宿主直接写 `--fve-radius`                                 | **不另设属性**：它只是一个变量，宿主在 `:root` 上写一行就赢过预设（S2 起靠两层变量：宿主写 `--fve-radius`、预设写 `--fvp-radius`，钉住的预设也赢不了宿主）                  |
| 字体、阴影 | 预设里的 `--fve-font-sans`、`--fve-shadow-*`；宿主直接覆盖                         | 同上，不另设属性                                                                                                                                                            |
| **密度**   | 新属性 `data-fve-density="compact｜default｜comfortable"`，或面上的 `density` prop | 宿主的属性总赢过预设的推荐：两者写**不同的变量**——属性写 `--fve-density`，预设写 `--fve-preset-density`，`styles.css` 取 `var(--fve-density, var(--fve-preset-density, 0))` |

为什么密度要一个属性，而圆角不要：圆角是一个值，宿主写一个变量就够；密度同时动四五个长度（表格行高、单元格左右内边距、侧栏项高、面板内边距、列表项间距），它们必须一起变，否则比例失衡，所以用一个 −1／0／+1 的档位驱动，由 `styles.css` 算出各长度。为什么密度的「推荐」与「选定」要拆成两个变量：如果预设直接写 `--fve-density`，那么「`<html>` 上选了紧凑、某块面钉了另一套预设」时，内层预设的值会盖掉宿主的选择——两个变量让宿主的选择在任何嵌套下都赢。

**密度动什么、不动什么**：

| 长度                 | 紧凑 | 默认（今天） | 舒适                                                                          |
| -------------------- | ---- | ------------ | ----------------------------------------------------------------------------- |
| 记录表与分析表的行高 | 32px | 40px         | 44px                                                                          |
| 单元格左右内边距     | 6px  | 8px          | 12px                                                                          |
| 侧栏视图项高         | 28px | 32px         | 36px                                                                          |
| 仪表盘面板内边距     | 8px  | 12px         | 16px（上下仍 12px：仪表盘行高不动，一行高的指标卡要放得下它的数，2026-09-25） |

**不动**：按钮与输入框的高度（点击目标 ≥24px，WCAG 2.5.8；Q49 的顾虑正是全局缩放 `--spacing` 会让 `icon-xs` 跌破它）；字号；**仪表盘行高 80px**（D34：存下的板子几何不变）；弹层的尺寸。记录表的行高今天写在 vendored `Table` 的 `h-10` 里，按 shadcn 的规矩不改 vendored 文件，改在我们自己的 `TableDataRow` 配方与 `styles.css` 里对表格的那几条规则上（与 `--text-ui` 钉住两个 vendored 字号是同一种做法）。

**为什么修订 Q49**：Q49 当时的判断是「密度更像用户这次怎样看，归阶段 6 的偏好」，前提是「谁来选」没有答案。用户今天定了「宿主研发选」，密度就与预设一样是宿主的外观：运维平台要紧凑，面向业务人员的要舒适。阶段 6 若要做个人偏好，写的也是同一个 `data-fve-density`，不冲突。代价：多一条轴、多一组要量的尺寸（点击目标、表头与行的对齐、冻结列阴影），T4 一批做完。

**字体**：`styles.css` 在 `.fve-root` 上写 `font-family: var(--surface-font, var(--fve-font-sans))`。两个变量都没设时，这条声明在计算值阶段无效，`font-family` 按 `unset` 处理——而它是继承属性，于是就是继承宿主，与今天一样，不需要写 `inherit` 兜底。图表的 `fontFamily` 已经从计算样式读，自动跟上。

**弹层的字体就是面的字体**：弹层也是 `.fve-root`，但 portal 到 `<body>`，继承的是 `<body>` 的字体。宿主把字体写在应用外壳上、`<body>` 不设时（故事的宿主外壳就是这样），不带字体栈的预设（`neutral`、`slate`、`graphite`、`fjord`、`contrast`、`brand`）下弹层成了浏览器默认的衬线体。所以面把自己**算出的** `font-family` 读回来（与读 token 同一处、同一组观察者），经 `useSurfaceFont()` 交给 `ui/popups.tsx`，弹层把它写成自己身上的 `--surface-font`（行内样式，和层级一样不靠样式表就能到）。它是面的计算值，所以预设的栈、宿主的 `--fve-font-sans`（挂在 `<html>` 或只挂在子树上）、继承来的宿主字体，哪一种来源弹层都与面一致；样式表在每个根上先把它写成 `initial`，面不会从宿主页面上拿到同名变量。不写成属性：属性带不了字体值；也不直接写 `font-family`：主题仍由样式表说。（见 test/popups.test.tsx「every popup takes the type of its surface」，浏览器故事 `PopupsTakeTheSurfaceFontUnderNeutral`／`…UnderPorcelain`）

**阴影**：本包只在弹层、卡片的浮起态、拖动中的面板上用 Tailwind 的 `shadow-*`。`styles.css` 的 `@theme` 把 `--shadow-sm／md／lg` 改成 `var(--fve-shadow-*, Tailwind 原值)`，亮暗各一份。暗色下阴影几乎看不见，所以暗色阴影一般带一条 0.5px 的白色 10% 描边做高光，读作「浮起」。

### 2.5 图表色板怎样与 ECharts 同步

**同步机制不变**：ECharts 的每个颜色都来自 `readChartTheme` 在图自己的元素上读回的 token；换预设、换明暗时 `ViewSurface` 观察到属性变化、token 读数的 key 变了就重画（5A、5B 已做）。本页要补的是：

1. **观察的属性表**加上 `data-fve-density`（不影响颜色，但影响图表所在格子的尺寸，已有的 ResizeObserver 会管）与 `data-fve-change-colors`（影响 `--rise`／`--fall`）。这张表与 `CHART_TOKENS` 一样放在一处，读什么与看什么不会分家。
2. **`CHART_TOKENS` 用 `--rise`／`--fall` 代替 `--success`／`--destructive`**：瀑布图的升降是方向，不是好坏（2.6）。
3. **用探针解析颜色**：`getComputedStyle(el).getPropertyValue('--x')` 对未注册的自定义属性返回的是**替换过 `var()` 的原文**，不是算出来的颜色。今天所有值都是字面量，没有问题；一旦预设写了相对颜色语法（2.7 的 `oklch(from var(--fve-brand) …)`）或 `color-mix()`，culori 解析不了，图表就会悄悄落回 `CHART_FALLBACK`。T1 在 `readChartTheme` 里加一个隐藏探针元素：把 `color` 设成 `var(--x)`，读它的计算值 `color`，浏览器替我们解析。不用 `@property` 注册：`--primary` 这类名字也是宿主 shadcn 的名字，全局注册会改变宿主自己的变量。

**预设可以带自己的八色（修订 Q47）**：

- Q47 的理由是「系列色跨预设保持身份」。那时的假设是一页上可能同时出现几套预设。今天定了「宿主选一套」，同一个用户几乎不会在两套之间来回看同一张图；反过来，一套北欧冷色调的主题里出现默认色板的高饱和品红，才是每个用户每天都看得到的不协调。
- **色位是序数**：`--chart-3` 的意思是「第三个系列的颜色」，不是「青色」。这与 Office 主题的 accent1～6 是同一个模型。代码里 `ChartSpec.colors` 写 `var(--chart-3)` 的，换预设后颜色会变，这是有意的；要表达「好／坏」「涨／跌」的，必须用语义 token（`--success`、`--rise`），不能挑色位。这条写进 [model-shapes.md](model-shapes.md) 的 `ChartSpec.colors` 说明。
- **门槛一样**：每套色板在两种明暗下都要过 5.2 的色觉间距、对底色的对比与柱内字色三道门；过不了就不许带自己的色板，退回默认八色。实测（下面第 3 节）说明这道门是真的会拦东西：几套知名色板照原样搬过来，有的在绿色弱模拟下相邻两色只差 2.4（门槛 8），有的在白底上一半低于 3:1。
- **顺序色**：继续由第一色与底色混出（热力图今天的做法），不设 token。**发散色**：今天没有读者，不加 token（「没人读的 token 是没人守的合同」，Q45 删 `--info` 的同一条理由）；将来有读者时的配方是「`--chart-1` ← 底色 → `--chart-2`」，两端都是色觉友好的蓝与橙，**不用红绿**。

### 2.6 涨跌色：另起一条轴

今天有两处颜色表示变化：`MetricCard` 的变化（「较前一日」这类较上一期，和对比指标）按**好坏**着色（`MetricCardSpec.lowerIsBetter` 决定上升是好是坏，好为 `success`，坏为 `danger`），瀑布图按**方向**着色（升用 `--success`，降用 `--destructive`）。这是西方 BI（以及 IBCS）的做法。中国大陆的股票与大量企业看板按**方向**着色，而且红涨绿跌；港股、欧美股市是绿涨红跌。

- 新属性 `data-fve-change-colors="semantic｜red-up｜green-up"`，默认 `semantic`（今天的行为）。它是**宿主按市场与读者**选的，不属于任何预设：同一套外观，A 股行情看板要红涨，海外子公司的销售看板要好坏色。
- 新 token `--rise`／`--fall`（输入层 `--fve-rise`、`--fve-fall` 与暗色两个）。`semantic` 与 `green-up` 下默认是 `success`／`destructive`，`red-up` 下对调。
- **怎样做到只靠 CSS**：`MetricCard` 已经写了 `data-direction`（`up`／`down`／`flat`）与 `data-tone`。`styles.css` 在 `:where([data-fve-change-colors='red-up'], [data-fve-change-colors='green-up']) .fve-root` 下按 `data-direction` 取 `--rise`／`--fall`，否则按 `data-tone` 取好坏色。组件不需要知道约定，也不需要 context；面照抄最近祖先上的这个属性给弹层，与预设一样。
- **一个坑**：不能在 `themes.css` 里写 `[data-fve-change-colors='red-up'] { --fve-rise: var(--destructive) }`。自定义属性里的 `var()` 在**声明它的那个元素**上替换；`<html>` 上没有 `--destructive`（它定义在 `.fve-root` 上），结果是无效值。所以约定的规则写在 `styles.css` 的 token 块里，按祖先属性选择。
- **色觉**：红与绿对红绿色弱几乎一样，所以涨跌**永远不只靠颜色**：`MetricCard` 已有箭头图标与正负号，瀑布图的标签带符号，提示框写「较上一期 +12%」。质量门里加一条：带涨跌色的元素都要有方向的非颜色线索（5.3）。

### 2.7 宿主自定义：覆盖变量，或只给一个品牌色

两条路，都只用 CSS：

1. **覆盖变量**（已有）：在 `:root` 上写任何 `--fve-*`，赢过选中的预设。README 的 token 表每行标出它要守的线。
2. **给一个品牌色，挂任何一套预设**（S4 起，[theme-architecture.md](theme-architecture.md) 第 2 节）：宿主写 `--fve-brand: <任意颜色>`（暗色可另给 `--fve-dark-brand`，不给就用同一个），预设照挂——或不挂。派生式只在 `styles.css` 写一处，包在 `@supports (color: oklch(from red l c h))` 里、声明在面的边界上：
   - 主色 `oklch(from var(--fve-brand) clamp(L下, l, L上) min(c, C上) h)`，暗色一半读 `var(--fve-dark-brand, var(--fve-brand))` 与暗色的边界；主色上的字仍是预设自己的 `primary-foreground`；
   - `accent`、`sidebar-accent` 与选中行（角色 `row-selected`）取品牌色相的一档淡色，亮度与彩度由预设给（`--fvp-brand-<token>-lc` 两个数）；
   - `ring` 只在预设给了焦点的亮度边界（`--fvp-brand-ring-l-min`／`-max`）时派生：`porcelain`、`contrast` 的焦点本来就是主色，给了；`neutral`、`azure` 的焦点是调到 3:1 的灰，没给，派生无效、焦点不跟品牌色；
   - 图表第 1 色只在宿主写 `--fve-brand-chart: 1` 时跟品牌色（取色相，保留预设第 1 色的亮度与彩度，`--fvp-brand-chart-1-lc`），默认关；
   - 其余（灰、`input`、状态色、图表其余七色）是预设自己的。
   - **边界是预设的**，因为线是在预设自己的底上量的：`neutral` 亮 0.40～0.50、暗 0.68～0.80（彩度 ≤0.18），`porcelain` 亮上限 0.48、暗 0.77～0.82（焦点暗色下限 0.78），`contrast` 为了 7:1 亮 0.25～0.36、暗 0.80～0.90；淡色的亮度也按各自的底调（`azure` 选中行亮 0.975、暗 0.26，`porcelain` 暗色选中行 0.34，`contrast` 暗色选中行 0.20）。`test/brandInput.test.ts` 在**每一套**、每种明暗、两种回到色域的方式下扫 1 314 个颜色，夹具里每一对都过该预设的线。代价是极亮（黄、青）或极暗的品牌色会被压到夹子里，看起来比品牌手册深或浅——这是可达性优先的有意取舍，文档写明。
   - **没给颜色、或浏览器不支持相对颜色**：派生值在计算期无效（或整块 `@supports` 不生效），每个 token 落回预设的字面量——像素不变。
   - **挂在哪**：任何祖先都行——派生在面的边界上算，`var(--fve-brand)` 在那里替换，不在挂预设的元素上。弹层 portal 到 `<body>`，所以只给某一块面时用 `tokens`。
   - **优先级**：宿主明写的 `--fve-primary` 等 > 品牌派生 > 预设的字面量 > 内置值。

**不做 JS 主题对象、`createTheme()`、ThemeProvider**：它们会成为第二个真相源（phase5 3.4 已定）。给宿主 CI 用的主题自查脚本仍按 Q50 暂不做；Storybook 的「主题一览」可以粘贴一段变量当场量（已有）。

### 2.8 与宿主已有的 shadcn 主题共存

`/shadcn-bridge.css` 已有：把 `--fve-*` 指向宿主的 shadcn token，`input`、`ring`、状态色、图表八色四类不桥接（Q46）。本页补两条：

- **桥接写预设层**（S2 起，`--fvp-*`）：宿主的 `--fve-*` 仍先读，钉住预设的面由复位规则清掉桥接给的值。
- **桥接与预设二选一，且规则写死**：今天两者都是零特异性、都可能落在 `<html>` 上，谁赢取决于宿主引入两个文件的先后，这是隐患。改成桥接只在**没有选预设**时生效：`:where(:root:not([data-fve-preset]))`。宿主既引了桥接又挂了预设，就是要预设。
- **桥接也桥 `radius`（已有）与新的 `--fve-font-sans`**（指向宿主的 `--font-sans`，shadcn v4 的名字）；阴影不桥，shadcn 没有标准的阴影 token 名。

给宿主的选择表（写进 README）：

| 宿主的情况                       | 用什么                                                  |
| -------------------------------- | ------------------------------------------------------- |
| 已经是 shadcn 应用，有自己的主题 | `shadcn-bridge.css`，不挂预设                           |
| 没有设计系统，想要一个现成的风格 | `themes.css`（或单套文件），挂 `data-fve-preset`        |
| 只有一个品牌色                   | 任何一套预设（或不挂）加 `--fve-brand`                  |
| 有完整的设计规范                 | 选最接近的预设，再在 `:root` 上覆盖差的那几个 `--fve-*` |

## 3 内置预设目录

### 3.1 命名规则

- **名字是描述性的普通词**（材料、自然、性格），小写：`porcelain`、`azure`、`contrast`。**不用**任何公司、产品、设计系统、编辑器主题的名字，也不用它们的特征子名（某个配色方案里的「某某风味」「某某夜」之类），也不用与某家公司强绑定的地名。
- **对外只描述性格，不点名出处**：README、故事标题、类型注释写「圆角大、系统字体、柔和阴影的桌面风格」，不写「像某某」。**一处例外**（用户 2026-09-25，[D46](decisions.md#d46-主题架构重构五条结构一张登记表2026-09-25)）：「该选哪套」的指路表里可以写「想要 macOS／Apple 桌面应用那种感觉 → `porcelain`」，只为让宿主找得到；预设名仍按风格取（`porcelain` 不改成 `apple`：Apple 是商标，预设一律以风格命名，不以品牌命名），规格仍注明「受其启发，与其无关」。本设计页是内部文档，**只在「参考」一栏注明灵感来源**，便于评审理解取舍，并明确是「受其启发、与其无关」。
- **值是我们自己按门调出来的**，不是整套照搬品牌色板；下表每套都写了与参考的差异及原因。若某套预设近乎原样使用了一个以开源许可证发布的色板，在 `THIRD_PARTY_NOTICES.md` 注明来源与许可证。
- **不带任何标识、图标库、插画、字体文件**。系统字体只经 `system-ui` 一类的名字引用本机已装的字体，不打包、不从网络加载——例如某些平台的系统字体授权只许在该平台上使用，引用本机字体不涉及分发。

- **不做「跟随系统提高对比度自动切到这套」**：换哪套预设是宿主的外观（已定）。系统的「提高对比度」已经自动开花纹（Q57）；Windows 的强制颜色模式（`forced-colors: active`）是另一件事，由浏览器接管颜色，本包要保证的是焦点、控件边、选中态在那种模式下仍然看得见——列入质量门（5.4）。

#### 3.4.6 `neutral`（`slate`、`brand` 已删）

**`slate` 已删**（2026-09-25，[D46](decisions.md#d46-主题架构重构五条结构一张登记表2026-09-25)）：在视觉走查里与 `neutral` 分不出来（只差灰的色相与主色）。**`brand` 已删**（S4）：品牌色成为任何一套都接受的输入（2.7），原来的 `data-fve-preset="brand"` 就是不挂预设（或 `neutral`）加 `--fve-brand`。

- `neutral` 不变（5C 的值）；它一个预设变量也不写，品牌色的边界用 `styles.css` 里的默认值。

### 3.5 推迟的，以及重新考虑它们的条件

暖灰（stone）、Material 风格、Fluent 风格、Primer 风格，以及几套暗色优先的编辑器配色（紫粉高饱和、马卡龙、霓虹夜色、经典编辑器暗色、日光米黄）。**加回来的条件**：有一个真实宿主要，且那一套的亮暗两半都能过 5.1～5.3 的门。每加一套的成本约半天到一天（值、量、故事、README 一行），机制不用动。

## 4 选择与切换

### 4.1 宿主 API

```css
/* 必须 */
@import '@ahoo-wang/wow-view-engine/styles.css';
/* 任选其一 */
@import '@ahoo-wang/wow-view-engine/themes.css'; /* 全部预设，运行时切换 */
@import '@ahoo-wang/wow-view-engine/themes/porcelain.css'; /* 只要一套 */
@import '@ahoo-wang/wow-view-engine/shadcn-bridge.css'; /* 用宿主的 shadcn 主题 */
```

```html
<html
  class="dark"
  data-fve-preset="porcelain"
  data-fve-density="comfortable"
  data-fve-change-colors="red-up"
></html>
```

- **属性挂在 `<html>` 上**，所有面与 portal 到 `<body>` 的弹层都继承。**要让一块嵌入与页面不同**，用面上的 prop：`theme`、`preset`（已有），加一个 `density`。涨跌约定不设 prop：它是整页的市场口径，一页里两种约定会让读者读反。
- **CSS 的粒度**：CSS 没有 tree-shaking，粒度就是文件。`themes.css` 保留（全部预设，属性切换），另出每套一个 `themes/<名>.css`，两者由同一份源在构建时生成，`verify-package` 断言单套文件拼起来等于 `themes.css`。体积见 5.6。
- **类型**：`/ui` 导出 `BUILT_IN_PRESETS`（只读名字数组）与由它得出的内置预设名类型（名字实现时定）；`preset` prop 的类型是「内置名 ∪ `(string & {})`」——内置名有补全，宿主自己的预设名也能传。这是公开面的一处新增，按 D29 在 `test/surface/ui.txt` 里逐名记。不导出显示名：引擎里没有选择器，显示名没有读者；宿主要做选择器就自己起名，README 的目录表给中英文的一句话描述可以抄。

### 4.2 终端用户的选择器：不在引擎里（已定）

工作台、视图管理、仪表盘里都不放主题开关。宿主要给用户选，就在**自己的 chrome** 里放（设置页、头像菜单），改的是 `<html>` 上的属性。README 给一段示例：用 shadcn 的 `Select` 列 `BUILT_IN_PRESETS`，外加一个明暗三档（亮／暗／跟随系统）。

### 4.3 跟随系统

- 明暗：`theme="system"`（5B 已做），宿主可选；或宿主自己在 `<html>` 上根据 `prefers-color-scheme` 挂 `.dark`。
- 花纹：跟随系统的「提高对比度」（Q57，已做）。
- 预设、密度、涨跌约定：**不跟随任何系统设置**，都是宿主的决定。

### 4.4 持久化是宿主的事（写进 README 的做法）

1. 用户在宿主的选择器里选了，宿主把 `{ preset, mode, density }` 存到它自己的地方（用户资料、localStorage、cookie）。
2. **不闪**：在 `<head>` 里、样式表之后放一段同步小脚本，读出存的值，在首帧之前把属性与 `.dark` 写到 `<html>` 上（与常见的明暗切换库同一做法）。视图在客户端渲染，读到的已经是最终属性，图表首画就用对的颜色。
3. **服务端渲染**：宿主按 cookie 直接在 `<html>` 上渲染属性。`theme="system"` 要在客户端才知道答案，SSR 的宿主应当改用上面的小脚本挂 `.dark`，而不是依赖面上的 `system`——否则首帧按亮色画、水合后再变暗。
4. 引擎不读、不写任何存储，也不提供「主题偏好」一类的钩子。

### 4.5 Storybook

- **工具栏**：「预设」全局已有（从 `themes.css` 读名字，新预设自动出现）；加「密度」「涨跌约定」两个全局，同一种装饰器把属性挂到 `<html>`。
- **「主题一览」扩成一张矩阵**：每行一套预设，每行里亮、暗两块，每块钉住预设与明暗，放**三种视图**：记录视图（表格，含冻结列、徽章、一行选中、一个获焦的控件）、分析视图（一张柱图带图例与较上一期、一张瀑布图显示涨跌）、仪表盘（筛选条带一个选中值、一个指标卡、一个图表面板）。粘贴自定义变量当场量的输入框保留。页面很长，按预设分锚点。数据等 Storybook 的真实交易订单夹具改造落地后换成那套（第 7 节）。
- **每套一页「预设」故事**（已有 Neutral／Blue／Slate 的形状）：新增的每套一页，便于截图与评审。删掉的预设连同它的故事与截图基线一起删（2026-09-25）。

### 4.6 打印与导出

- **打印**：`styles.css` 加 `@media print`：强制读当前预设的**亮色一半**（暗色选择器包进 `@media not print`）、去掉阴影、悬停色与粘性表头的阴影、强制开花纹（黑白打印时系列只能靠花纹区分）、图表与徽章用 `print-color-adjust: exact`。这样每套预设天然有一份打印样子，不需要打印预设。
- **导出图片**（ECharts 批 E，Q58）：所见即所得，用当前预设与明暗画；背景填当前的卡片色，不留透明。批 E 不需要等本方案，但若在 T1 之后做，瀑布图的涨跌色就直接用 `--rise`／`--fall`。

- **对照**：首页、运营日报、Record 工作台、分析工作台，`neutral` 与 `porcelain` 各亮暗两半，1280 宽，在真浏览器里并排看。字体（系统栈）、圆角 0.75rem、主色 #0066CC 都已经生效，其余读起来仍是一套通用 shadcn：
  1. **页底与卡片同是纯白**：合同里有 `background` 与 `card` 两个色，但看板的页底用的就是 `background`，而记录表、分析结果也写在 `background` 上——同一个色既当「分组的底」又当「内容的底」，`porcelain` 只能两个都给白。
  2. **卡片靠 1px 环线画出来，没有浮起**：面板是 registry 的 `Card`（`ring-1 ring-foreground/10`），预设能改颜色，改不了「用线还是用阴影」。
  3. **筛选条与分段控件是描边的**：边是 `input`（3:1 的灰），填色写死在组件里。
  4. **徽标是描边的药丸**：`ToneBadge` 的 30% 同色边与 `neutral` 的 `input` 边。
  5. **标题是 500**：视图标题、面板标题都是 registry 的 `font-medium`，苹果的层级靠更重的标题。
  6. **图表色**：`porcelain` 的八色确实生效了（计算样式里 `--chart-1` 是压暗的系统蓝，不是默认的 #2675D3）。看起来像默认色板，是因为前两个色位在两套里是同一色相族（蓝、橙），一两个系列的板子分不出来——这不是缺口，色位是序数（2.5）。
  7. **暗色**：页底 #1E1E1E、卡片 #2C2C2E、弹层 #343436，本来就不是纯黑。
- **缺口，修在合同上**（四个新的可选组，都有亮暗两半，`neutral` 全写 `initial`；每个的内置值就是改前画出来的样子，所以没设这些组的预设与宿主一个像素都不变）：
  - **`canvas`**：分组的底，看板和宿主按卡片排的页面站在它上面；不设时就是 `background`。看板的根（`data-kind='dashboard'`，由 `WorkbenchShell` 与 `EmbedFrame` 写在根上）画它，记录与分析仍写在 `background` 上。宿主在自己的 `.fve-tokens` 里用 `bg-canvas` 把页面接上（这个工具类即使包内没人写也照样发出去，`@source inline`）；故事的宿主外壳加了 `grouped`。
  - **`card-edge`／`card-shadow`**：卡片的环线颜色与浮起。不设时是 registry 的前景 10% 与无阴影。看板面板、记录卡片与它们的骨架都穿 `CARD_LIFT`；面板的警告仍在环线上，是一个 variant，压过主题的颜色。
  - **`control`／`control-edge`／`control-thumb`**：以文字或图标自明的控件——看板筛选条、分段控件——的静止填色、边与按下项。**没有内置值**：这些控件从来不是同一个值（筛选条是 `muted` 40% 加 `input` 边，分段控件是透明加 `input` 边、按下 `muted`），所以不设时各自回到原来的值（规则里的 `var()` 后备）。分段控件的按下项是轨道上的滑块：它的边和里面一像素取轨道的填色。规则放在 utilities 层、只重一个属性，所以组件的悬停、焦点、按下与错误态照旧压过它。
  - **`title-weight`**：视图标题与卡片标题的字重，不设 500。
- **决定**：
  - **打字的框仍有 3:1 的边**。WCAG 1.4.11 不要求以文字自明的控件有边界（选择框有字和箭头），要求输入框有；所以装着输入框的筛选条（「搜索订单」）不管主题怎么说都保留 `input` 边，`input` 本身仍守 3:1。苹果自己的 macOS 输入框也是有边的。
  - **字号阶梯不进主题**（1.2 不变），只给字重：13／14／16 是为可读性定的，标题大一号还会让各预设的标题栏高度不同。四组都是颜色、阴影与字重，不是组件形状（1.2），线宽也没进主题；只有卡片的阴影改了 1.2 的「不改哪里用阴影」，记为 [D43](decisions.md#d43-主题可以说面怎样分层控件怎样画2026-09-25)。
  - **`porcelain` 的弱字从 #6E6E73 压到 #636368**：筛选条的占位字（「未设置」「搜索…」）写在 12% 的填色上、填色又落在分组底上，只有 3.97:1；#636368 在那里是 4.71，在白底上 6.01。
  - **`porcelain` 暗色的控件填色是不透明的 #3A3A3C**，不是苹果的 24% 半透明：滑块外那一圈要与轨道同色，半透明叠在滑块上会成另一种灰。亮色仍是 12% 的半透明——不透明的浅灰落在分组底上会看不见。
- **没修的，留给下一步**（每条都写了为什么）：
  - **描边按钮**（「另存为」「刷新」、工具栏的按钮）：registry 的 `Button` 不在元素上写 variant，只能按类名去选，那是最脆的写法（D16）。要做就先让按钮在元素上说出 `data-variant`——上游 registry 目前没有，`shadcn add --diff` 确认过——或者包一层我们自己的配方。
  - **徽标**：`ToneBadge` 的边是为「在行上仍是一个徽标」（≥1.5:1）留的，只有淡色时在选中行上只剩 1.16～1.22:1（P-21）。去掉边就要改这条线，是产品判断，等用户拍板。（2026-09-25 已定：保留边，[D46](decisions.md#d46-主题架构重构五条结构一张登记表2026-09-25)。）
  - **选中的着色**：侧栏里打开的视图已经是一张浮起的白片（与苹果的侧栏选中相近），选中的行是 `muted` 带。改成主色的淡色要重新量行上的每一对字，另开一批。
- **门**：`test/presetContrast.test.ts` 把 `canvas` 加进每种底（字、状态色、徽标、涨跌、控件边与焦点），并在主题给了 `control` 时量填色上的正文与弱字、焦点边，以及滑块上的字；浏览器里的对比度矩阵（`themeContrast.tsx`）同样加了分组底与填色上的字。`verify-package` 把四组列进 `OPTIONAL_GROUPS`，并断言各组的数目（2／4／6／1）。README（中英）的 token 表加了七行。
- **实测最小值**（`porcelain`，三种约定取最差）：亮色字 4.71（T2 时 4.90；最紧的一对现在是分组底上、筛选条填色里的弱字）、控件边与焦点 3.25（`input` 在分组底上；T2 时 3.33）、标记 5.11；暗色 4.51／3.05／5.93，与 T2 相同，填色与分组底上的字最低 5.50。色板没动，间距与 T2 相同。

**T5 落地记录**（2026-09-25，裁定 [D45](decisions.md#d45-主题一览拆成每套一个故事截图基线在-playwright-的-linux-容器里截2026-09-25)）：

- **先解决的风险：主题一览的时长**。在 Playwright 的 Linux 容器里（`mcr.microsoft.com/playwright:v1.63.0-noble`，2 个 CPU）用 WebKit 量：
  - **改前**：一页 24 条带（8 套 × 亮／暗／跟随系统，每条一块板加一块卡片视图，约一万个元素、48 块面、24 张图）的故事 9～12 秒（第一次冷启动两个故事都超过 15 秒）；对比度矩阵单独跑 2.9 秒，跟在一览后面 4～5 秒。
  - **怎么量的**：在页里包一层计时，记下每个超过 60ms 的长任务里触摸／滚轮监听的增减，与每次读布局的耗时；再在装好的页上逐项试一次「改一处、强制一次布局」。
  - **根因**：Linux WebKit 在两种事件之后的下一次布局要把**整页**走一遍——根上的样式失效（在 `body` 上改一个自定义属性），以及任何一个 `touch*`／`wheel`／`pointer*` 监听的增减（重算事件区域）；`click`、`mousedown` 不算。这一页上每走一遍约 300ms，与监听的个数无关（再加 200 个触摸监听，一遍仍是 300ms），只与页面大小有关。一览的时间就花在这些整页走查上，外加 axe 在一万个元素上的一遍：挂载一个 1.6 秒的长任务（react-grid-layout 给 48 个面板各加两个触摸监听、24 张图各加滚轮监听，都在同一次提交里）；`userEvent.click` 导出按钮 1～1.3 秒（鼠标经过带提示的图标按钮，Base UI 的提示框打开、关闭时在 `document` 上加减触摸监听，每一次都是一遍）；故事后 axe 约 4.6 秒；卸载约 1 秒外加 Storybook 在两个故事之间停动画时读一次布局 0.43 秒——卸载算在**下一个**故事头上，这就是「没有图表的对比度矩阵也要 9 秒」：矩阵自己量完 640 个探针只要 0.12～0.18 秒。
  - **产品里有没有同样的代价**：#3408 之后没有「每块面板一遍」的走查了——图表同一帧创建（`watchSize`），栅格的监听同一次提交挂上，数据落地只改内容、不增减监听。剩下的都是**一次性**的（挂载、打开一个弹层、卸载），一遍的代价随页面大小涨：按元素数折算（估算，没有逐一量），一块十来个面板的真实仪表盘约是一览的五分之一，一遍约 60ms，而且只在 Linux 的 WebKit（GNOME Web、WPE）上付；macOS 的 WebKit 与 Chromium 不付（#3408 量过）。所以产品里没有可修的根因，改的是一览的形状。
  - **改法**：一览拆成**每套预设一个故事**（「能力/主题与预设/主题一览」下八个），每个故事亮、暗两条带、每条三种视图，六块面；对比度矩阵挪到 `ThemeContrast.stories.tsx`。没有放宽任何时限。
  - **改后**（同一容器、WebKit）：每套 1.6～2.8 秒；对比度矩阵 2.4～3.6 秒；强制颜色与打印两个故事 1.2～2.0 秒。Chromium 本机每套 0.8 秒左右。
  - **顺带看到、没有在这批改的**：react-grid-layout 在**只读**的板上也给每块面板挂两个非 passive 的 `touchstart`（拖动与缩放角即使关着也在），触屏上从面板开始的滚动要等主线程答完 `touchstart`。这是一个真实的触屏代价，但要在只读时绕过这个库、自己按它的算法摆面板，进入搭建时还要不重挂面板，不在 T5 的范围里，记在 [todo.md](todo.md)。
- **三视图矩阵**（`storybook/stories/view-engine/ThemeGallery.stories.tsx`，数据 `retail/gallery.ts`）：记录视图（近 30 天华东仓的单：单号钉住、订单状态与售后状态是带色徽章；故事用键盘勾第一行，那一行选中、它的复选框获焦）、分析视图（本月至今与上月同期的 GMV，分渠道两组柱，图例在上）、仪表盘（筛选条「发货仓 = 华东」、带走势与涨跌徽章的 GMV 指标卡、净销售额按渠道累加的瀑布图）。**与方案的偏差**：瀑布图放在仪表盘里而不是分析视图里（仪表盘本来要一张图表面板）；瀑布只有涨没有跌——零售数据里没有一个按组求和会是负数的可加指标（「较上月的变化」是派生指标，瀑布不收，D33），跌的颜色由指标卡的变化徽章露出来；「较上一期」在提示框里，截图里不画。不再有「跟随系统」一条带：它解析成亮或暗之一，`theme="system"` 的跟随由 jsdom 的 `chartTheme`／`styleBoundary` 守着。
- **工具栏**：「Change colors」一个全局（`semantic`／`green-up`／`red-up`），像宿主一样把 `data-fve-change-colors` 挂在 `<html>` 上；「Density」T4 已有。
- **截图基线**（5.5）：Vitest 浏览器模式的 toMatchScreenshot（pixelmatch，允许的不同像素为 0）。另起一个 `visual` 工程，只在 `STORYBOOK_BROWSER_WS` 设了时存在，只跑带 `'visual'` 标签的故事，视口 1280×900、`reducedMotion: 'reduce'`；故事里 `matchScreenshot(元素, 名字)`，在交互工程与 Storybook 面板里什么也不做。浏览器永远在 Playwright 的 Linux 容器里（`scripts/linux-browser.mjs` 起 `run-server`，按主机的架构原生地跑），Vitest 在本机或 CI 的主机上经 `exposeNetwork: '<loopback>'` 连过去，所以字体（文泉驿正黑）、ICU 与光栅化都是那个镜像的；图上的时间读引擎的时钟（`RETAIL_NOW`），页面上没有读墙上时钟的字。实测：同一个镜像连跑两遍逐像素相同，arm64 与 amd64 两种架构截出的图也逐像素相同。**与方案的偏差**：不是只在 CI 里生成——本机经同一个容器截出的就是 CI 的图，所以两条路都给（本机 `pnpm --filter wow-storybook test:visual --update`；CI 手动触发 `TypeScript Storybook` 并勾 `update-screenshots`，下载产物），都要人看过再提交；截图不只「主题一览」，加了三块关键屏；51 张 3.3 MB。
- **CI**：`typescript-storybook.yml` 多一个 `visual` 作业，`typescript-storybook-gate` 等它，没有新的必需检查；失败时把参考图、实际图与差异图作为产物 `storybook-screenshot-diffs` 上传。
- **强制颜色**（5.4）：Chromium 下 `forced-colors: active` 时，vendored 控件的焦点（`focus-visible:ring-3` 叠在 `outline-none` 上，是一层阴影）与表格获焦行（`FOCUS_ROW`，也是阴影）全被丢掉，选中行的 `bg-muted` 被重画成页底——焦点看不见、选中只剩复选框。修在 `styles.css` 的 `@media (forced-colors: active)`：`:focus-visible` 画 2px `CanvasText` 的轮廓，选中行画 2px `Highlight` 的内框（系统色，浏览器不重画；不用 `Highlight` 填满，那要让格子退出重画，里面的复选框与徽章就会留着为主题挑的颜色），获焦行的轮廓压过选中框。故事「强制颜色与打印/回归 · 强制颜色」断言获焦复选框、板上获焦的按钮有 ≥2px 实线轮廓，勾与未勾的复选框都有边，选中行有框、邻行没有；去掉这组规则它就红。
- **打印**（4.6）：暗色的变体与暗色 token 块包进 `@media not print`，纸上读预设的亮色一半；`@media print` 把三级阴影、卡片的浮起阴影（D43 的 `--card-shadow`）、钉住列的边影与行悬停色设成透明（透明阴影，不写 `none`，T2 的理由）、把 `--fve-chart-patterns` 设成 `on`（设在边界上，压过宿主挂在 `<html>` 上的开关），图表、徽章与变化徽标 `print-color-adjust: exact`。图表是脚本画的，媒体查询够不到：新的 `charts/print.ts`（`usePrinting`）在打印开始与结束时让 `EChart` 重读一次主题，纸上的图就是亮色、带花纹的；`useChartMotion` 在纸上也不动。故事「打印」在 Playwright 的 `media: 'print'` 仿真下断言暗色那条带读成亮色、没有阴影、图的坐标轴字色与亮色那条带相同且有花纹、`print-color-adjust` 是 `exact`，回到屏幕后变回暗色；去掉重读，它就红。
- **体积**：`styles.css` gzip 27 219 B（rebase 到 D43、D44 之后，含本批打印与强制颜色两组规则；预算 31 000 B 内）；`themes.css`、单套文件与桥接不动。

## 8 裁定

用户 2026-09-24「按你推荐」全部拍板，结论记在 [D35](decisions.md#d35-内置主题目录与三条轴的四条裁定2026-09-24)。下面保留当时的问题与推荐。

只列真正的产品决定；其余细节本页已定，理由在各节。

- **Q60 首发目录**：`neutral`（默认）、`slate`、`azure`、`porcelain`、`graphite`、`fjord`、`contrast` 七套，加 `brand` 派生；删掉 `blue`；其余推迟（3.5）。（2026-09-25 收敛为 `neutral`、`azure`、`porcelain`、`contrast` 四套，见 3.3 与 D46。）**推荐：同意。** 理由：每套在形状（圆角、密度、层级的画法）上都与其余明显不同，覆盖了中国企业后台、桌面原生、运维紧凑、开发者工具、高对比五类真实宿主；只换颜色的需求由 `brand` 满足，不再一色一套。代价：七套 × 两种明暗都要量、都要截图，约占 T2、T3 的四天。
- **Q61 涨跌色的默认约定**：默认 `semantic`（按好坏着色，今天的行为），`red-up`／`green-up` 只在宿主显式设置时生效；**不按界面语言自动切**。**推荐：同意。** 理由：语言不等于市场——中文界面看海外业务、英文界面看 A 股都常见；自动切会让同一份看板换个语言就红绿颠倒。代价：国内做行情类看板的宿主要多写一个属性，README 在 `azure` 那一行提示。
- **Q62 预设可以带自己的图表八色**（修订 D30 Q47）：可以，但全带或全不带，且必须过 5.2 的门；色位是序数。**推荐：同意。** 理由见 2.5：宿主只选一套，跨预设的系列身份几乎没有读者，而一套风格配一套不协调的色板每天都看得见。代价：每套自带色板多一份色觉与墨色的量；`ChartSpec.colors` 写色位的配置换预设会换色（写进发布说明）。
- **Q63 密度成为宿主的一条轴**（修订 D30 Q49）：三档，只动表格行、单元格内边距、侧栏项与面板内边距，不动控件高度、字号与仪表盘行高。**推荐：同意。** 理由见 2.4：「宿主研发选」定了之后，密度与预设一样是宿主的外观；阶段 6 的个人偏好可以写同一个属性。代价：T4 一批，外加三档下的对比度、点击目标与冻结列复量。
