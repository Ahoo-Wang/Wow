# Benchmarks

The end-to-end architecture benchmark of decision D224 (roadmap M7.5, B.0 to B.R) and the performance evidence of the project. Conclusions come only from requests that enter through HTTP and complete when the result the client waits for is visible. Services, stores and the bus are separate processes, in V10's recommended production topology. This folder holds the benchmark domain and its server, the load generator, the harness and the committed results.

V10 is measured against itself: each change against the code before it (alternating rounds locally, the head against a V10 baseline on GitHub Actions). The comparison with 9.x ended once it had settled V10's advantage; its last report, [`v10-vs-9x.md`](https://github.com/Ahoo-Wang/Wow/blob/26f1fa05030db5bcaeae70c34b6531dd1938c821/test/benchmarks/results/reports/v10-vs-9x.md), and its `vs-9x` suites were removed on 2026-10-24, and the 9.x server stays on the side branch `v10-9x-baseline` for the migration.

## The domain

The package `me.ahoo.wow.benchmark.transfer`:

| File | Concept |
| --- | --- |
| `TransferContext.kt` | The bounded context `transfer` and its aggregate `account` |
| `AccountCommands.kt` | `OpenAccount`, `Deposit`, `Withdraw`, `Prepare`, `Entry`, `Confirm`, `UnlockAmount`, `FreezeAccount`, and `Annotate` (the large payload) |
| `AccountEvents.kt` | `AccountOpened`, `Deposited`, `Withdrawn`, `AmountLocked`, `Prepared`, `AmountEntered`, `EntryFailed`, `Confirmed`, `AmountUnlocked`, `AccountFrozen` |
| `AccountRejections.kt` | The rejection codes: invalid amount, insufficient balance, frozen |
| `AccountState.kt` | Owner, balance, locked amount, frozen |
| `Account.kt` | The rules: `Withdraw` and `Prepare` read the balance and reject when it does not cover the amount; a frozen account refuses a transfer out (rejection) and an entry in (`EntryFailed`) |
| `TransferSaga.kt` | `Prepared` → `Entry` on the target; `AmountEntered` → `Confirm` on the source; `EntryFailed` → `UnlockAmount` on the source (the compensation). | `TransferServer.kt` | The server |

The semantics are those of the Java example `examples/transfer`, ported to Kotlin, with `Deposit` and `Withdraw` added. `src/test/.../TransferCases.kt` is one table of cases, which `AccountSpec` and `TransferSagaSpec` run through the test DSL.

## Topology

| | |
| --- | --- |
| Events | MongoDB log (`mongo` profile) or PostgreSQL log (`postgres` profile) |
| Snapshots | the same store |
| Commands | routed between the nodes over their internal ports (the cluster router) |
| Events to other services | the state stream published to Kafka (`wow.transfer.account.state`) |
| Cluster of 3 | a node id and internal port per node, leases on the store |
| Defaults otherwise | V10's |

The servers and the load generator run on JDK 25 (D393), the runtime Wow recommends (D368); the build's bytecode stays Java 21. The servers run with `-Xms1g -Xmx1g -XX:+UseG1GC` unless `--heap` says otherwise; JDK 25's new options (compact object headers, the AOT cache) stay out of the measurements. `bench.sh` refuses to start a JVM when `JAVA_HOME` is older than 25, and each result's `meta` records the full versions of the servers' JDK and the load generator's (`serverJvm`, `loadJvm`). Results before D393 were measured on JDK 21; the `jdk` suites measure what the runtime alone changes. `bench.sh` starts every run on empty containers and removes them afterwards.

## Completion points

Each scenario's request waits for its completion point; `load/.../TransferApi.kt` holds the routes and wait plans.

| Scenario | Operation | Completion |
| --- | --- | --- |
| E1 write | `Deposit` | `Wow-Wait: committed` (the append; the Kafka publication runs afterwards in its own subscription) |
| E2 read-your-write | `Deposit`, then a state read that must show its version | `snapshot`, then `GET /transfer/account/{id}/state` |
| E3 saga chain | `Prepare` from one account to another | `committed > handled(TransferSaga.onPrepared) > committed`: the saga's `Entry` stored on the target (the source's `Confirm` is not awaited, D224 implementation note) |
| E4 read by id | state of one account | `GET /transfer/account/{id}/state` |
| E4 list | ten accounts | `POST /transfer/account/snapshot/query`, `match-all`, limit 10, unsorted |
| E5 cluster | E1 and E3 on 3 nodes, requests spread round-robin over the nodes | as E1 and E3 |

The server has no Bean Validation provider and the commands declare no constraints.

## Load model and recorder

- **Open loop** (`run`): operation `i` is scheduled at `start + i / rate`, whatever the earlier ones are doing, and its latency is measured from that scheduled time, so a slow server cannot slow the arrivals (no coordinated omission). A warm-up (not recorded) precedes the measured phase. At most 20,000 operations are outstanding; one beyond is counted as `generator-overload`. Errors are counted by kind and their latencies kept apart. The operations go round robin over the nodes, as a load balancer with passive health checks would: a node whose connection fails is left out for a second, and an operation it refused (never sent) runs on the next node, its latency still counted from its scheduled time; the results count these as `rerouted`.
- **Closed loop** (`saturate`): concurrency doubling from 1 until throughput gains less than 5% twice, errors pass 1%, or `--max-concurrency`; the best throughput is the saturation point the open-loop runs take their 50% and 80% rates from. Its latencies only locate the knee.
- **Keys:** `uniform`, `zipf` (exponent 1.1) or `hot` (`--hot-fraction` of the requests to `--hot-keys` accounts, the rest uniform) over the seeded accounts, from a seeded generator, so the arms of a comparison see the same key sequence.
- **Recorder:** a log-linear histogram of its own (`Histogram.kt`): exact below 256 µs, 128 buckets per power of two above (at most 0.8% wide), lock-free. A run reports p50, p95, p99, p999, max, mean, and per second of the measured phase p50, p99 and max, whose worst p99 is the worst-second p99. The non-empty buckets go into the results as raw data.

## Resource capture

Over the measured phase, beside the load:

- every server JVM: CPU time and RSS from `ps` each second; heap and collections from one `jstat -gc -t <pid> 1000` per JVM (heap used max and average, the deltas of `YGC`, `YGCT`, `FGC`, `FGCT`, `CGC`, `CGCT`, `GCT`); `--jfr` adds a flight recording per server; the bytes it allocated (`totalThreadAllocatedBytes` of its `ThreadMXBean`, read over the Attach API at start and at stop, `Allocations.kt`), which the report divides by the run's operations as Alloc/op beside CPU ms/op;
- every container: CPU and memory from one `docker stats` stream;
- the stores: MongoDB's `serverStatus().opcounters` with its journal's syncs and their time (`wiredTiger.log`), the write concern's majority waits and their time (`metrics.getLastError.wtime`), the writes' and transactions' operations and latency (`opLatencies`), the transactions aborted and the retried commands (`transactions`) and the write conflicts (`metrics.operation.writeConflicts`), PostgreSQL's `pg_stat_database` of `transfer` with `pg_stat_wal` (`track_wal_io_timing` gives the WAL's write and sync times), and the end offsets of every Kafka topic, before and after, and their difference; each store's counters also once a second over the phase (`postgresSeries`, `mongoSeries`).

## Running it

From the repository root, with Docker and `JAVA_HOME` set to a JDK 25 (on macOS, `export JAVA_HOME=$(/usr/libexec/java_home -v 25)`: the script cannot read a shell alias). `bench.sh build` runs Gradle, whose toolchain still compiles for Java 21:

```bash
test/benchmarks/harness/bench.sh build
test/benchmarks/harness/bench.sh run --scenario=E1 --rate=200 --warm-up=30 --measure=60
test/benchmarks/harness/bench.sh run --backend=postgres --scenario=E3 --rate=200
test/benchmarks/harness/bench.sh run --nodes=3 --scenario=E1 --rate=200 --distribution=zipf
test/benchmarks/harness/bench.sh saturate --scenario=E1 --max-concurrency=256
```

`--accounts=<n>` with `--seed-concurrency=<n>` sizes the data set; seeding opens the accounts over HTTP, about 3,000 a second at a concurrency of 128 on a laptop. A creation that fails may have committed all the same, so up to three rounds, each failed account is read and opened again only when it does not exist; the seed fails only for accounts still missing. `--mix=E1:50,E4-state:40` runs a weighted mix of scenarios instead of one. On Linux, `--load-cpus` and `--server-cpus` pin the load generator, and the servers with the containers, to separate CPUs; `--store-cpus` and `--bus-cpus` give the store's and Kafka's containers CPUs of their own. `--install=<dir>` runs another build, for instance a baseline's `installDist` output (`<dir>` is the distribution's root, the one holding `bin/`); by default the harness runs the build in this tree. `--server-java=<JDK home>` runs the servers on another JDK, 21 or later, the load generator staying on `JAVA_HOME`'s: the runtime calibration's other arm.

For many runs on one data set, a **session** seeds and primes once:

```bash
test/benchmarks/harness/bench.sh up --backend=postgres --accounts=100000 --prime --jfr
test/benchmarks/harness/bench.sh saturate --reuse --backend=postgres --accounts=100000 --scenario=E1 --sweep
test/benchmarks/harness/bench.sh run --reuse --backend=postgres --accounts=100000 --scenario=E1 --rate=1900
test/benchmarks/harness/bench.sh down
```

`up` starts the stores and servers, seeds and primes as a run would, and leaves them up; each run with `--reuse` waits until the nodes are quiet (`load settle`), measures, and leaves them up too; `down` stops them. A reused run names the session's version, backend, nodes, accounts, heap and install, and is refused otherwise. With `up --jfr`, each reused run dumps the servers' recordings over its warm-up and measured phase (and on PostgreSQL resets `pg_stat_statements` before it). `saturate --sweep` runs every concurrency up to `--max-concurrency` instead of stopping at the knee. Runs on one session share the data the previous runs wrote, so each run's aggregates are further along than on a fresh seed; compare runs of one session with each other. The [local baseline](https://github.com/Ahoo-Wang/Wow/blob/1357642891a5a458bdb8fc7adc364af7bcb8ee21/test/benchmarks/results/reports/v10-local-baseline.md), now out of the tree, was made this way.

An ABAB compares two builds (or two configurations) on one machine: fresh sessions in the order A B B A per backend, each with its own `--install` (or `SPRING_APPLICATION_JSON`), every session's phases written to `<root>/<round>-<arm>-<backend>/<phase>` (a heap histogram beside a phase, `<phase>.hist` from `jcmd GC.class_histogram`, counts the cached states). `bench.sh compare <root>` then prints each backend's and phase's numbers by arm and round, and each arm's ratio to the first from the medians of its rounds. A sweep is most of a session's time: `--growth=4` steps the concurrency 1, 4, 16, 64, 256, 1024, six steps where doubling takes eleven. On Docker Desktop the disk image's fsyncs stall for up to seconds, which a run's tails then measure instead of Wow: `--tmpfs` puts the stores' data in memory for an ABAB that compares two arms' costs, while a baseline keeps the disk. `--mongo-cache-gb` sets MongoDB's WiredTiger cache (2 GB unless set). The stores run with a deployment's settings: PostgreSQL's checkpoints by time (`max_wal_size=8GB`, `checkpoint_timeout=15min`, `wal_compression=lz4`; `synchronous_commit` and `full_page_writes` on), MongoDB's cache sized to hold the indexes and the hot documents.

A run writes `result.json` (load, results, histogram, resources, machine, commit, JVM and configuration) and `summary.md` beside the servers' logs to `test/benchmarks/results/e2e/<time>-<label>-<version>-<backend>-n<nodes>-<scenario>/`, which git ignores; a report copies the results it cites into `results/reports/`. Ports: public 18080 to 18082, V10 internal 19090 to 19092, MongoDB 27017, PostgreSQL 5432, Kafka 9092.

On one machine every service, store and the load generator share the CPU: results are directional, and the report says so (D224).

## The industry comparison

Besides itself, V10 is compared once before GA with Axon Framework 4 on PostgreSQL (user 2026-10-25): one node, E1 and E3, the same load generator and harness. The first round, on an Apple M4, an M4 Pro and an M5 Max, left the tree with [`v10-vs-axon.md`](https://github.com/Ahoo-Wang/Wow/blob/1357642891a5a458bdb8fc7adc364af7bcb8ee21/test/benchmarks/results/reports/v10-vs-axon.md); before GA the comparison is measured again on the M5 Max and on GitHub Actions. `bench.sh --install=test/benchmarks/axon-server/build/install/axon-server` runs the Axon server instead of Wow's; `--server-args="--wow.transport=none"` runs Wow with no topics, as the Axon server has no bus. A blank `--wow.kafka.bootstrap-servers=` is not the same: the benchmark node's internal port is on loopback, so it counts as development and falls back to topics in its JVM, which a long run fills (X-33). The Axon server reads `Wow-Wait` headers not at all: each route waits for its scenario's completion point (E1 the command's unit of work committed, E3 the target's entry committed after the transfer's tracking processor handled `Prepared`).

**Why Axon Framework 4 and not 5.** The latest Axon Framework is 5.4.1 ([Maven Central](https://repo1.maven.org/maven2/org/axonframework/axon-framework-bom/), 2026-10-21). The comparison holds both servers to one PostgreSQL and to open-source modules, without Axon Server, and on those terms Axon 5 can run only in a configuration its documentation does not recommend:

- Axon 5 has no JDBC event storage engine. On PostgreSQL its open-source modules offer `AggregateBasedJpaEventStorageEngine`, which needs JPA and stores events by aggregate and sequence number, without DCB ([event store](https://docs.axoniq.io/axon-framework-reference/5.4/events/infrastructure/)).
- That engine takes its global index from a database sequence whose allocation size must stay 1, so every event appended takes a call to it, and events that become visible out of order leave gaps the processors revisit at a cost ([relational databases](https://docs.axoniq.io/axon-framework-reference/5.4/tuning/rdbms-tuning/)).
- The 5.4 reference says caching is not yet available in Axon Framework 5 ([caching](https://docs.axoniq.io/axon-framework-reference/5.4/caching/)), and the only snapshot store of the open-source modules is `InMemorySnapshotStore`, for testing or ephemeral use ([snapshots](https://docs.axoniq.io/axon-framework-reference/5.4/snapshotting/)).
- `PostgresqlEventStorageEngine` (DCB, on PostgreSQL), the persistent snapshot stores and the Axon Server connector are in Axoniq Framework (`io.axoniq.framework`), which needs a commercial license in production ([modules](https://docs.axoniq.io/axon-framework-reference/5.4/modules/)).

So an Axon 5 measured on these terms would run with no cache, snapshots in memory and a call to a sequence per event: not Axon 5 at its best, and unfair to it. Axon 4 stores its events in PostgreSQL through its JDBC engine, with the strong-reference cache below, the closest match on one store and the line most of Axon's users run. The server takes the latest 4.x BOM, `axon-bom` 4.13.3, whose framework modules are 4.13.2, the latest of them ([Maven Central](https://repo1.maven.org/maven2/org/axonframework/axon-bom/4.13.3/axon-bom-4.13.3.pom)). The comparison is to be looked at again when Axon 5's open-source modules have a JDBC or PostgreSQL engine, or an entity cache. Axon 5 with Axon Server, a dedicated event store, is another deployment, not measured before GA.

One difference stays: Axon Framework 4 runs on Spring Boot 3, so the Axon server is on Spring Boot 3.5.16, and Wow on 4.1.2. Both serve HTTP with WebFlux on Reactor Netty, but their Spring, Reactor and Netty versions differ.

**Axon's side of the comparison** (`axon-server/`, as Axon's reference guide configures production):

- The account repository caches every account with strong references (`BoundedCache`, 131,072 entries), as Wow's state cache holds its states. It is a `ConcurrentHashMap`, so a read takes no lock, which would bottleneck thousands of concurrent commands; past its capacity the entries put first leave first, which the data set never reaches. Axon's `WeakReferenceCache` loses its entries at every collection and so rarely hits. Axon's own strong-reference caches adapt EhCache or JCache, both third-party libraries, so the module has its own, with unit tests of Axon's cache contract.
- An account is snapshotted every 100 events, on two threads of the snapshotter's own (`snapshotter-1`, `snapshotter-2`), not on the thread whose commit triggered it. The node logs an `axon-stats` line every 10 s: the cache's entries, hits and misses, the snapshots and the threads they ran on, the connection pool's connections in use and idle and the threads waiting for one, the commands in flight, those whose request already timed out included, and the commands queued for a thread.
- E1 and `open-account` answer `504 timeout` after 10 s, as E3 does and as Wow answers a wait that timed out; the command goes on.
- The routes send their commands from 200 platform threads (`CommandSenders`, as many as Tomcat's default `server.tomcat.threads.max`; `benchmark.axon.command-threads` sets them), past which commands queue. Not from virtual threads: a pool of platform threads is how Axon 4's blocking API is deployed, and it stays on JDK 25 (D393), where [JEP 491](https://openjdk.org/jeps/491) no longer pins a virtual thread that blocks inside `synchronized`. On JDK 21, where these runs began, such a thread pins its carrier, and Axon 4.13 blocks there at the end of every handler, whose timeout it cancels under a monitor on the lock of its janitor's one queue (`AxonTimeLimitedTask.complete`). On a runner the server has two CPUs, so two carriers; with virtual threads the diagnostics `axon-diag` saw E3 stop for good in the middle of a sweep: a command's thread parked on its carrier in `AxonTimeLimitedTask.complete`, no new command started, and the connections stood idle.
- The transfer's reactions run in a tracking processor of 16 segments with a thread each (`benchmark.axon.segments` sets them). Each reaction waits on a PostgreSQL round trip, so the processor is sized by the parallelism its reactions need, not by the node's CPUs. The suite `axon-pg-segments` measures 16 against 2, the server's CPUs, on a runner ([run 41619207524](https://github.com/Ahoo-Wang/Wow/actions/runs/41619207524)): 16 reach 12–17% more at E3's peak and 16–24% more at its sustainable rate, beyond the A/A spreads of 4.5% and 3.9%; E1, which runs no reaction, is level. 2 cost less per command at 300/s, 1.98 against 2.52–2.61 ms of the node's CPU and 196 against 263–265 KB allocated, but cap E3's throughput. The comparison's same-rate costs are therefore Axon's at 16; at 2 they would be about a fifth lower in CPU and a quarter lower in allocation.
- A transfer reaction that fails (a lock or a connection that timed out, a handler interrupted at Axon's timeout) is retried: the transfer group's error handler is `PropagatingErrorHandler`, so the processor rolls the event's unit of work back and retries it after a pause. Axon's default, `LoggingErrorHandler`, logs the failure and skips the event, which leaves the transfer half done.

## Running it on GitHub Actions

The timed measurements need a machine to themselves for hours, so `.github/workflows/bench.yml` (Bench) runs them on GitHub's runners. The benchmark serves four purposes: it guards V10 against regressions (the head against a V10 baseline), gives capacity guidance (the sustainable rate of each scenario), tests behaviour under overload and through a hand-over, and finds defects, because every run is checked for anomalies.

A run starts when a branch under `bench-run/` is pushed. The head is the pushed commit:

```bash
git push origin v10:bench-run/20261020
```

Runs follow D224's tiers: run the smallest one that answers the question. There is no L0: the JMH microbenchmarks left with 9.x (D262). The tiers are:

- **L1**: component counts, `component-mongo` and `component-pg`, at 1k. They take the head against the baseline when there is one.
- **L2** (the default): end-to-end points, head against baseline. They are `e1-mongo-uniform`, `e1-pg-uniform`, `e3-mongo` and `e3-pg`.
- **L3**: the end-to-end grid, every `ab` suite, run before an rc or after a major merge.
- **L4**: the special runs: the sustainable rates, cliffs, the cluster, and `cold-*` at a million accounts.

Named `suites` replace the tier's list. Each suite runs at the tier's data sets:

- `1k` accounts, which fit every cache (hot);
- `100k`, the default from L2 up;
- `1M`, cold.

L3 runs its grid at 1k and 100k; `dataset` replaces the tier's sets.

From 100k accounts up, every run is **primed** (`bench.sh --prime`, D224 note ⑤): before its warm-up, an untimed closed-loop pass touches each seeded account once with a deposit, whose snapshot write also warms the pages the reads hit. Otherwise the measured window would still be filling the caches, because at uniform keys and a few hundred operations a second a warm-up touches only a small share of the aggregates. The prime runs at full speed and leaves the nodes a backlog, which a short warm-up does not absorb on a 4-core runner, so the run then waits until every node has used less than a quarter of a core for 3 seconds in a row, at most 180 s (`load settle`, `settle.json`). The report records whether each suite was primed, how long priming took and how long the nodes took to settle. The cold suites are never primed, and the report labels them cold. Above what the node's state cache holds (by default a tenth of the heap in bytes, `wow.state-cache`), the steady state is a full cache with evictions, which priming reaches too; the report says so. If a primed run still trips the stability check, that is a finding. The other defaults are 30 s warm-up (at least 30 s from L2 up, D224 note ⑤), 40 s measured, 2 rounds, 80% of saturation before calibration, and a p99 limit of 200 ms for the sustainable rates. The baseline is the newest `v10.*` release tag that has the benchmark server (`test/benchmarks/server/`, or `wow-benchmarks/e2e/bench-v10/` before the move); without one, and without `base_ref`, the baseline suites are skipped and the report says so. To change any of this, commit `test/benchmarks/bench-run.json` on the run branch:

```json
{ "tier": "L4", "base_ref": "v10.0.0-beta.1", "p99_limit_ms": 500 }
```

The keys are `tier`, `suites`, `dataset`, `aa`, `profile`, `warm_up`, `measure`, `repeats`, `fraction`, `p99_limit_ms`, `properties` and `base_ref`. `suites` takes suite names and the group names below (`all` is every group). `properties`, a JSON object of server properties, goes to the last arm of every paired suite: the head, or with `"aa": true` the second of the two head arms, so an A/A run with properties measures the head's defaults against the changed head on one runner (a probe; its ratios are not written to `noise.json`):

```json
{ "suites": ["e1-pg-uniform"], "aa": true, "properties": { "wow.snapshot.maintenance-interval": "PT10S" } }
```

When the run has finished, delete the branch; its results stay with the run:

```bash
git push origin --delete bench-run/20261020
```

The workflow can also be dispatched by hand, with the same settings as inputs plus `head_ref`, once a copy of the file is on the default branch: GitHub only dispatches workflows that are there. Two runs of one ref queue; runs of different refs run side by side.

Each suite runs in a job of its own; `.github/scripts/bench.mjs` drives `bench.sh`, and the baseline's server is passed as `--install`. A baseline from before the move to `test/benchmarks/` builds from its own layout (`:e2e-bench-v10`).

A paired suite first finds each arm's saturation in closed loop: 3 s warm-up, 8 s steps, concurrency doubling up to 2,048, the open loop's in-flight ceiling per target, so a saturation is never found where the open loop cannot follow (`.github/scripts/bench-calibration.mjs`). A saturation found at the cap is a lower bound, marked `≥`. When the two arms' saturations differ more than 3×, the lower is searched once more, since a search can stop early on a stalled step; the second search stands, and the report shows the first beside it.

The closed loop reaches its best throughput only with deep queues, so before measuring, each arm's rate is checked in open loop. A probe runs at `fraction` of the saturation (10 s warm-up, 30 s measured: as long as a round's warm-up, so a queue a round builds in that time shows in the probe) and steps down by a quarter, at most 4 probes, while more than 1% fails, less than 97% of the rate completes, or the rate times the probe's p99 (by Little's law, what it holds in flight) needs more than half its in-flight cap.

The arms then run alternately at their calibrated rates, plus one more round when two runs of an arm differ by more than 5% in throughput or p99. In an open loop the throughput is the offered rate whenever the node keeps up, so these calibrated rounds say whether each arm kept up with its own rate, not which arm is faster; their CPU and latencies are at unequal loads. When the arms ran at different shares of their saturations (a probe stepped down), the report says so. The same number of equal-rate rounds follows, with both arms at the lower calibrated rate, and the latency and cost ratios come from those.

Every comparison is a pair measured on the same runner, so the ratios hold across runners; the absolute numbers belong to that runner. A run's server properties reach the servers as `SPRING_APPLICATION_JSON`, which they inherit from `bench.sh`'s environment.

Every run sets `bench.signals.enabled=true`. With it, the benchmark server's `BenchSignals` observer (`server/.../BenchSignals.kt`) logs the node's cumulative overload and fallback counts once a second, as `bench-signals {json}` in the node log. It counts the tails' store reads by reason, refused commands by code, timed-out waits by stage, dropped signals, failed forwards, paused and resumed partitions, a subscription's retries on a downstream's push-back (by subscription and by code), its partitions throttled and unthrottled, the shared states rebuilt with the replay gate's summed wait, and the stores' fallbacks by capability and reason (`storeFellBack`, `snapshot-load/failed` or `snapshot-load/timed-out`). With it, `BenchQueryLimits` logs each store's query bound once a second, as `bench-query-limits {json}`, as the node's health says it (the `wow` contributor's `queries` component, which `/actuator/health/wow` shows an operator): the bound and its ceiling, the queries running and queued, and for an adaptive bound whether its write pressure pressed, how often it was lowered and the pressure it read. A read the store's bulkhead refused is answered 429 `wow.query.busy`; the report counts these in a column of their own, `wow.query.busy (bulkhead)`, beside each store's bound over the measured phase, so they read as the bulkhead at its bound, lowered by the adaptation or not, and never as a silent error count.

With `bench.pipeline.enabled=true`, which no suite sets (`bench.sh --server-args="--bench.pipeline.enabled=true"` asks for it), `BenchPipeline` (`server/.../BenchPipeline.kt`) logs the saga pipeline once a second, as `bench-pipeline {json}`: where a command's chain queues between one commit and the next, which the executor's in-flight count does not see. It has the shape of the other two lines, `{"t": <seconds>, "<section>": {"<field>": <number>, …}, …}`, and its sections are: `appendDepth` (now: the appends not yet in a batch, and the lanes' groups and streams handed to the two committers and not yet taken into a call); `appendCalls` (cumulative: the calls to the log, their streams, and the calls full at `mergeMax`, so streams over calls between two lines is that second's mean call); `handoff` (cumulative: the entries the tails delivered from memory, and their store reads); and `window` and `windowMax` (now, per subscription: the entries its workers took above their watermarks, summed over the partitions and the largest one partition's, against `wow.subscription.max-in-flight`). Its reads take no lock on a command's or an entry's path, and the append queue counts its calls only once the line reads them: off, the node counts none of it. On, it costs at most two atomic adds per handed group and per taken group, three per call to the log, and once a second a walk of each subscription's workers; a run recorded with it is therefore not compared with one without. The report does not read this line yet; a measurement that needs it reads the node log.

p99.9 is reported only when a run has at least 1000 samples beyond it (a million operations); otherwise it shows `n/a`.

The report counts what these lines grew by over each run's measured phase, summed over the nodes (a restarted node's log included): a node's counts are cumulative from its start, so its last line alone also holds the seeding and priming, which run flat out. A failed run, which has no measured phase, shows each node's last line. It flags these anomalies:

- a partition paused (D243);
- a tail read the store after a gap or an overflow (D249);
- a store call given up at its timeout: a snapshot load past `wow.snapshot.load-timeout`, its state replayed from the log (`storeFellBack` in `bench-signals`, `snapshot-load/timed-out`), so the run is no capacity figure;
- more than 1% errors;
- a measured second below half the rate;
- p99 above 10× p50, when p99 is at least 50 ms;
- the head allocating more than 5% more bytes per operation than the baseline, in the median of the equal-rate pairs (bytes per operation fall as the rate rises, since a node's background allocation is spread over more operations).

Two more anomalies are flagged:

- **Unstable:** the measured phase's halves differ in mean throughput or in median per-second p50 by more than the suite's A/A noise (from `noise.json`; without it 5% and 25%). p99 is compared too, against its A/A noise (default 50%), but only when each half has at least 1000 samples beyond it; with fewer, half a run's tail is noise, and a stable system would trip the check.
- **Load generator saturated:** the generator used 90% of its CPUs, so the run measured the generator rather than the servers.

Where a run went past what the node keeps up with by design (probes, cliff steps that did not keep up), only the signals are flagged.

On a runner of 4 or more CPUs, the load generator gets CPUs to itself, the last ones, and the servers and containers get the others (`bench.sh --load-cpus`, `--server-cpus`; D224 note ③). A paired PostgreSQL suite gives it the last two: on one core it reached 0.91–0.98 of it before the servers saturated, so those suites measured the generator. A paired MongoDB suite gives the generator, Kafka, mongod and the node one CPU each (`--bus-cpus`, `--store-cpus`): sharing two, the node, mongod and Kafka used all of them, so a ratio measured whichever took the CPU first, while the generator, its samplers counted, used at most 0.78 of a core. The other suites give the generator the last CPU. A paired suite gives both arms the same layout, so its ratios compare; the suite records it (`cpus`), and the report's runners table shows it. Their absolute numbers from before the layout (2026-10-27 for the PostgreSQL suites, 2026-10-28 twice for the MongoDB ones: the L3/L4 RC report, the M4 Pro snapshots) came from another server layout and do not compare with later ones. The run then records the load generator's CPU, that of its whole process tree (the `jstat` and `docker` samplers it starts run on its CPUs too), and names the busiest consumer, the servers, a container or the generator, as the bottleneck. An open-loop run keeps at most rate × request timeout operations in flight, and at most 2,048 per target: one past that is not sent but counted as `generator-overload`, so an overloaded server shows as overload or 429 rather than as connections it refuses. A run whose generator refused more than 1% of its operations is flagged `generator-bound`, not as the node's errors, and its seconds are left out of the confidence intervals. The run's `load.inFlightCap` and `load.inFlightBoundBy` record the cap and which bound set it.

The closed-loop saturation records the generator's cores at its saturation step too. When the generator used 90% of its CPUs there, or in a run of either arm at the calibrated rates, the report shows `invalid: generator-bound` instead of the saturation ratio, the calibrated pairs and the kept-up verdict: what they measured is the generator.

With `"profile": true`, every paired suite adds one more run per arm after its timed rounds, never inside them (D224 note ⑧). This run takes a flight recording (`--jfr`, settings `profile`) at the rate the latencies compare at. The recording uses the JDK's `profile` settings plus safepoint events, and socket reads, writes and thread parks from 1 ms (`jfr configure`, passed as `bench.sh --jfr-settings`). The summary shows the first lines of `jfr view` hot-methods, allocation-by-class, contention-by-site, gc-pauses, safepoints, latencies-by-type and socket-reads-by-host, so a tail can be attributed to GC pauses, safepoints, store latency or lock and pool waits. On PostgreSQL the profile run also loads `pg_stat_statements` and dumps the top statements, the checkpoints and the waits after the run (`postgres-stats.txt`). The run's directory keeps the full views and the recordings.

Significance (D224 note ②) works in two steps:

1. An A/A run (`"aa": true`) measures the head against itself in the baseline suites, with at least 4 equal-rate rounds. For each metric (throughput, p50, p99), the half-width of the 95% bootstrap interval of its A/A ratio, at least 2%, becomes the suite's noise threshold. The report writes these thresholds as `noise.json`; committed as `test/benchmarks/noise.json`, they apply to later runs.
2. The report's Significance table gives p50 and p99 at the equal rate a 95% bootstrap interval over the measured seconds. A latency's point estimate is the median of the rounds' own percentiles, each from the run's whole histogram. A ratio counts as higher or lower only when its interval clears the threshold; without a threshold it is marked `uncalibrated`. Throughput is given as the closed-loop saturation ratio, a measurement without an interval (`~` and a lower bound when a search reached the cap), and beside it whether each arm completed at least 97% of its own calibrated rate; neither is counted beyond noise. Each job uploads its results, server logs and summary, and the report job combines them into `report.md`, anomalies first.
