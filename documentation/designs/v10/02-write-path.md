# V10 写平面

日期：2026-10-11。基线：`main` `b5813af56f`。状态：草案。上位文档：[00 目标架构](00-architecture.md)（A1、A6）。相关决定：D6、D15、D24、D26、D133、D135、D137、D143。

## 1. 命令生命周期

1. **准入**（`CommandGateway`，D92）：解析命令类型 → 身份解析（每个事实只有一条规则，来源冲突即拒绝）→ 动作级授权 → 解码 → 改写（不得改身份）→ 校验 → 构造不可变的 `Command`；已有聚合的作用域由内核守卫（D94）。等待计划是 `Command` 的类型化字段；**默认等待 `SNAPSHOT`**（D69）：命令返回时快照已写到这次提交的版本，调用方紧接着查询就能读到自己的写入。
2. **路由**（`Router`）：决定由哪个节点执行（§2）。
3. **执行**（`Executor`）：每个有在途命令的 `AggregateRef` 一条车道，按到达顺序逐条执行，车道之间互不阻塞（decide 挂起在 I/O 上只占住自己的聚合）；车道有排队上限，满了直接拒绝；停机时立即拒绝新命令，并等在途命令完成。状态缓存（`StateCache`）每次把状态取出给一次尝试，只在提交成功或未演化时放回：可变状态（D7）演化时改的是缓存里的同一个对象，没有提交的尝试必须让它作废。
4. **去重先于决定**（D46）：Decide 可以做 I/O，重复的请求不能再跑一遍有副作用的 decide。L2 按 `(tenant, requestId)` 唯一索引查存在性，命中即返回「已处理」，不再决定。L1 是进程内轮转布隆过滤器，「没见过」时跳过 L2；但它的「没有假阴性」只在本进程、本轮转窗口内成立，进程重启、属主切换、窗口轮转之后都会漏。所以 L1 只用于**纯计算的 decide**（同步、无 `DecideScope` 依赖，KSP 编译期可知，D36）：它即使被重复执行也无副作用，重复由追加时的唯一键兜住。**有 I/O 的 decide 每次都走 L2**。去重在冲突重试循环之外只做一次。日志条目记录命令指纹（命令类型 + 请求体哈希）：同一请求 ID 携带不同命令时拒绝，而不是把别的命令的结果当成本次结果。
5. **内核**：取状态（缓存 → 快照加尾部 → 初始状态）→ 守卫 → decide（命令函数，再接 after 钩子，D39）→ evolve → 追加。版本冲突时驱逐缓存、重新加载、重新决定；结局未知时按版本槽查明（沿用 9.3 已证明正确的版本槽判定）。**追加成功之后是不可撤销区**：调用方取消、HTTP 断开都不能中断其后的缓存更新、版本视图与信号（KaeX 运行时规格的 `NonCancellable` 约束）。版本视图是多读者的（D133）：凡有状态消费者（快照、Sink、订阅）的类型都记进共享缓存，消费者读不到时退回 `Kernel.stateAt`。
6. **信号**：追加成功后通知发起节点；本地执行是进程内调用，转发执行经集群通道回传。

**准入的落地**（实现说明）：

- **命令转换**（D182，#4388）：只有准入网关做转换，Kafka 命令入口与 Saga 不做；转换器运行过就在命令上记 `transformedFrom`，事件流 headers 写 `wow.transformed-from`、`wow.transformed-from-id`；目标本身是挂载命令（链式）即 `wow.command.unhandled`；无 ID 的输入按 `ref.id = "(none)"` 授权。
- **创建命令的 ID**（D171、D191，#4408）：命令不带 ID 时，准入先按（类型，租户，请求 ID）查已提交的事件流，同一作用域的调用方复用原 ID，否则由目标聚合配置的生成器取号；Saga 派生的创建命令同样处理。
- **归属**（D189，#4408）：`@AggregateRoot(ownership)` 写进 Manifest；`OWNER` 聚合记录并校验调用方的全部作用域，`TENANT` 聚合只记录与校验空间；派生命令不对已存在的目标做作用域检查（D199）。

**派生命令的作用域**（D189、D199）：Saga 派生、补偿与定时触发的命令继承根命令的作用域与操作人；继承的作用域只决定新建聚合的归属并用于审计，内核不对已存在的目标做调用方作用域检查，授权在根命令准入时已完成。

9.x 的证据：同一身份在四五处决定（9.3 重构的诊断 D1、命令链路 B20）；`Command-Header-*` 冒充操作人（B1）；门面绕过 `enabled=false`（B2）。

## 2. 路由

拆开 9.x「每条命令经过命令总线」的两个理由：

- **单写者不是正确性前提**：版本唯一键保证正确，并发写者只会冲突后重新决定。
- **单写者是性能前提**：随机负载均衡下，状态缓存命中率约 1/N，每条命令多两次存储读，热点聚合频繁冲突；一次集群内转发（约 1 ms）比两次存储读便宜。
- **持久摄入只对异步命令有意义**：同步调用方等待 `COMMITTED`，失败带同一请求 ID 重试；Saga 的检查点在派生命令提交前不前进。

| Router | 做法 | 适用 |
|---|---|---|
| `Partitioned`（默认，D6，H2 已验证） | 按 `AggregateRef` 的哈希找到日志分区属主；本节点是属主就本地执行，否则经集群通道转发。属主与订阅共用同一套分区租约 | 多节点部署 |
| `Local` | 收到即执行，乐观并发 | 单节点；交接与属主不可达时降级（D71） |
| `Kafka` | 写入按聚合分区的命令主题 `wow.<ctx>.commands`（分区数等于日志的 P，生产者用日志的 `Partitioner`，D135），由日志分区属主消费，无需转发；按聚合类型配置 `wow.aggregates.<ctx.agg>.routing: kafka`，`accepted` 即持久、回 202（D143） | 需要持久摄入的异步命令；削峰 |

`ACCEPTED` 只表示通过准入，**不表示持久**；只有经 `Kafka` 路由时才表示不会丢失（D15）。

**跨上下文的命令**（D33）：发往另一个限界上下文的命令（典型是 Saga），由目标上下文的服务执行，发送方不在它的集群通道里。所以跨上下文命令一律写入目标上下文的命令主题，发送方等到持久 `ACCEPTED` 即完成：Saga 的 `SagaContext.command` 指向本服务不承载的上下文时，broker 确认即这一跳完成（D137）。目标的命令入口按请求 ID 在内核去重、按信封里的 `WaitContext` 执行，结局定了才推进检查点；执行时的技术故障停放 `wow.commands` 订阅、记入目标上下文的失败台账；业务拒绝作为回执发回发起方（D47、D136，[04](04-subscriptions.md) §5），而不是让发送方等待。线上类型名取自对端 Manifest（D139）。

## 3. 集群通道

同一个服务（一个部署单元）的节点之间唯一的内部通信（D24），不跨服务；承载：

- 命令转发（§2）；
- 本服务内的等待信号（例如属主节点执行转发来的命令后，把结果回传给发起节点）；跨服务的信号直接发往发起节点，不经集群通道（D65，[04](04-subscriptions.md) §6.3）；
- 新条目推送：提交节点把新条目推给本服务的尾随读，免去轮询延迟。

成员关系与分区属主来自存储上的租约，不依赖 ZooKeeper、Kafka 消费组或注册中心。

**分区分配与再平衡**（D70～D72）：

- **HRW，无主对账**（D70）：每个节点从同一份成员列表算出同一个目标分配，owner(p) = argmax hash(节点, p)（最高随机权重哈希）。对账循环每秒一次、成员变化时立即触发：目标里不再归自己的分区就交出，归自己的就 acquire。不选主；成员变化只移动约 P/N 个分区；成员视图短暂不一致时，租约本身仲裁，下一轮收敛。
- **主动交接**（扩容、滚动升级、优雅停机）：旧属主停止接收该分区的新命令 → 有时限地执行完在途命令 → 保存订阅检查点 → 释放租约；新属主在下一轮对账 acquire。状态缓存不交接，新属主靠快照加尾部冷启动。
- **交接与故障期间命令降级为 Local，不等待**（D71）：转发确定未送达（连接失败、`NOT_OWNER` 或 `EXPIRED` 拒绝、在途已满）或属主未知时，收到命令的节点在本地执行；请求已发出后的超时不降级（D223）。正确性由版本唯一键保证（单写者是性能前提，不是正确性前提），代价是少量冲突重试，MongoDB 在秒级窗口内有短暂争用（D52）。命令的可用性因此不依赖租约 TTL；属主崩溃时只有该分区的订阅暂停到租约过期。
- **参数**：租约 TTL 10 秒、每 3 秒续约；成员心跳 TTL 10 秒；对账每秒一次。要求节点间时钟偏差远小于 TTL（D53）。
- **租约组与地址**（D72）：租约组是（服务，上下文）；`Member` 带节点的内部地址，路由表由每秒读取 `owners` 与 `members` 加转发失败时刷新维护。
- **转发**（D78）：一种同步消息，请求是命令的线上形式加绝对截止时间，响应是属主的 `CommandResult`；之后的等待信号直达发起节点（D65）。连接失败、`NOT_OWNER` 或 `EXPIRED` 拒绝、对端在途已满（默认每个对端 1024）、属主未知都降级 Local，不重试转发。**请求已发出后超时不降级**（D223，修订 D80）：属主可能还在 decide，降级会让同一请求在两个节点各 decide 一次，有 I/O 的 decide 重复执行（违背 D46）；发起节点返回超时（结果不确定），调用方用同一请求 ID 重试，属主已提交的得到 `duplicate` 与原结果。超时默认 1 秒且不超过命令剩余的截止时间（D80）。
- **实现要点**（Ahoo-Wang/Wow#4251）：HRW 的权重是 `fmix64(FNV-1a-64("节点/分区"))`，与日志分区共用同一个稳定哈希，按无符号比较、平局取节点 ID 小者；租约组名为 `服务/上下文`；成员心跳每 3 秒；租约的属主不是存活成员时视为属主未知（降级 Local）；属主只接收自己持有、或在 HRW 目标里尚未取得的分区的转发命令，收到的转发不再转发；正在交出的旧属主把新命令转给 HRW 的下一个属主；续约失败时本地停止该分区，不释放租约。
- **真实传输**（D89）：宿主在独立的内部端口上起 h2c 服务承载集群通道与信号入口，公开 REST 仍走主端口；客户端用 JDK `HttpClient`。
- **实施顺序**（D77）：先做与传输无关的部分（端口、对账、交接、降级、进程内回环传输），宿主提供 HTTP/2 栈后再接真实传输。
- **僵尸属主**：停顿超过 TTL 后醒来的旧属主会重复处理订阅，D45 已接受（确定性 ID 幂等）；命令由版本唯一键兜住。
- **热点分区**：HRW 平衡分区数而非负载，暂不处理，由 H6 的数据决定是否需要固定或加权。不做认证：集群内部流量受信任，且只监听不对外暴露的内部端口（部署前提见 [00](00-architecture.md) §1，D35）；内部协议，但**同一主版本内相邻的次版本必须能混部**（D48）：10.x 的日常升级是滚动升级，升级过程中新旧节点共用集群通道、日志、租约与等待信号；只有跨主版本（9 → 10、10 → 11）才用蓝绿切换。协议选型见 D26。
