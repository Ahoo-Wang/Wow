# Wow 10 安全性：GA 前的统一讨论

日期：2026-10-26。基线：`origin/main` `c403da4e4`。状态：**已采纳**（2026-10-26；用户 2026-10-26 要求把 T4 与「只允许信号」的服务身份放在一次安全讨论里定；同日定下基本原则 D295：公开 API 前置安全网关，§2.1；D298：服务内部是受信环境，§2.2；D299：低维护成本，§2.3）。结论为 D295～D302，工作包是路线图 9.3d 的 S.1～S.3，发现登记在[审查台账](reviews.md) §8。

上位文档：[00 目标架构](00-architecture.md)、[R5 设计](2026-10-26-r5-ga-architecture-review-design.md)、[决策台账](decisions.md)（D35、D97、D173、D175、D208、D226、D232、D236、D237、D254 ⑦、D267 ⑯）。

## 1. 为什么现在讨论

GA 后，安全默认值的收紧就是行为变更：已经上线的部署升级后会被拒绝启动或拒绝请求。日志又是不可删除的（D175），写进去的个人数据收不回来。所以凡是「默认放开」「默认记录」的地方，都要在 GA 前定对；只是**增加**能力（如原生 TLS、信封签名）的，可以留到 10.x，因为它们是加法。

## 2. 第一性原理：资产、参与者与边界

**资产**：① 改变状态的权力（谁能发哪条命令）；② 租户隔离的读；③ 日志本身（不可变的事实，法律意义上的记录）；④ 集群与服务凭据；⑤ 日志里的个人数据。

**参与者**：终端用户（公开端口）、被信任的服务（`Wow-Call`，D208）、本服务的节点（集群令牌，D226）、运维人员（ops 服务与控制台）、能触到内部端口、Kafka 或数据库网络的任何人。

**边界与现状**（按代码梳理，2026-10-26）：

| 边界 | 认证 | 授权 | 现状要点 |
| --- | --- | --- | --- |
| B1 公开端口 | `CallerResolver`；没有 bean 时为匿名调用方（只告警一次） | `CommandAuthorizer`，默认 `ALLOW_ALL`；CoSec 的授权器默认关 | 读侧作用域、跨租户（默认关）、遮罩都已就位；`Wow-Call` 在公开端口一律 403 |
| B2 内部端口 | 集群令牌（≥ 32 字符，摘要恒时比较）；服务令牌或 CoSec 服务主体 | `wow.http.services.<svc>.commands`/`reads`：不列即全部领域命令、全部模型 | 明文 HTTP/h2c，没有 TLS 选项；无令牌在非开发 profile、非回环时拒绝启动 |
| B3 Kafka 主题 | 无（Kafka 自己的 SASL/ACL） | 摄入不做授权（`wow.ledger.*` 按来源上下文） | 能写 `wow.<ctx>.commands` 的人可伪造任意操作人、租户、作用域；信封里的等待来源决定节点把信号与凭据发往哪里 |
| B4 存储 | 应用自己的 DataSource/MongoClient | — | 框架不持有数据库凭据（ClickHouse 除外） |
| B5 平台服务 | CoSec JWT（HMAC256 共享密钥）或 `trust-identity-headers` | 服务自己的角色 | 头部身份开关一项配置就能完全冒充身份，没有回环或 profile 守卫 |

**由此推出的原则**（本文用来评判每一项）：

| 编号 | 原则 |
| --- | --- |
| P1 | **生产默认关闭**：放开必须显式；开发便利只靠开发 profile 或回环（与集群令牌的规则一致，R3.5-1） |
| P2 | **最小权限**：没写的就是没有，「全部」要显式写 `*` |
| P3 | **不可删除的日志只收必要数据**：框架默认不往日志写个人数据（D175 的推论） |
| P4 | **凭据只发给已知的对端**：地址来自配置或成员表，不来自消息内容 |
| P5 | **不认证的传输是信任边界**：要么在文档和启动检查里写成硬要求，要么加认证 |
| P6 | **安全开关拼错即失败**：安全与隐私相关的键不能静默退回默认值 |

### 2.1 基本原则：公开 API 前置安全网关（D295，用户 2026-10-26）

Wow 服务的公开端口不直接面对终端用户，前面总有一个安全网关。由此划分职责：

| 关注点 | 安全网关 | Wow 服务 |
| --- | --- | --- |
| 终端用户的认证（令牌、会话、登录） | 负责 | 不负责；把网关断言的身份映射成 `Caller`（租户、主体、空间、作用域） |
| 粗粒度授权（路径与方法、角色）、限流、CORS、对外 TLS | 负责 | 不重复 |
| 领域内的授权（租户隔离、所有者、空间、`Wow-Scope`、跨租户、遮罩） | 不知道领域模型，做不了 | 负责（读取门面 D237、准入、`CommandAuthorizer`） |
| 内部端口、Kafka 主题、存储 | 不经过网关 | 各自的边界（B2～B4），本原则不覆盖 |

推论：① 网关只解决「是谁」，**不解决「能对哪个租户的哪个聚合做什么」**，所以身份映射在生产中仍是必需的；② Wow 信任的是网关转发的身份，因此**「只有网关能到达公开端口」本身成了一条边界**：CoSec 的注入模式（`cosec.inject.enabled`）不校验令牌签名（`CoSecAutoConfiguration.kt:72`），绕过网关到达公开端口的请求可以冒充任何身份；③ 网关之后，连接的对端是网关，`remote_ip` 记录的是网关地址（框架不读 `X-Forwarded-For`）。

### 2.2 基本原则：服务内部是受信环境（D298，用户 2026-10-26）

内部端口、集群通道、Kafka 主题与存储所在的网络是受信环境，重申 D35、D173 的部署前提：外部客户端只经网关（D295）到达公开端口，到不了内部。

推论：① 内部的凭据（集群令牌 D226 ①、服务身份 D208）的作用是**识别与防误配**，不是抵御内网里的攻击者：集群令牌防止别的服务的节点误入本服务的集群通道，服务身份决定谁能声明根命令的租户与操作人、可调哪些命令，并留下调用来源。这些机制已经做好、代价小，保持不变；② 内部不再为「内网中有攻击者」加防御：传输加密、Kafka 信封签名、按消息内容限制凭据去向都不是 GA 的安全要求；③ 部署文档把「内部端口、Kafka、存储不对外暴露」写成硬要求，与 D296 的「公开端口只对网关可达」并列。


### 2.3 基本原则：低维护成本（D299，用户 2026-10-26）

安全措施要让使用者和框架都少维护：不新增要人保管的密钥，能不加配置键就不加，复用已有的机制（开发 profile 与回环的豁免、未知键检查、部署清单）；要求维护拓扑或成员信息的措施不做。

据此：请求事实的大小上限是固定常量，不设配置键；有意匿名的服务声明一个返回匿名调用方的 `CallerResolver` bean，不新增键；凭据去向的加固（SQ4）需要知道其他服务的节点成员，取消。


## 3. 发现

级别：P0 默认即可被利用；P1 误配或单点失守即越权、泄露凭据或留下不可删除的数据；P2 加固。

| 编号 | 级别 | 位置 | 发现 | 违反 |
| --- | --- | --- | --- | --- |
| S-1 | P0 | `WowAutoConfiguration.kt:706-718`、`:535` | 没有 `CallerResolver` bean 就以匿名调用方服务所有公开路由，授权器默认 `ALLOW_ALL`；漏掉 CoSec 依赖或 profile 时，全部命令、读、Manifest、OpenAPI 静默放开，只有一行告警 | P1 |
| S-2 | P1 | `HttpSignalSender.kt`（类注释与 `credential`） | 发往**其他服务**的信号带本服务的 `Authorization` 凭据，地址取自等待来源，而来源来自消息（含 Kafka 信封）。集群令牌已限定只发给成员（R2.3-1），服务凭据没有对应限制：能写 Kafka 的人可以把来源指向自己的地址，拿到本服务调用别的服务用的凭据 | P4 |
| S-3 | P1 | `CommandIntake.kt` | Kafka 是不认证的命令入口：能写主题即可绕过准入、授权与租户规则，伪造操作人与作用域；ops 的 `wow.ledger.*` 也只靠 ACL | P5 |
| S-4 | P1 | `RequestHeaders.facts`、`WowProperties.kt:1098`（T4） | `wow.http.client-facts` 默认 `true`，客户端 IP 与 UA 写进不可删除的日志 | P3 |
| S-5 | P1 | `CallPermits.kt`（路线图 §6「只允许信号」） | 被信任的服务不列 `commands` 即可调用全部领域命令，不列 `reads` 即可读全部模型；只想收信号的服务也拿到了全部写权 | P2 |
| S-6 | P1 | `ConfigurationKeys.kt` `STRICT_PREFIXES` | 只有 4 个前缀拼错会拒绝启动；`wow.http.client-facts`、`wow.query.cross-tenant.*`、`wow.query.abac.*`、`wow.ops.enabled` 拼错只告警，环境变量不检查 | P6 |
| S-7 | P1 | `deploy/*/secret.yaml` | 示例集群令牌 `replace-me-…-32-characters` 满足长度检查；原样部署就是公开已知的令牌 | P1 |
| S-8 | P1 | `InternalHttp.kt:91` | 内部端口只能明文：集群令牌、服务令牌与带身份的转发命令都不加密；`NetworkPolicy` 可选，部分 CNI 不执行 | P5 |
| S-9 | P2 | `OpsCallers.kt`（`wow.platform.trust-identity-headers`） | 平台服务的头部身份开关没有回环或 profile 守卫 | P1 |
| S-10 | P2 | `wow.http.request-facts` | 白名单里的请求头原样进日志，没有单条大小上限 | P3 |
| S-11 | P2 | 平台服务 | 三个平台服务共用一个 HMAC 共享密钥（`COSEC_JWT_SECRET`），泄露即处处可伪造身份 | — |
| S-12 | P2 | `CrossTenantAudit` | 跨租户查询的审计只是一行 INFO 日志，没有持久记录 | — |

保持不变、已经扎实的部分：集群令牌的长度、轮换与摘要比较；无令牌拒绝启动；`Wow-Call` 在公开端口 403；等待来源的服务校验（R2.3-1）；系统命令须显式授权；读侧作用域、跨租户默认关、遮罩在读取门面统一处理（D237）；框架不记录凭据。Saga、定时器与进程内客户端走网关而不经 WebFilter：它们是服务自己的代码，属于同一信任域，维持现状并在文档写明。

## 4. 需要你定的问题

| 编号 | 问题 | 选项 | 推荐与理由 | GA 前 |
