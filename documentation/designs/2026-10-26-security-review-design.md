# Wow 10 安全性：GA 前的统一讨论

日期：2026-10-26。基线：`origin/main` `c403da4e4`。状态：已实施（结论为 D295～D302）；本文留作威胁模型与设计依据：资产、参与者、边界、原则 P1～P6、三条基本原则（D295、D298、D299）与各问题的决定。§3 的发现 S-1～S-12（都已处理，见[审查台账](reviews.md) §8）与 §5 的分批已删（见 `2c08f318ea`），节号不变；§2 的边界表按 D300、D301、D334 之后的实现改过。

上位文档：[00 目标架构](00-architecture.md)（§9 是 R5 审查的不变式）、[决策台账](decisions.md)（D35、D97、D173、D175、D208、D226、D232、D236、D237、D254 ⑦、D267 ⑯）。

## 1. 为什么现在讨论

GA 后，安全默认值的收紧就是行为变更：已经上线的部署升级后会被拒绝启动或拒绝请求。日志又是不可删除的（D175），写进去的个人数据收不回来。所以凡是「默认放开」「默认记录」的地方，都要在 GA 前定对；只是**增加**能力（如原生 TLS、信封签名）的，可以留到 10.x，因为它们是加法。

## 2. 第一性原理：资产、参与者与边界

**资产**：① 改变状态的权力（谁能发哪条命令）；② 租户隔离的读；③ 日志本身（不可变的事实，法律意义上的记录）；④ 集群与服务凭据；⑤ 日志里的个人数据。

**参与者**：终端用户（公开端口）、被信任的服务（`Wow-Call`，D208）、本服务的节点（在请求头里声明自己的服务，D300）、运维人员（ops 服务与控制台）、能触到内部端口、Kafka 或数据库网络的任何人。

**边界**：

| 边界 | 认证 | 授权 | 要点 |
| --- | --- | --- | --- |
| B1 公开端口 | `CallerResolver`；非开发 profile、非回环时没有 bean 即拒绝启动（D301） | `CommandAuthorizer`，默认 `ALLOW_ALL`；CoSec 的授权器默认关 | 读侧作用域、跨租户（默认关）、遮罩都已就位；`Wow-Call` 在公开端口一律 403 |
| B2 内部端口 | 没有凭据：节点与服务在请求头里声明自己的服务名，边界是网络策略（D300） | `wow.callers.<service>.commands`/`reads`：不列即全部领域命令、全部模型，系统命令须显式列出 | 明文 HTTP/h2c，没有 TLS 选项（§4 SQ7） |
| B3 Kafka 主题 | 无（Kafka 自己的 SASL/ACL） | 摄入不做授权（`wow.ledger.*` 按来源上下文） | 能写 `wow.<ctx>.commands` 的人可伪造任意操作人、租户、作用域；信封里的等待来源决定节点把信号发往哪里 |
| B4 存储 | 应用自己的 DataSource/MongoClient | — | 框架不持有数据库凭据（ClickHouse 除外） |
| B5 平台服务 | 与其他服务相同（B1）：CoSec，或在网关之后信任网关注入的身份（D296） | 服务自己的角色 | ops 与分析目录对没有用户的请求答 401，view-store 保留匿名读（D334） |

**由此推出的原则**（本文用来评判每一项）：

| 编号 | 原则 |
| --- | --- |
| P1 | **生产默认关闭**：放开必须显式；开发便利只靠开发 profile 或回环 |
| P2 | **最小权限**：没写的就是没有，「全部」要显式写 `*` |
| P3 | **不可删除的日志只收必要数据**：框架默认不往日志写个人数据（D175 的推论） |
| P4 | **凭据只发给已知的对端**：地址来自配置或成员表，不来自消息内容 |
| P5 | **不认证的传输是信任边界**：要么在文档和启动检查里写成硬要求，要么加认证 |
| P6 | **安全开关拼错即失败**：安全与隐私相关的键不能静默退回默认值 |

### 2.1 基本原则：公开 API 前置安全网关（D295，用户 2026-10-26）

Wow 服务的公开端口不直接面对终端用户，前面总有一个安全网关。由此划分职责：

| 关注点 | 安全网关 | Wow 服务 |
| --- | --- | --- |
| 终端用户的认证（令牌、会话、登录） | 负责 | 不负责；把网关断言的身份映射成 `Caller`（租户、主体、空间、作用域） |
| 粗粒度授权（路径与方法、角色）、限流、CORS、对外 TLS | 负责 | 不重复 |
| 领域内的授权（租户隔离、所有者、空间、`Wow-Scope`、跨租户、遮罩） | 不知道领域模型，做不了 | 负责（读取门面 D237、准入、`CommandAuthorizer`） |
| 内部端口、Kafka 主题、存储 | 不经过网关 | 各自的边界（B2～B4），本原则不覆盖 |

推论：① 网关只解决「是谁」，**不解决「能对哪个租户的哪个聚合做什么」**，所以身份映射在生产中仍是必需的；② Wow 信任的是网关转发的身份，因此**「只有网关能到达公开端口」本身成了一条边界**：CoSec 的注入模式（网关之后的服务，`wow.cosec.mode: gateway`）不校验令牌签名，绕过网关到达公开端口的请求可以冒充任何身份（§4 SQ0）；③ 网关之后，连接的对端是网关，`remote_ip` 要从网关的转发头取（§4 SQ2）。

### 2.2 基本原则：服务内部是受信环境（D298，用户 2026-10-26）

内部端口、集群通道、Kafka 主题与存储所在的网络是受信环境，重申 D35、D173 的部署前提：外部客户端只经网关（D295）到达公开端口，到不了内部。

推论：① 内部的身份（节点与服务声明的服务名，服务身份 D208）的作用是**识别与防误配**，不是抵御内网里的攻击者：它挡住别的服务的节点误入本服务的集群通道，决定谁能声明根命令的租户与操作人、可调哪些命令，并留下调用来源。按同一条原则，集群令牌与服务令牌随后删除（D300，§4 SQ8）；② 内部不再为「内网中有攻击者」加防御：传输加密、Kafka 信封签名、按消息内容限制信号去向都不是 GA 的安全要求；③ 部署文档把「内部端口、Kafka、存储不对外暴露」写成硬要求，与 D296 的「公开端口只对网关可达」并列。

### 2.3 基本原则：低维护成本（D299，用户 2026-10-26）

安全措施要让使用者和框架都少维护：不新增要人保管的密钥，能不加配置键就不加，复用已有的机制（开发 profile 与回环的豁免、未知键检查、部署清单）；要求维护拓扑或成员信息的措施不做。

据此：请求事实的大小上限是固定常量，不设配置键；有意匿名的服务声明一个返回匿名调用方的 `CallerResolver` bean，不新增键；凭据去向的加固（SQ4）需要知道其他服务的节点成员，取消。

## 4. 问题与决定

| 编号 | 问题 | 选项 | 推荐与理由 | GA 前 |
| --- | --- | --- | --- | --- |
| SQ0 | 网关到服务的信任（推论 ②） | **已定 D296（用户，选 ②）**：信任网关，沿用 CoSec 注入模式 | 注入模式的用途就是让下游服务不配密钥也能拿到身份；服务各自校验签名会让密钥复制到每个服务，难以维护。前提「请求必须经过网关」写成部署的硬要求：公开端口只对网关可达（随附的部署清单带只放行网关的 NetworkPolicy），网关覆盖而不是追加 `X-Forwarded-For` 与身份相关的请求头。启动时无法探测网络拓扑，不加检查。若将来要纵深防御而又不复制密钥，可用非对称验签（服务只取网关的公钥，JWKS），登记为 10.x 候选（与 S-11 合并） | — |
| SQ1 | 生产环境的身份映射是否必须显式（S-1） | **已定 D301（用户按推荐）**：非开发 profile、非回环时，没有 `CallerResolver` bean 即拒绝启动；有意匿名的服务声明一个返回 `CallerResolver.ANONYMOUS` 的 bean；授权器默认 `ALLOW_ALL` 保留 | 漏了身份映射时所有人都是租户 `(0)`，写进日志的是删不掉的错误数据；不新增键，复用集群开发豁免的判断 | 是 |
| SQ2 | T4：`wow.http.client-facts` 的默认值（S-4），以及 `request-facts` 的大小上限（S-10） | **已定 D297（用户）**：服务需要最终用户的 IP，`client-facts` 默认保持 `true`；每条请求事实加大小上限 | 按 D295，连接的对端是网关，所以 `remote_ip` 要从网关的转发头取：Spring Boot 的 `server.forward-headers-strategy`（`framework` 或 `native`），由网关保证该头不可被客户端伪造（与 D296 同一前提）。Wow 以默认属性源打开该策略（D303 ⑥，取代原定的启动告警）。文档写明 IP 与 UA 是进入不可删除日志的个人数据，以及怎样关闭 | 是 |
| SQ3 | 「只允许信号」的服务身份（S-5） | **已定，维持现状**（D298、D299）：不列 `commands` 即全部领域命令、不列 `reads` 即全部模型，系统命令仍须显式列出（D226 ②） | 内部受信；收紧默认要每份配置补 `*`，维护成本高，收益只针对受信调用方 | — |
| SQ4 | 服务凭据的去向（S-2） | **已定，不做**（D298、D299）；D300 之后内部端口不再有凭据可泄露 | 信号发往对方服务的某个节点，配置里只有对方服务的 URL、没有它的节点成员；要做就得引入对端成员发现，维护成本高；按 D298，能伪造等待来源的只有内网写入者 | — |
| SQ5 | Kafka 作为命令入口的信任边界（S-3） | **按 D298 直接定**：Kafka 属于受信环境；部署文档写明一个上下文的命令主题只由本服务的节点、经 Saga 向它发命令的上下文与 ops写入（附 ACL 示例，#4949），不做信封签名 | — | 文档 |
| SQ6 | 安全开关拼错即失败（S-6） | **已定 D302（用户按推荐）**：所有未知的 `wow.*` 键（Spring 的各属性源）一律拒绝启动；环境变量的松散绑定不检查 | 去掉现有的前缀筛选即可；并入批 4 配置定稿 | 是 |
| SQ7 | 内部端口的传输加密（S-8） | **按 D298 直接定**：内部明文是设计；需要加密的部署用服务网格的 mTLS，文档写明；原生 TLS 不排期，有需求再作为加法（新键、默认关）登记 | — | 文档 |
| SQ8 | 内部端口还要不要令牌（用户 2026-10-26 提出） | **已定 D300（用户，选 ①）**：集群令牌与服务令牌全部去掉；节点与服务在请求头声明身份，内部端口的边界是网络策略；② 令牌改为可选 | 按 D298，两种令牌防的都是内网中的不可信调用方，已不在威胁范围；按 D299，每个服务一个集群令牌、每对调用关系一个服务令牌及其轮换是主要的维护负担，与 SQ0 否掉服务端验签同一理由；GA 前删除最便宜 | 是 |
