- **分工**：主会话是协调者、审查者与架构师：派发工作包、审查与合并、与用户讨论方案，并**独自编写设计文档**（`documentation/designs/**`）。工作包交给子会话（各自的 worktree），子会话从最新 `origin/main` 开分支，开草稿 PR；改完并在本地验证过再推送，不每步推送，不冲突就不 rebase，不重跑只是在排队的作业，每个会话最多 3 个未合并的 PR（2026-11-09：五个会话每步推送时 Actions 积压到 50 多个运行，每次推送约 90 个作业）；已通过审查的 PR 除非 CI 失败不再推送，新的 head 须重新审查，所以主会话不对子会话的 PR 开自动合并，绿了之后按审过的 head 合并；子会话同时最多 5 个（用户 2026-11-09；此前为 2 个），按文件分工。
- **避免冲突与返工**（用户 2026-10-26）：按文件分工，同一组热点文件（宿主装配与属性、内核、ABI 转储较多的模块）同一时间只交给一个会话，派工前先看改动落在哪些文件、有重叠就串行；先定设计再派工，任务说明列出未定的问题，子会话遇到时先停下来问；少叠放，必须叠放时自底向上尽快合并，期间暂停碰同批文件的其他合并；审过且变绿的 PR 立即合并；生成的文件冲突时一律重新生成；设计文档同一时间只开一个 PR。
- **先落盘，再派工**：审查发现登记在[审查台账](reviews.md)，方案写进决定或 PR 描述，未排期的事项登记在路线图 §6。
- **审查标准**（用户 2026-11-09：以资深架构师的要求审查架构与代码质量）：每个 PR 按八条逐条看，任何一条不过就退回，不以「测试通过」代替审查。
  - 清洁：在拥有这个职责的那一层修根因，不在调用处打补丁；没有死代码、重复逻辑、兼容桥与只为这一个用例加的特例；名字说明是什么，注释只写为什么。
  - 高内聚：改动落在该职责所在的模块与类；一个类只因一种原因而变。
  - 低耦合：不新增跨模块依赖，不把内部类型漏到公开面；模块边界（[模块设计](06-modules.md) §3，`:architecture` 把守）不动；SPI、存储与线上格式的改动先有决定。
  - 高性能：决定、追加与订阅的热路径上不多一次往返、一次分配或一把锁，不阻塞线程；动热路径的改动带 Actions 上的 ABAB。
  - 高扩展性：经已有的端口扩展，不按后端或类型写分支；内存有界，按分区而不是全局加锁。
  - 高可用：取消、超时、重试与退避、幂等、崩溃后恢复这些失败路径都有定义并有测试；不静默丢弃，失败可见（台账、指标、日志）。
  - 易用性：公开 API 与运维动作的承诺简单、一致；报错说明该怎么办；行为变了，用户文档同一个 PR 改。
  - 可维护性：回归测试断言的是行为而不是实现；不靠时序碰运气；改动小到能一次读完，读不完就拆。
  - 类不过大（用户 2026-11-09）：单个类或文件过大，读不完也改不动。超过约 600 行的类或文件，修复不得让它再长：要加的逻辑属于哪个职责，就把那个职责抽成自己的类型，抽取小而机械的随修复同一个 PR，否则先出一个不改行为的 PR；新写的类型远低于这个数。600 行是提醒线而不是指标，判断仍看职责是否单一；声明式的文件（配置属性表、文案目录、TCK 规格）按内聚判断。PR 的「Review notes」写明它在超线文件上的行数增减。现存的超线文件见[审查台账](reviews.md)的 X-88。
- **合并**：主会话审查后开启 GitHub 自动合并（squash，锁定审过的 head）；子会话的权限不允许把草稿转为 ready，用户 2026-11-03 授权主会话：子会话的 PR 审过、CI 绿了之后，由主会话转 ready 并合并；`ci-gate` 要求 CI 全绿，并在上传了覆盖率的 PR 上要求改动行的覆盖率（本次运行自己的报告，≥ 89%）不判失败，Codecov 只作参考（X-30）；必需检查为 PR Safety 与 ci-gate。合并说明与提交不带 Claude 署名。
- **CI**：`ci.yml` 按改动范围运行；PR 上不跑 Node 22（main 推送与夜间运行时跑）；负载与基准只在 GitHub Actions 上跑，不在本机测（用户 2026-11-08，取代 2026-11-02 的两地都做）：4 核 runner 代表性能较低、资源受限的服务器，用来评估低配下的表现，并暴露只在资源受限时出现的问题（L3、L4 与浸泡在这里跑）；runner 的型号决定 p99 的噪声带，判定按 D392 取足够的 A/A 样本并定有意义的最小差异。
- **验证命令**（构建需 JDK 21，基准的运行时为 JDK 25，D393；不要 `./gradlew --stop`）：`./gradlew :check :integrationTest`；改 Markdown 后跑 `npx prettier --check` 与 `pnpm check:docs-layout`。
- **设计文档**：新决定在 `decisions.md` 登记一次，同步受影响的专题文档、路线图、本文与 README 的评审日志。

## 6. 用户的长期要求

- 与用户用中文交流；代码、提交与 PR 用英文。默认按推荐推进，不必询问；只有重大决策才给出推荐方案与用户讨论（用户 2026-11-09 重申）。
- 发版：alpha、beta 由用户决定时机；打标签与对外发布须用户确认，rc 与 GA 须用户确认（D202）。
- 新增第三方依赖、改发布自动化、改安全设置或 Dependabot 须先问用户；不绕过 PR 安全门禁。
- 负载测试与基准只在 CI 上跑（用户 2026-11-08）；子会话同时最多 5 个（用户 2026-11-09；此前为 2 个）；不要 `./gradlew --stop`。
- 审查按资深架构师的标准：架构与代码清洁、高内聚、低耦合、高性能、高扩展性、高可用、易用性、可维护性，并避免单个类过大（用户 2026-11-09；细则见 §5 的「审查标准」）；实现交给子会话（Opus），主会话只审查、合并、编辑共享文档。
- 打开的 PR 不超过约 15 个；保持仓库整洁：无孤儿文件、无死链、无名称中的版本特例。
