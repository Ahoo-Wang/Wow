## 5. 工作方式

- **分工**：主会话是协调者、审查者与架构师：派发工作包、审查与合并、与用户讨论方案，并**独自编写设计文档**（`documentation/designs/**`）。工作包交给子会话（各自的 worktree），子会话从最新 `origin/main` 开分支，先开草稿 PR，每步推送；会编译的子会话同时最多 3 个。
- **先落盘，再派工**：审查发现登记在[审查台账](reviews.md)，方案写进决定或 PR 描述，未排期的事项登记在路线图 §6。
- **合并**：主会话审查后开启 GitHub 自动合并（squash，锁定审过的 head）；`ci-gate` 要求 CI 全绿，并在上传了覆盖率的 PR 上等 `codecov/patch` 通过；必需检查为 PR Safety 与 ci-gate。合并说明与提交不带 Claude 署名。
- **CI**：`ci.yml` 按改动范围运行；PR 上不跑 Node 22（main 推送与夜间运行时跑）；负载、浸泡与基准只在 GitHub Actions 上跑。
- **验证命令**（需 JDK 21；不要 `./gradlew --stop`）：`./gradlew :check :integrationTest`；改 Markdown 后跑 `npx prettier --check` 与 `pnpm check:docs-layout`。
- **设计文档**：新决定在 `decisions.md` 登记一次，同步受影响的专题文档、路线图、本文与 README 的评审日志。

## 6. 用户的长期要求

- 与用户用中文交流；代码、提交与 PR 用英文。默认按推荐推进，只有真正需要用户拍板的才问。
- 发版：alpha、beta 由用户决定时机；打标签与对外发布须用户确认，rc 与 GA 须用户确认（D202）。
- 新增第三方依赖、改发布自动化、改安全设置或 Dependabot 须先问用户；不绕过 PR 安全门禁。
- 本机不做负载测试；同一时间本机编译最多 3 个；不要 `./gradlew --stop`。
- 打开的 PR 不超过约 15 个；保持仓库整洁：无孤儿文件、无死链、无名称中的版本特例。
