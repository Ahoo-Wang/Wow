# 切换

切换把流量从 9.x 服务迁到它的 V10 服务。9.x 和 V10 从不同时写入同一份数据：它们之间没有混合版本的协议，所以切换就是一次写入停止，你要选择的是这次停止的时长。

- **离线，默认方式。** 停止 9.x 的写入，导入全部数据，比对，写出快照和标签，启动 V10。它的步骤最少，可能出错的地方也最少。
- **在线，大型系统的选项**，用于导入时间超出可停机窗口的系统。数据导入和跟随期间 9.x 照常服务，V10 处于待机，写入停止缩短为一次最后遍历。

消费另一个 9.x 服务的事件、向它发送命令、调用它的路由或与它共用 api jar 的服务，不会单独切换：整组服务在一个窗口里一起迁移，见[服务群的切换](#cut-over-an-estate)。

[迁移数据](./data)描述 `migrate-data` 的每个命令；本页讲围绕它们的这次切换。

## 离线还是在线 {#offline-or-online}

用演练实测的导入时间与业务能接受的停机时间对比来选择，并记录这个选择。对 9.x 示例及其视图存储（四个租户之上的 50,000 个订单和 12,500 个视图）的演练，在同一个 runner 上走了两条路径：

| 路径 | 写入停止，从 9.x 停止到 V10 提供服务 | 时间花在哪里 |
| --- | --- | --- |
| 离线 | 243.4 s | 完整导入 98.2 s，比对 23.5 s，快照 43.8 s，标签 35.4 s，启动两个服务 36.3 s |
| 在线 | 159.5 s | 最后遍历 15.2 s，比对 24.2 s，快照 46.5 s，标签 38.0 s，激活两个服务 29.3 s |

离线的停止随整个历史增长，在线的停止随 tail 上次读取以来 9.x 写入的数据增长，再加上两者共有的步骤。能在可停机窗口内导入完的历史，就走离线。

## 写入之前先盘点 {#inventory-before-any-write}

为每个存储和每个流记录：

- 环境、负责人、数据库、限界上下文，以及 9.x 和 V10 的版本；
- 9.x 的存储（MongoDB 事件存储、`PrepareKey` 集合、补偿数据库）和 V10 的目标（日志、快照、预留、失败台账）；
- 每种聚合类型的流和聚合数量，以及其中有 9.x 快照的比例；
- 9.x 数据的每个写入者和读取者，以及各自怎样停止；9.x 事件总线的每个外部消费者，以及它要迁往的 V10 Kafka 事件流；
- 9.x 的主题和 V10 的主题，以及它们所在的 broker。9.x 的状态主题名为 `wow.<context>.<aggregate>.state`，V10 发布的事件流默认也是这个名字：在 9.x 用过的 broker 上，给 V10 设置 `wow.kafka.topics.prefix`，否则 V10 的订阅会在这些主题里遇到 9.x 的记录，回退之后 9.x 也会遇到 V10 的记录；
- 每个 9.x 存储的备份，以及一次经过测试的恢复；
- 迁移映射，以及检查它时所对照的 V10 Manifest。

存在未知的写入者、未知的负责人或未经测试的备份时，不要开始任何写入。

## 演练必须留下什么 {#what-the-rehearsal-must-leave}

在隔离的目标上、用生产规模的数据进行端到端演练，留下：

1. 在生产映射上通过的 `check`；
2. 一次被中断后无重复地续跑的 `import`，以及一次什么都不写的第二次运行；
3. 每种差异都已解释并签字确认的 `compare`；
4. 在目标上启动的 V10 服务：对迁移来的聚合发出的命令在下一个版本追加，读取和查询回答迁移来的状态，投影已重建，停放条目已列出；
5. 耗时：离线时是完整导入加上 `compare`、`snapshot` 和 `backfill-tags`，在线时是最后遍历；
6. 两种回退都已演练，并附上无法回退的内容清单。

## 不再轻易回头的那一刻 {#the-point-of-no-easy-return}

在 V10 写入之后回退，需要 V10 写入的每个流都有 9.x 的形式。根据映射和 V10 的 Manifest，列出每个没有 9.x 形式的 V10 事件类型，把清单交给决定切换的人：

- **超出映射 `toRevision` 的事件。** V10 的类升级到了 9.x 所存储形状之外，这往往就发生在迁移本身：以修订号 1 导入的 9.x `OrderCreated`，V10 以修订号 2 写入。V10 创建的每个新订单都会阻断回退。
- **V10 新增的事件或聚合**，没有任何 9.x 名字映射到它。

生产中第一次这样的写入就结束了回退窗口。要么接受从那次写入起切换是单向的，要么在窗口关闭之前，不让这些形状和类型进入 V10 的第一个版本。演练自己的拒绝说明了这一点：V10 以修订号 2 创建了订单和视图之后，`export --dry-run` 拒绝了这两种类型。

## 离线切换 {#the-offline-switch}

1. **公布窗口，停止 9.x 的写入。** 停止 9.x 服务的入口流量，排空它们的命令队列，并同时停止补偿服务。检查没有遗留的 9.x 写入者。
2. **备份 9.x 存储并核实备份。**
3. **导入：** 先 `check`，再 `import`。
4. **关卡：** `compare` 只显示已签字确认的差异种类，没有无法解释的未解决的键或执行。否则就在这里停下并重启 9.x：V10 什么都没有写。
5. **准备读取侧：** `snapshot`，以及在 ABAC 读取事件模型的地方运行 `backfill-tags`。
6. **启动 V10 服务**并探测关键路径：对迁移来的聚合发一条命令、一次读取、一次查询、一个订阅、停放条目。
7. **迁移 9.x 总线的外部消费者**到 V10 发布的事件流。
8. **把流量切到 V10**，然后扩容。让 9.x 保持停止，而不是删除。
9. **观察**约定的信号：错误和 problem 错误码、延迟、等待、订阅延迟、停放的聚合以及消费者。回退的决定依据它们做出。

## 在线切换 {#the-online-switch}

从第一次导入到切换之前，9.x 提供服务，V10 等待：`tail` 跟随 9.x 的写入，每个 V10 节点都以 `wow.node.standby=true` 启动。待机的节点提供对导入所写数据的读取和查询，以 503 `wow.node.standby` 拒绝每条命令，不运行任何订阅、停放重试、作业或快照维护，所以 V10 所做的任何事都不会写入。它报告就绪，所以切换之前就能对照生产数据检查读取侧。

1. **公布窗口，停止 9.x 的写入**，与离线时相同。
2. **做最后一次备份并核实。**
3. **最后遍历。** tail 一直跟随 9.x 直到它停止时，运行 `import --final`：从检查点开始的一次 tail 遍历，并向回看，以捕捉较晚才可见的提交，然后再处理一次预留和未解决的执行。当导入不完整或 tail 已经落后时，它会拒绝，什么都不写；这时最后遍历就是 `import --restart`，时长与完整历史相当。然后运行 `compare`、`snapshot` 和 `backfill-tags`。
4. **关卡**，与离线时相同。否则回到 9.x：V10 节点仍在待机，什么都没有写。
5. **对着生产目标探测待机节点。**
6. **迁移外部消费者。**
7. **激活每个 V10 节点：** 在每个节点的内部端口上发送 `POST /wow/node/activate`，带上 `Wow-Service: <节点的服务>` 和 `{"by": "<operator>", "reason": "<why>"}`。节点加入它的分组，开始它的工作，然后接受命令。激活结束了写入停止；`GET /wow/node/standby` 显示每个节点对此的记录。
8. **把流量切到 V10**，然后扩容。让 9.x 保持停止。
9. **观察**，与离线时相同。

## 回退 {#roll-back}

两条路径，绝不混淆：

- **V10 还没有写入：** 停在关卡处、仍在待机，或者在 V10 第一次提交之前切了回来。停止 V10，把流量切回，在未被改动的存储上重启 9.x。没有需要对账的东西。
- **V10 已经写入。** 9.x 没有 V10 的流，所以只重启 9.x 会丢失它们。停止 V10 的写入，让 9.x 保持停止，运行 `migrate-data export --dry-run`。它为每个上下文输出一个结论：切回、导出 N 个流、窗口已在某个时间关闭，或者 9.x 在切换之后被写入过，这需要先由人来解决。然后 `export` 按反向读取的映射，把 V10 新增的流写回 9.x 存储，可续跑且幂等，并检查每个 9.x 聚合保存的流数量与 V10 中该类型的流数量相同，然后 9.x 再次启动。在演练中，V10 写入的 16,914 条订单命令和 16,815 条视图命令在 52.9 s 内导出并完成检查。

只有事件流能回退：V10 做出的预留、它停放的条目和它的投影视图都没有 9.x 的形式，要手工对账。9.x 的快照显示的是导出的流之前的状态，直到 9.x 再次写入该实例或重新生成快照。一旦 V10 写入过，重新部署 9.x 就不是回退。

## 服务群的切换 {#cut-over-an-estate}

服务群是一组不能分处两个主版本运行的 9.x 服务：彼此消费对方的事件、向对方发送命令、调用对方的路由，或者依赖对方的 api jar。服务群作为一个整体切换：所有服务共用一次写入停止，每个服务的数据都导入，每个节点都激活，回退也只做一个决定。与其他服务没有这类联系的服务，单独切换。

### 为什么一起切换 {#why-it-moves-together}

9.x 服务和 V10 服务之间什么都不互通：

- **V10 不读取 9.x 的主题。** V10 服务只读取 V10 发布的事件流和命令主题，从不读取 9.x 的 `.event`、`.state` 和 `.command` 主题。上游仍在 9.x 上的 V10 服务，收不到上游的任何东西。
- **9.x 不读取 V10。** 没有 9.x 格式的 Sink，所以上游已迁走的 9.x 服务同样什么都收不到，它在 9.x 命令主题上发出的命令也到不了任何 V10 服务。
- **路由变了。** V10 服务只提供 V10 的路由和请求头（[HTTP 与 TypeScript 客户端](./http-and-clients)）：它的命令、快照或事件路由的 9.x 客户端，在它切换时就失效。
- **api jar 不能混用。** V10 服务从对端的 V10 api jar 读取对端的契约，9.x 服务需要对端的 9.x api jar，任何模块的类路径上都不能同时有两者。依赖另一个服务 api 的 api 会把它一起带进来：支付的 api 依赖订单的 api 时，迁到 V10 的订单服务就不能依赖 9.x 的支付 api，因为它会把 9.x 的订单 api 带回来。

9.x 主题和 V10 事件流之间没有桥接。调用服务自己编写的路由，且它的 V10 版本原样提供这个路由，这样的调用不会把两个服务绑在一起。

### 找出服务群 {#find-the-estate}

画一张图，每个 9.x 服务一个节点，下面每种联系一条边；服务群就是与你要迁移的服务直接或间接相连的所有服务。从构建、源码和配置画出这张图，再对照 broker 核实。

1. **api 模块。** 列出每个服务运行时类路径上、以及它自己的 api 模块类路径上，其他服务的 api jar（`com.example` 是这些服务的 group；同一构建内的模块显示为 `project :<name>-api`）：

   ```bash
   ./gradlew -q :order-server:dependencies --configuration runtimeClasspath | grep -o -E 'com\.example:[a-z0-9-]+-api:[^ ]+' | sort -u
   ```

   ```bash
   ./gradlew -q :order-api:dependencies --configuration runtimeClasspath | grep -o -E 'com\.example:[a-z0-9-]+-api:[^ ]+' | sort -u
   ```

   第一条列出服务运行时带的每个 api jar，第二条列出它自己的 api 带给消费者的 api jar。两个 api 模块直接或间接地互相依赖，就构成一个环。

2. **事件。** 9.x 的事件处理器、Saga 和投影（`@EventProcessor`、`@StatelessSaga`、`@ProjectionProcessor`）中，`@OnEvent` 或 `@OnStateEvent` 函数接收另一个服务 api 里的事件类或状态类的那些。
3. **命令和读取。** 服务通过 `CommandGateway` 或从 Saga 发出的、另一个服务 api 里的命令类，以及它对另一个服务的客户端：`wow-apiclient` 接口（`@CoApi`）、快照查询客户端、缓存其状态的 CoCache。
4. **配置。** 每个服务的配置和它的网关路由里提到的其他服务：基础 URL 和服务 ID（`lb://payment-service`）。每一个都是第 3 步里要对上的一次调用。
5. **broker。** 9.x broker 上的每个消费者组，以及它读取的主题：

   ```bash
   kafka-consumer-groups --bootstrap-server kafka-9x:9092 --describe --all-groups
   ```

   某个服务的消费者组读取另一个上下文的 `.event` 或 `.state` 主题，就是第 2 步的一条边。不属于你任何服务的消费者组是外部消费者，它在同一个窗口里改到 V10 发布的事件流。

把服务群记成一张表：

| 服务 | 消费谁的事件 | 向谁发命令或调用谁 | 它的 api 依赖 |
| --- | --- | --- | --- |
| 订单 | 支付 | 库存 | 支付的 api |
| 支付 | 订单 | 订单 | 订单的 api |
| 库存 | 订单 | — | — |

订单和支付互相消费事件，它们的 api 模块构成一个环；库存消费订单的事件。三者是一个服务群。调用其中任何一个的前端和网关都随它一起改，它们 9.x 主题的每个外部消费者也一样。

它们的源码迁移也一起进行：每个 V10 服务都依赖对端的 V10 api jar 编译，所以先按依赖顺序改写 api 模块，处在环上的一起改写。

### 一个窗口 {#one-window}

服务群共用一次写入停止。每个服务仍按自己的导入时间选择[离线还是在线](#offline-or-online)，服务群的停止时长等于其中最慢的那个服务所走的路径：在线导入的服务在窗口之前就用 `tail` 跟随 9.x，离线导入的服务在窗口之内完成全部导入。

1. **停止服务群的每个 9.x 写入者。** 停止每个服务的入口：网关、前端、定时任务、外部生产者。让服务群排空，直到服务群的任何 9.x 消费者组在任何主题上都没有延迟（`kafka-consumer-groups --describe` 显示每个组的 `LAG`），并反复检查，直到一轮检查都没有延迟为止，因为 Saga 发出的命令会产生别人要消费的事件。然后停止每个 9.x 节点和每个补偿服务，并记下最后一个写入者停止的时间：**停止时刻**。

   V10 不会接手 9.x 还没处理的东西：本上下文的 Saga 或反应器从它的日志末尾开始，另一个上下文事件流的 Saga 或反应器从停止时刻开始（第 4 步）。写入停止时某个 9.x 消费者还没处理的事件，就再也没有人处理。

2. **备份**服务群的每个 9.x 存储并核实备份。
3. **导入每个服务。** 每个 V10 日志存储由一次独立的 `migrate-data` 运行迁移，有自己的配置、映射和检查点，所以这些运行可以并排进行：离线是 `check` 和 `import`，在线是 `import --final`。然后每个服务过关卡：`compare` 只显示已签字确认的差异种类；接着运行 `snapshot` 和 `backfill-tags`。任何一个服务没过关卡，整个服务群就停下：重启每个 9.x 服务，因为没有任何 V10 服务写入过。
4. **设定对其他上下文的订阅从哪里开始。** 服务一旦处于活动状态，它的 Sink 就把导入的全部历史写到它发布的事件流上，而另一个上下文事件流的 Saga 或反应器在没有检查点时从主题的开头开始（[发布与消费事件流](../guide/published-streams#where-it-starts)）：它会再次对这段历史采取行动，为过去发出命令。第一次启动之前，把每个这样的订阅设为从停止时刻开始：

   ```yaml
   wow:
     subscriptions:
       "[payment.OrderPaymentSaga.onOrderCreated]":
         start: "2026-11-07T22:00:00Z"
   ```

   每条导入的流都保留 9.x 的提交时间，早于停止时刻，而 V10 提交的一切都在它之后。另一个上下文事件流的投影仍从开头开始，用发布的历史构建它的读模型：给发布的主题足以容纳这段历史的保留期。

5. **以待机方式启动每个 V10 节点**，离线导入的服务也一样（`wow.node.standby=true`），并对照导入的数据探测每个服务的读取和查询。
6. **把每个服务 9.x 主题的外部消费者**改到 V10 发布的事件流。
7. **激活每个服务的每个节点**：发送 `POST /wow/node/activate`，与[在线切换](#the-online-switch)相同。作业和 Saga 在激活时开始，而待机的节点拒绝命令，同步调用也在其中：在同步调用没有环的地方，先激活被同步调用的服务（`SagaContext.call`，以及经 `wow.peers` 的 `CommandClient` 和 `QueryApi`），再激活调用它的服务。命令主题上发出的命令会在那里等待，直到它的上下文被激活。
8. **每个服务的每个节点都处于活动状态之后，把服务群的流量切到 V10**，前端和网关一起切，然后扩容。让每个 9.x 服务保持停止。
9. **观察**每个服务，以及跨服务的流程：订单被支付，它的库存被预留。

### 演练服务群 {#rehearse-the-estate}

先按[演练必须留下什么](#what-the-rehearsal-must-leave)演练每个服务，再把服务群作为一个整体演练：在隔离的目标和隔离的 broker 上，用同一时刻取得的每个服务的生产数据副本。

1. 按上面的顺序端到端走完整个窗口，每个服务的 `migrate-data` 运行并排进行，并计时：服务群的停止时长，以及每一步所占的部分。
2. 没有 Saga 或反应器对导入的历史采取行动：从激活到第一个请求之间，发出的命令只有定时任务的命令。
3. 跨服务的流程：新订单被支付、它的库存被预留，每个服务都通过主题和调用回应其他服务。
4. 服务群的回退，两条路径都演练，并附上每个服务 `export --dry-run` 的结论。

### 服务群的回退 {#roll-back-the-estate}

服务群要么整体回退，要么不回退：单独回到 9.x 的服务，已经失去了与仍在 V10 上的其他服务的联系。

- **还没有任何 V10 服务写入：** 停止每个 V10 服务，把流量切回，在未被改动的存储上重启每个 9.x 服务。
- **某个 V10 服务已经写入。** 停止每个 V10 服务的入口，让服务群排空，直到每个订阅的积压都为零（`wow.subscription.backlog`），再停止每个 V10 节点。在每个服务的日志存储上运行 `export --dry-run`。只有每个结论都允许时，服务群才能通过导出回退：第一个关闭窗口的服务就关闭了服务群的窗口，所以服务群[不再轻易回头的那一刻](#the-point-of-no-easy-return)是其中各服务最早的那一刻。然后对每个服务运行 `export`，再启动每个 9.x 服务。

9.x 不发布导出的流，所以没有任何 9.x 消费者能看到 V10 在窗口内写入的东西。V10 的 Saga 为此所做的事已经在它们写入的那些服务的导出流里，但 9.x 投影的读模型缺少这些流：与其他不能回退的内容一起手工对账。

## 报告 {#report}

记录离线还是在线以及原因；对服务群，记录它的服务、把它们绑在一起的联系以及停止时刻；盘点结果；演练的证据，即每个命令及其退出码和计数；已签字确认的差异种类；无法回退的类型以及对它们做出的决定；窗口的各项耗时；以及切换中实际执行的步骤。数据已导入、V10 已提供服务、消费者已迁移、回退已演练，是四个独立的事实：任何一个都不意味着下一个。
