# Wow 用户文档重写设计

## 背景

Wow 当前拥有完整的中英文 VitePress 站点、根 README 和若干模块 README，但入口与内容分类同时混用了读者角色、学习阶段、框架组件和文档类型。顶部的“指南”与“入门导航”也承担了相近的分流职责，新用户需要先理解站点结构，才能开始学习。

本次重写首先服务第一次接触 Wow 的 Kotlin/Java 开发者。成功标准不是“浏览过文档”，而是用户能在 30 分钟内从项目模板创建应用，完成一个最小聚合，使领域测试通过，并通过真实 HTTP 命令写入后读取事件溯源状态。

## 已确认的设计决策

- 采用“用户旅程优先”的信息架构，不按仓库模块或文档理论组织一级导航。
- 中文是内容基线；已有中英文页面逐页保持章节、示例和技术语义一致。
- [`documentation/docs/zh/guide/introduction.md`](../../documentation/docs/zh/guide/introduction.md) 是价值叙事的权威来源，不因精简导航而删除或稀释。
- 根 README、站点首页、简介、快速上手、指南和参考页各自承担单一职责，使用摘要和链接复用事实，不复制整段内容。
- 保留现有页面 URL 和文件路径。重写信息架构主要通过导航、侧栏、入口页和页面内链接完成。
- 不增加文档框架、生成器或第三方校验依赖；优先使用 VitePress、Gradle、pnpm 和仓库现有测试能力。

## 范围

### 包含

共 160 个现有 Markdown 文档：

1. 根入口：`README.md`、`README.zh-CN.md`。
2. VitePress 站点：`documentation/docs/en/` 与 `documentation/docs/zh/` 下的 148 个 Markdown 页面。
3. 面向用户的模块 README：
   - `wow-api/README.md`、`wow-api/README_CN.md`
   - `wow-core/README.md`、`wow-core/README_CN.md`
   - `test/wow-test/README.md`、`test/wow-test/README.zh-CN.md`
   - `compensation/README.md`
   - `compensation/dashboard/README.md`
   - `example/transfer/README.md`
   - `wow-benchmarks/README.md`
4. 为实现新信息架构而必须调整的 VitePress 导航、侧栏和站点配置。

已有双语页面必须同步重写。只有单一语言的模块 README 保持当前语言，并链接到双语站点中的权威页面；本次不为它们新增镜像文件。

### 不包含

- `document/design/` 中既有设计、证据与实验记录。
- `wow-benchmarks/results/reports/` 中的历史基准报告。
- `skills/` 下的 Skills、参考资料和评测夹具。
- `AGENTS.md`、`CLAUDE.md`、`CONTRIBUTING.md`、`SECURITY.md`、`CODE_OF_CONDUCT.md`。
- 文档主题视觉重构、新插图、站点框架替换、搜索服务或分析系统。
- Gradle 模块、公开 API、OpenAPI/Schema、CI/CD、PR、合并、发布和部署行为变更。

如果文档重写发现源码、配置、示例或公开契约缺陷，只记录为独立问题，不在文档批次中顺手修改实现。

## 信息架构

站点一级导航调整为：

| 入口 | 职责 | 主要内容 |
| --- | --- | --- |
| 开始使用 | 建立价值认知并完成首次成功 | 简介、30 分钟快速上手、接入现有项目、按角色评估与参与 |
| 开发指南 | 从领域模型构建完整应用 | 核心概念、建模、命令与事件、投影与查询、Saga 与补偿、测试与 OpenAPI |
| 生产运维 | 说明运行责任与风险闭环 | 生产配置、可观测性、恢复与重放、排障、迁移、BI 运维 |
| 参考 | 提供可核对的精确信息 | 配置、模块、扩展、兼容性、示例 |
| API | 查询符号和签名 | Dokka API 与指南中的类型深链 |
| 资源 | 承载非主学习路径内容 | 文章、项目模板、Agent Skills、生态、更新日志 |

“入门导航”不再作为与“指南”竞争的一级入口。原有角色页面保留 URL，归入“开始使用”的“评估与参与”。文章保留内容和 URL，但退出新用户的主学习路径。

侧栏按用户完成任务的顺序排列，不要求读者从头到尾阅读。每个分区首页提供：适用读者、最短路径、完成标志和下一步。

## 价值叙事

《简介》继续完整表达以下不可丢失的主张：

1. 软件研发应围绕业务价值和领域知识，而不是表结构与 CRUD。
2. “领域模型即服务”意味着开发者表达领域行为，Wow 连接命令、事件、状态、OpenAPI 与运行时组件。
3. `命令 → 领域事件 → 状态` 让业务决策可见、可测试、可追溯。
4. `SENT`、`PROCESSED`、`SNAPSHOT`、`PROJECTED` 等完成语义用于准确表达异步读写边界。
5. 领域测试、投影、BI 与审计建立在具有业务语义的数据之上。
6. 采用 Wow 同时意味着承担事件演进、最终一致性、幂等、恢复和响应式边界等责任；简单 CRUD 等场景应谨慎采用。

不同入口的职责如下：

- 根 README 和站点首页：用最短篇幅回答“是什么、为什么值得继续看、从哪里开始”。
- 简介：提供完整价值论证、适用边界与采用成本，是其他页面引用的权威来源。
- 快速上手：用可运行的垂直切片证明价值，不重复长篇理念。
- 开发与运维指南：解释怎样完成实际任务，以及怎样验证完成。
- 参考与 API：记录精确事实，不承担营销或理念叙事。

## 页面模型

### 教程

用于“开始使用”。顺序固定为：预期结果、最少前置条件、完整步骤、可观察验证、下一条学习路径。教程必须形成一个可运行的垂直切片，不能只展示零散代码。

### 操作指南

用于开发与生产任务。内容包括：任务和适用场景、前置状态、最短步骤、成功验证、已证实的失败模式与恢复。一个页面解决一类任务，不同时承担完整概念教学。

### 原理说明

用于核心概念和深入内容。内容包括：问题、心智模型、运行机制或数据流、取舍与边界、相关操作指南。原理页不复制配置表和 API 签名。

### 参考页

内容包括：模块或契约范围、配置项与默认值、兼容性与限制、最小示例、源码/测试/API 链接。所有事实必须能从当前版本的公开契约、配置、实现或测试中核对。

### README

根 README 负责项目定位和文档分流。模块 README 负责模块用途、适用场景、依赖、最小用法、公开边界，并链接站点详解。README 不复制站点全文。

### 共同底线

- 开头让读者立即判断本页目的、适用对象和预期结果。
- 一个事实只设一个权威页面，其他页面使用摘要与链接。
- 优先复用仓库已有 Demo、订单/购物车和 Java 转账示例，不创建第二套文档专用实现。
- 示例中的命令、类型、配置键、路由和默认值必须在对应源码或可运行环境中验证。
- 当前版本号、依赖版本和性能数字不得脱离事实来源手工复制到多个页面。
- 结尾给出一个明确下一步，不堆砌无优先级的“相关链接”。

## 首次成功路径

快速上手以独立演进的 `wow-project-template` 为入口，默认使用内存总线、事件存储和快照存储，避免把 Kafka、MongoDB 或 Redis 变成首跑前置条件。

完成标志必须同时满足：

1. 从模板创建并克隆项目，确认模板使用的 Wow 版本。
2. 领域测试通过，证明命令产生预期领域事件并能得到预期状态。
3. 服务成功启动。
4. 通过 HTTP 发送真实命令，并检查命令结果中的成功状态、等待阶段、聚合 ID 与版本。
5. 按版本读取事件溯源状态，证明状态确由已持久化事件重建。

外部基础设施、完整生产配置、Saga 扩展演示和项目结构详解移到后续页面，不能阻塞这条主路径。模板与本站版本不一致时必须明确提示并验证，不能假定二者同步。

## 事实来源与重写数据流

事实来源优先级为：

1. 当前 tag 的公开契约和生成契约。
2. Gradle 配置、版本目录和 Spring 配置元数据。
3. 运行时实现与模块装配。
4. 测试、示例和 CI 工作流。
5. 既有文档。

每个批次按以下顺序推进：

```text
目标页面清单
  → 定位源码/配置/测试事实
  → 重写中文基线
  → 生成并核对英文镜像
  → 更新导航与交叉链接
  → 运行最窄相关示例/测试
  → 构建整站并检查差异
```

文档与事实来源冲突时，以事实来源为准并修正文档。无法证实的能力、性能、兼容性或生产承诺不得发布；必要时改成明确限定的经验描述或删除。

## 兼容性与链接

- 不移动现有 Markdown 文件，不改变既有页面 URL。
- 导航重组通过 `navbar.*.ts`、`sidebar.*.ts`、分区首页和页面内链接实现。
- 合并重复内容时，原页面保留简洁、独立有用的说明，并链接权威页面；不留下空壳页面。
- 保留 `README_CN.md`、`README.zh-CN.md` 等既有文件名，不在本次统一命名。
- 中英文页面使用相同的目标结构、代码和锚点语义；语言自然表达可以不同。

## 异常与不确定性处理

- **源码与文档不一致**：修正文档并在批次记录中注明事实来源，不顺手修改源码。
- **外部模板漂移**：重新核对模板版本和命令；无法完成首次成功路径时，该批次不得验收。
- **示例无法运行**：先定位最小失败原因；只有文档错误才修改文档，实现缺陷单独记录。
- **中英文不一致**：以批准后的中文基线为准修复英文；任何一侧缺页或技术语义不同都阻塞批次完成。
- **历史性能数据缺少来源**：删除当前能力承诺，或链接带代码版本、硬件、参数和结果的证据。
- **外链或锚点失效**：优先链接仓库内稳定入口；源码行号只用于需要精确证据且可接受随版本更新的页面。

## 实施批次

整个范围不能作为一个不可审查的大提交。按以下顺序形成可独立构建、评审和回滚的批次：

1. **信息架构基础**：中英文导航、侧栏、站点首页、指南导览和角色入口归并。
2. **价值与首次成功**：根 README、简介、核心概念、快速上手、接入现有项目。
3. **领域开发主线**：建模、测试、命令网关、事件存储、快照、事件处理、Saga 与补偿。
4. **读模型与接口**：投影、查询、数据权限、OpenAPI、Schema、API 客户端与相关示例。
5. **生产运维与迁移**：配置、模块依赖、可观测性、指标、恢复、排障、BI 运维和迁移。
6. **扩展与深入参考**：所有扩展、运行时生命周期、数据流、编译器、序列化、事件演进等深入页面。
7. **角色、文章与模块入口**：角色指南、文章索引、模块 README 和生态入口。
8. **全站收口**：双语一致性、导航覆盖、交叉链接、冗余内容、术语和最终整站构建。

每个批次只修改该批次目标和必要的导航/链接，不提前重写后续页面。当前批次验收后再开始下一批，避免 160 个文件长期同时处于未完成状态。

## 验收与验证

每个批次至少执行：

```bash
cd documentation
pnpm docs:build
git diff --check
```

根据页面内容追加最窄验证：

- 快速上手：在干净模板项目中执行领域检查、启动服务、发送 HTTP 命令并读取版本化状态。
- 示例页：执行对应示例模块的最窄 `check`、`test` 或 `run` 验证。
- 配置与扩展页：核对 Spring 配置元数据、Gradle feature capability 和模块依赖。
- 测试页：运行页面使用的测试类或模块检查。
- API、查询与序列化页：核对公开契约及相关契约/集成测试。

全站收口批次还必须验证：

- 148 个中英文站点页面成对存在，并保持章节职责、代码示例和技术语义一致。
- 新导航覆盖所有站点页面，没有孤立页面或重复主入口。
- VitePress 未报告失效的内部链接和锚点。
- 根 README 与模块 README 的仓库内链接有效。
- 不存在无证据的当前性能、质量、兼容性或生产承诺。
- 工作树不包含构建输出、`node_modules`、Visual Companion 草稿或其他本地状态。

## 明确不做的设计

- 不创建文档内容数据库、生成管线或自定义 DSL。
- 不引入新的链接检查、翻译或内容管理依赖；现有工具不足时才另行设计。
- 不为了统一目录而移动 148 个站点页面。
- 不把所有页面强制套成相同标题结构。
- 不以大段自动翻译替代中英文技术语义核对。
- 不在文档任务中修复框架实现、发布新版本或部署站点。

## 后续计划边界

本设计批准后，先为“信息架构基础”批次编写实施计划。后续批次沿用本设计的共同规则，但分别计划、验证和交付；如果某批次发现会改变公开契约、生成内容、模块边界或站点框架的隐藏复杂度，必须停止并单独设计。
